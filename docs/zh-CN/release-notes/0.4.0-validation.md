## Chat 补验与源码冻结

原生补验发现了真实的短消息失败：运行时上下文为 4096 token，Chat 使用默认的 4096
token 输出预算（模型的显式输出设置为空）。输入估算遗漏了模板／tokenizer 开销；后端
报告实际输入为 22 token，剩余输出额度为 4074，但 App 直接报告上下文溢出，没有使用
该额度。失败的原生尝试和直接 HTTP 复现保存在初始目录的 `native-chat-followup/`，
不计入通过验收。

现在只剩最新问题、无法再裁剪更早对话时，Chat 会按后端返回的正数且更小的输出额度
重试一次。HTTP 和首 token 前的流式错误使用同一规则；零、负数或未降低的上限不触发
重试，第二次溢出仍会失败。最新问题和保存的模型设置不变。修复仅涉及 Swift，不改变
后端上下文限制。

控制器测试最初 42 项通过。最终复查还改为按实际发送的消息判断是否仍有历史可裁剪，
避免以前没有回复的问题阻止预算恢复；包含该回归的完整 Swift Release 测试 811 项通过。
源码指纹、构建日志
和原生结果保存在 `.build/release-readiness/0.4.0-chat-context/`。原生测试使用提交前的
App：Swift 可执行文件已重建，固定的 Rust／MLX 组件未变；该派生 App 的新签名验证通过，
但未对其公证。

维护者从真实菜单栏打开 Chat，并在 CUA 丢失窗口目标时关闭重开。随后通过原生 AX 控件
完成以下验证：

- 原先失败的短消息在同一 4096-token 运行时上下文中回复 `IRONMLX_CHAT_OK`。
- 关闭重开后回复仍然可见；显式设置 512-token 输出预算后，后续问题能回忆同一 marker。
- 新对话为空，历史选择可恢复两个完整问答。
- 达到长度上限时保留回复并显示截断提示；另一次立即停止保留非空部分回复并标记 `stopped`。

4 个用户提示产生 3 个持久化对话；内部预热和 413 重试不计入该提示数。第一次停止尝试
在取消前达到长度上限，只计入截断覆盖。临时 App／模型克隆已移除，生产偏好变更已按
原始字节恢复。

授权提交后，干净重建、签名／公证、归档、安装和完整 App 更新结果保存在补验目录的
`readiness.json`，绑定精确 commit 和制品哈希。本记录保留此前工作区及提交前身份，
不将这些旧制品改称为干净源码构建。

## 剩余发布门禁

- 核对最终冻结源码的 CI；新本地提交须在另行授权推送后才能得到远端 CI 覆盖。
- 确定不可变的发布 tag，通过源码／tag／Bundle 身份检查；补验台账中的干净构建结果不免除这项有意推迟的 tag 门禁。
- main fast-forward 和公开 Release／feed 发布分别取得后续授权。

# Qwen3.6 35B A3B B4 30K prompt 并发性能对比

[English](../../benchmarks/qwen36-moe-b4-30k.md)

> [!NOTE]
> 本页是 30K 长 prompt 的并发性能对比；短 prompt 的对比见 [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)和 [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-short.md)。30K 长 prompt 性能对比测试系列：
>
> - Qwen3.6 35B A3B B4 并发
> - [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-30k.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.6-35B-A3B 混合专家（MoE）模型，四个请求同时到达服务。所有计分请求都使用约 30K token 的长 prompt（每个请求输入 30,732 token），输出上限为 256 token。这种负载对应几个用户或几个 Agent 同时把长文档、代码库片段交给同一个本地服务的场景；四个 30K 输入都要读完，最后一个请求要等约半分钟。本页结论只适用于这种负载。参与本次并发性能对比的本地推理应用有 oMLX、Splash 和 IronMLX，其中 Splash 与 [B1 页](qwen36-moe-b1-30k.md)一样测了两种设置（见下方说明）。TensorFold 1.1.6 不支持这个模型，没有参测。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

> [!NOTE]
> 本页 Splash 测了两种设置，以 `--verify-rows` 的取值区分（含义见[短 prompt B1 页](qwen36-moe-b1-short.md#splash-的两种设置)）：
>
> - **Splash auto**：默认设置（`--verify-rows auto`）。速度更快，但在这个模型上，贪心输出每次运行可能不同。
> - **Splash all**：`--verify-rows all`，每个周期验证整个草稿块；单请求时输出可复现，本页的并发负载下输出不可复现（见[Splash 的两种设置](#splash-的两种设置)）。

## 结论

30K 长 prompt B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下（名次在 4 个配置之间排列）：

<!-- benchmark:kpis qwen36-moe-b4-30k -->

- **完成时间中位数最短。** 四个请求完成时间的中位数为 20.3 s，两轮都第一；Splash auto 为 21.3 s，比 IronMLX 长 5.0%，Splash all 为 21.4 s，oMLX 为 32.9 s。
- **解码阶段输出速度最高。** 在有请求正在解码的时间里，IronMLX 每秒输出 198.0 个 token，两轮都第一，约为 Splash auto（83.0）的 2.4 倍；Splash all 为 77.9，oMLX 为 75.1。IronMLX 每个请求出首字后 0.7–1.9 s 就完成。
- **内存最低。** 服务时内存峰值为 22.1 GiB，两轮都最低；Splash 两种设置约 22.6 GiB，oMLX 为 34.2 GiB。
- **首字时间中位数第三。** 四个请求首字时间的中位数为 19.1 s，比 Splash auto（17.3 s）长 10.0%，比 Splash all（17.4 s）长 9.4%，两轮都是如此；oMLX 为 27.2 s。
- **prefill 速度最慢，整批完成较晚。** 四个 30K 输入合计 122,928 个 token，IronMLX 的整批 prefill 速度为 3,786 tok/s，两轮都最慢，比 oMLX（4,340）低 12.8%，比 Splash 两种设置（约 4,240）低 10.7–10.8%。30K 下各应用 83–95% 的整批时间花在读入四个输入上，所以 IronMLX 的解码优势没有体现在整批结果上：最慢请求的首字时间（32.5 s）最长，最慢请求的完成时间（34.0 s）与 oMLX（34.1 s）并列第三，比 Splash auto（30.4 s）长 11.7%；整批吞吐（30.1 tok/s）也与 oMLX 并列第三，比 Splash auto（33.7）低 10.4%。
- **输出可复现。** IronMLX 每个任务在所有批次中的输出逐字节相同，并且与 [B1 页](qwen36-moe-b1-30k.md)中单独处理时相同；oMLX 和 Splash 两种设置的输出都随批次变化。

### prefill 速度与首字时间

整批 prefill 速度是四个请求的输入 token 总数除以从最早发出请求到最后一个请求出首字的时间，反映服务读入长输入的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，在长 prompt 下主要反映读入长输入和排队等待的时间。图中越靠右下表现越好。

| 单请求解码速度（tok/s，辅助）³ | 209.4 (209.3–⁠209.6) | 47.7 (45.7–⁠49.6) | 87.2 (85.4–⁠89.0) | 84.2 (82.4–⁠86.0) |

首字时间中位数、解码阶段输出速度和解码并发度的先后两轮完全一致。完成时间中位数两轮都是 IronMLX 第一、oMLX 最后；最慢请求的首字时间两轮都是 oMLX 第一、IronMLX 最后；整批 prefill 速度两轮都是 oMLX 第一、IronMLX 最后；内存和单请求解码速度两轮都是 IronMLX 第一、oMLX 最后；这些指标中 Splash 两种设置在两轮中先后互换。最慢请求的完成时间和整批吞吐两轮都是 Splash auto、Splash all 领先，IronMLX 与 oMLX 在两轮中先后互换。

> [!NOTE]
> ¹ 这三项是测试完成后，用每个计分批的客户端时间戳推导出的，不在事先写定的测试协议中，定义如下（都包含传输时间和第一个输出 token 的生成时间，不等于引擎内部的计时）：
>
> - 整批 prefill 速度：四个请求的输入 token 总数（服务端计数，共 122,928）÷ 从最早发出请求到最后一个请求收到第一个输出内容的时间。
> - 解码阶段输出速度：整批实际输出的 token 数 ÷ 至少有一个请求在解码的总时间（每个请求从收到第一个输出内容到 `[DONE]` 算作在解码，取四个区间的并集）。这段时间里可能同时在读入其他请求的输入，所以它是有负载时的有效解码速度。
> - 解码并发度：四个请求的解码时间之和 ÷ 上述并集。1 表示从没有两个请求同时解码，4 表示四个请求始终一起解码。

> [!NOTE]
> ² 整批吞吐为整批实际输出的 token 数 ÷ 整批完成时间（最早发出到最后一个 `[DONE]`）。30K 下整批时间主要花在读入输入上，这项基本只反映 prefill 速度，因此只作辅助参考。每批都输出 1,024 个 token（Splash auto 有一个请求客户端重新计数为 255，在允许的误差内，按 256 计）。整批完成时间与最慢请求的完成时间只差各请求发送时刻的差异（不超过 2.7 ms）。

> [!NOTE]
> ³ 单请求解码速度取决于各应用如何安排四个请求：一个请求如果在其他请求读入之前或之后单独解码，速度接近单请求；如果和其他请求的 prefill 交替进行，速度会低很多。

> [!NOTE]
> 服务时内存峰值在计分批期间测量，包含四个 30K 输入的 KV 缓存。加载模型和预热阶段的峰值：IronMLX 约 22.1 GiB，与服务时相当；oMLX 约 23.4–23.9 GiB，Splash 两种设置约 21.2–21.3 GiB。本页不比较加载阶段的内存。

### Splash 的两种设置

四个 30K 请求并发时，Splash 两种设置的首字时间几乎相同；Splash auto 的整批吞吐比 Splash all 高 2.4%（33.65 对 32.87 tok/s），最慢请求的完成时间短 2.3%（30.4 对 31.2 s）。

与单请求时不同，本页 Splash all 的输出也不可复现：同一 prompt 在不同批次中的输出不同（每个任务 2–4 种），也都与 [B1 页](qwen36-moe-b1-30k.md)中单独处理时不同。本页没有确定原因。

### 请求响应时间线

下图展示四个请求同时发出后，每个请求的首字时间和完成时间，用于观察各应用在并发负载下如何安排四个请求的处理。横轴是从发出请求起经过的时间；竖线表示请求收到第一个输出内容的时间，圆点表示请求完成的时间。图中数值的取法是：在每个批次内，把四个请求的首字时间和完成时间分别按先后排序，再对 6 个批次同一位次的数值取中位数。因此竖线和圆点是分别排序的，同一位次的竖线和圆点不一定属于同一个请求。

<!-- benchmark:timeline qwen36-moe-b4-30k -->

客户端同时发出请求，不等于引擎内部会合批。从时间线和各服务自己的日志、状态接口看，四个请求的处理方式如下：

- **IronMLX dev (c6ef14ec2)：** 四个输入依次读入，首字约在 6.8、15.0、23.3、32.5 s 出现；每个请求出首字后 0.7–1.9 s 完成，完成日志显示每个请求都单独解码（批宽 1）。下一个请求的首字在上一个请求完成后 7.1–7.6 s 出现，与 [B1 页](qwen36-moe-b1-30k.md)单个请求的首字时间（7.13 s）相当：一个请求解码时，下一个请求的输入没有同时读入。每批有 2 个验证窗口不带草稿（共 12 个，占全部 2,372 个窗口的 0.5%），由默认的窗口成本策略决定，其余窗口都带草稿。
- **oMLX 0.7.2：** 第一个请求单独读入，首字约在 6.7 s 出现；其余三个请求的输入一起读入，首字集中在 26–28 s。之后这几个请求一起做批量推测解码（日志中这条批量路径名为 “Lightning MTP”）；批处理中会做批量与标准解码的校准，部分请求在停放后以标准解码收尾。解码并发度为 1.69，是唯一有请求同时解码的应用。
- **Splash 1.4.1 auto 与 all：** 四个输入依次读入，首字约在 6.3、13.6、21.0、29.0 s 出现；上一个请求的解码与下一个请求的读入同时进行，下一个请求的首字在上一个请求完成后 1.8–4.6 s 就出现，因此首字比 IronMLX 早，但每个请求的解码要 1.5–6.6 s，单请求解码速度较低。

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX dev (c6ef14ec2) | `dev` 分支提交 `c6ef14ec2` 的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结 | 按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 32768 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置（ANE 对这个模型不适用），不加任何调优开关 |

| TensorFold 1.1.6 | — | 未参测：按其 [1.1.6 文档](https://github.com/ashhart/TensorFold/blob/v1.1.6/docs/recipes/qwen3.6-moe.md)，Metal 原生引擎没有这个模型的家族（`qwen3_5_moe`），只能使用旧版 Python 引擎 |

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次每个计分请求都因长度结束，服务端计数恰为 256。
- **Prompt：** 六个 30K prompt（三个编程、三个知识问答，与 B1 页相同），每个加上聊天模板后为 30,732 token；分成三组，每批四个 prompt 互不相同。每个请求的服务端 prompt token 数都核对为 30,732，没有截断或丢弃输入。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批（短 prompt），再同时发出一个四请求计分批（最大发送时间差 2.7 ms），然后关闭服务。2 轮 × 4 个配置 × 3 组 prompt = 24 个会话；两轮顺序为 ABCS、SCBA（互为倒序；A 为 IronMLX，B 为 oMLX，C 为 Splash auto，S 为 Splash all），每个配置的平均位置相同，三组 prompt 的先后按轮次轮换。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为实际输出 token 数（客户端按 target tokenizer 计数；因长度结束的请求计 256）除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。整批 prefill 速度、解码阶段输出速度和解码并发度是测试完成后用同一批时间戳推导的，定义见[各项指标对比](#各项指标对比)的注释。
- **有效性：** 24 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。正式运行前的预检中，沿用自短 prompt 测试的检查要求 IronMLX 每个验证窗口都带草稿，而默认的窗口成本策略在 30K 下会有少量不带草稿的窗口；正式运行前把这项检查改为允许不带草稿的窗口不超过该批窗口数的 10%，并在已有的真实记录上回放确认。
- **输出计数：** 服务端计数为准；客户端用 target tokenizer 对完整输出重新计数作核对，允许相差不超过 3 个 token（重新编码时相邻 token 的切分可能与生成时不同）。本次只有 Splash auto 的一个请求（知识 1）重新计数为 255，其余都恰为 256。
- **输出可复现性：** 每个任务在 4 个批次中出现（两轮 × 两组含该任务的 prompt）。IronMLX 每个任务 4 次输出逐字节相同，并且与 B1 页中单独处理时相同；Splash all 每个任务有 2–4 种不同输出，oMLX 有 2–4 种，Splash auto 每个任务 4 次输出都不同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优（Splash all 是另加的对照配置，每个周期验证整个草稿块）；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。TensorFold 没有参测，是因为其当前版本不支持这个模型，这不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为开发版本。** 本页的 IronMLX 是 `dev` 分支的构建，不是正式发布版本；正式发布版本的表现可能不同。
- **没有分出先后的项目。** IronMLX 与 oMLX 的整批吞吐和最慢请求的完成时间都只差 0.3%，两轮各领先一轮。Splash 两种设置在多项指标上两轮先后互换。
- **事后推导的指标。** 整批 prefill 速度、解码阶段输出速度和解码并发度是在测试完成后才定义的，用的是测试中已记录的客户端时间戳，没有重跑；它们不是事先写定的比较项。
- 其他输入长度、其他模型、其他并发度或真实多用户负载下的表现。本页只测了约 30K token 一种长输入，四个请求同时到达。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量；也没有评估 oMLX 和 Splash 输出的变化对回答质量有没有影响。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 多轮对话中的长上下文复用。每个计分请求都是全新的长输入且不使用前缀缓存。
- 批次间波动。同一组 prompt 两轮之间，oMLX 的整批吞吐最多相差 5.2%（第一组：29.44 到 30.98 tok/s），Splash all 1.9%，Splash auto 1.2%，IronMLX 1.1%。

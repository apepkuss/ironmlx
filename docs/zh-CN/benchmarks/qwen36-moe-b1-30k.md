# Qwen3.6 35B A3B B1 30K prompt 性能对比

[English](../../benchmarks/qwen36-moe-b1-30k.md)

> [!NOTE]
> 本页是 30K 长 prompt 的单请求性能对比；短 prompt 的对比见 [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)和 [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-short.md)。30K 长 prompt 性能对比测试系列：
>
> - Qwen3.6 35B A3B B1 单请求
> - [Qwen3.8 27B B1 单请求](qwen38-dense-b1-30k.md)
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-30k.md)

B1 单请求性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.6-35B-A3B 混合专家（MoE）模型，服务每次只处理一个请求。所有计分请求都使用约 30K token 的长 prompt（每个请求输入 30,732 token），输出固定为 256 token。这种负载对应把长文档、代码库片段或长对话一次性交给模型的场景，用户等待的主要是模型读完长输入的时间。本页结论只适用于这种负载。参与本次单请求性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

30K 长 prompt B1 单请求性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen36-moe-b1-30k -->

- **完成时间最长。** 一个请求从发出到完成的时间中位数为 14.20 s，四轮都是四个应用中最长的；oMLX 最短（8.41 s），IronMLX 比它长 68.9%。Splash 为 8.90 s，TensorFold 0.6.6 为 10.97 s。
- **首字时间最长。** 首字时间中位数为 11.98 s，四轮都最长，比最快的 oMLX（6.76 s）长 77.3%。Splash 为 7.28 s，TensorFold 0.6.6 为 8.60 s。在 30K 输入下，首字时间的大部分是读入长输入的 prefill：IronMLX 自身日志记录的 prefill 时间为 11.0–12.2 s。完成时间的差距也主要来自这里。
- **解码速度第三。** 解码速度中位数为 116.3 tok/s，比 Splash（158.2）低 26.5%，也低于 oMLX（146.2）；四轮都快于 TensorFold 0.6.6（110.8）。
- **内存第三。** 服务时内存峰值为 25.3 GiB，比 oMLX（23.4 GiB）多 8.1%，略高于 Splash（25.1 GiB），四轮都是如此；TensorFold 0.6.6 为 30.8 GiB。

### 解码速度与首字时间

解码速度是一个请求开始输出后每秒生成的 token 数，反映生成长回复时的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，在长 prompt 下主要反映读入长输入的时间。图中越靠右下表现越好。

各应用处理单个请求时都使用外部 DFlash2 草稿模型做推测解码，每个计分请求都有草稿被接受，没有应用对整个请求退回普通解码。从各服务自己的日志和状态接口看：

- **IronMLX 0.2.0-rc.2：** 线性草稿验证（这个模型不使用草稿树），每个窗口的草稿数量由默认的窗口成本策略自动调整。在同一会话的后几个请求中，部分请求有较多不带草稿的窗口：策略会根据此前的接受情况调整预算，每个请求仍有 DFlash2 草稿被接受。各请求的输出四轮完全相同。
- **oMLX 0.7.0：** 每个请求的日志都记录了推测解码的接受情况；没有触发其长上下文回退（未设置 `dflash_max_ctx`）。
- **Splash 1.3.0：** 状态接口中的草稿与接受计数随每个请求增加。
- **TensorFold 0.6.6：** Python 引擎；在这个模型上还同时使用其内置的 copy proposer，个别请求中有少量草稿（最多 15 个 token）来自它，其余来自 DFlash2 草稿模型。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 电源 | 每个会话都接交流电 |
| 测试时间 | 2026 年 10 月 14 日（UTC 06:52–08:01） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，然后等到 macOS 热压力连续 60 秒处于正常水平才开始。会话期间每秒采样一次热压力：oMLX、Splash 和 TensorFold 0.6.6 的会话全程正常；IronMLX 的四个会话在最后一个任务（知识 3）期间升至较高水平，其余任务期间正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX 0.2.0-rc.2 | 官方发布包 `IronMLX.dmg`（sha256 `55a37763…`），tag `v0.2.0-rc.2` → `0ef3c55` | 使用包内服务程序和 Metal 运行时，按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 32768 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置，不加任何调优开关 |
| oMLX 0.7.0 | 官方 App | `--no-cache --max-concurrent-requests 4`；设置中上下文 32,768（`max_context_window` 与 `max_context_window_policy`），DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.3.0 | 官方 bottle | `--kv-format bf16 --max-context 32768`，SSD 缓存关闭；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 0.6.6 | 源码 tag（`cb2ebf05`） | `--drafter-bits 4 --lane-kernels on --parallel 4 --context 32768`，prompt 缓存与快照关闭 |

所有应用的共同设置：草稿模型 4-bit、BF16 KV 缓存、上下文 32,768 token、可配置容量的设为 4（测试客户端每次只发一个请求）；其余保持各应用自己的默认策略。每个服务实际生效的上下文都在启动后从其接口核对为 32,768。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。每个计分请求都因长度结束，服务端计数恰为 256。
- **Prompt：** 六个 30K prompt（三个编程、三个知识问答）。每个 prompt 由一段与问题相关的合成项目资料加末尾的问题组成，user 文本按 target tokenizer 计恰为 30,720 token，加上聊天模板后为 30,732 token。六个 prompt 互不相同，任意两个请求最多只共享开头 8 个 token（模板与标题）。
- **完整输入：** 每个请求的服务端 prompt token 数都是 30,732，与客户端按 target tokenizer 计算的值一致；没有截断、压缩或丢弃输入。所有应用使用完全相同的文本。
- **会话：** 每个会话启动全新服务，先发两个短 prompt 预热请求，再逐个发出六个 30K 计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。4 轮 × 4 个应用 = 16 个会话，四轮顺序为 ABCD、BCDA、CDAB、DABC，每个应用的平均位置相同。
- **缓存：** 每个请求都确认前缀缓存与磁盘缓存关闭或未被使用（服务端缓存命中 token 数为 0，命中计数不变）；每个请求都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容，包含传输、排队和读入完整长输入等时间，不等于单纯的 GPU prefill 时间；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取四轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。
- **有效性：** 16 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。每个应用的每个任务四轮输出逐字节相同。
- **输出计数：** 用 target tokenizer 对完整输出重新计数时，95 个请求恰为 256。Splash 的编程 3 四轮都是 255：它生成了 256 个 token，其中两个相邻 token 在重新编码时会合并为一个，输出本身完整。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。例如 TensorFold 1.0.5 没有参测，是因为其原生引擎尚未认证 Qwen3.6，这不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- 其他输入长度、其他模型、并发请求或真实多用户负载下的表现。本页只测了约 30K token 一种长输入；短 prompt 的单请求与并发结果见本页开头的系列链接。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同，每个计分请求都生成 256 个 token。
- 机器发热时的表现。每个会话都从正常热压力开始；会话期间 IronMLX 在最后一个任务时热压力升高，其他应用全程正常。本页没有覆盖机器持续发热时的情况。
- 多轮对话中的长上下文复用。每个计分请求都是全新的长输入且不使用前缀缓存；在多轮对话中复用已有上下文时，首字时间可能大不相同。
- 轮间波动。同一任务四轮之间，首字时间 IronMLX 最多相差 241 ms，TensorFold 0.6.6 188 ms，oMLX 144 ms，Splash 59 ms；解码速度 IronMLX 最多相差 11.1%（知识 3：95.9 到 106.6 tok/s），Splash 5.1%，TensorFold 0.6.6 4.2%，oMLX 1.3%。

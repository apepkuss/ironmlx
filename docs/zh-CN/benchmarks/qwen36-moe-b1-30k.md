# Qwen3.6 35B A3B B1 30K prompt 性能对比

[English](../../benchmarks/qwen36-moe-b1-30k.md)

> [!NOTE]
> 本页是 30K 长 prompt 的单请求性能对比；短 prompt 的对比见 [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)和 [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-short.md)。30K 长 prompt 性能对比测试系列：
>
> - Qwen3.6 35B A3B B1 单请求
> - [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-30k.md)
> - [Qwen3.8 27B B1 单请求](qwen38-dense-b1-30k.md)
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-30k.md)

B1 单请求性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.6-35B-A3B 混合专家（MoE）模型，服务每次只处理一个请求。所有计分请求都使用约 30K token 的长 prompt（每个请求输入 30,732 token），输出上限为 256 token。这种负载对应把长文档、代码库片段或长对话一次性交给模型的场景，用户等待的主要是模型读完长输入的时间。本页结论只适用于这种负载。参与本次单请求性能对比的本地推理应用有 oMLX、Splash 和 IronMLX，其中 Splash 与短 prompt 页一样测了两种设置（见下方说明）。TensorFold 1.1.6 不支持这个模型，没有参测。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

> [!NOTE]
> 本页 Splash 测了两种设置，以 `--verify-rows` 的取值区分（含义见[短 prompt B1 页](qwen36-moe-b1-short.md#splash-的两种设置)）：
>
> - **Splash auto**：默认设置（`--verify-rows auto`）。速度更快，但在这个模型上，贪心输出每次运行可能不同。
> - **Splash all**：`--verify-rows all`，每个周期验证整个草稿块，输出可复现。

## 结论

30K 长 prompt B1 单请求性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下（名次在 4 个配置之间排列）：

<!-- benchmark:kpis qwen36-moe-b1-30k -->

- **内存最低。** 服务时内存峰值为 22.1 GiB，四轮都最低；Splash 两种设置都是 23.1 GiB，oMLX 为 23.4 GiB。
- **解码速度第二。** 解码速度中位数为 184.3 tok/s，四轮都是第二：比 Splash auto（194.0）低 5.0%，比 Splash all（176.8）高 4.3%，比 oMLX（152.4）高 21.0%。
- **首字时间最长。** 首字时间中位数为 7.13 s，四轮都最长；Splash all（6.32 s）和 Splash auto（6.34 s）并列最短，IronMLX 比它们长 12.5–12.8%，oMLX 为 6.70 s。在 30K 输入下，首字时间的大部分是读入长输入的 prefill。
- **完成时间最长。** 一个请求从发出到完成的时间中位数为 8.57 s，四轮都最长；Splash auto 最短（7.71 s），IronMLX 比它长 11.1%。Splash all 为 7.85 s，oMLX 为 8.35 s。解码速度的领先不足以抵消 prefill 的差距。
- **输出可复现。** IronMLX 和 Splash all 的每个任务四轮输出都逐字节相同；oMLX 有 4 个任务、Splash auto 有 6 个任务的四轮输出不完全相同。

### 解码速度与首字时间

解码速度是一个请求开始输出后每秒生成的 token 数，反映生成长回复时的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，在长 prompt 下主要反映读入长输入的时间。图中越靠右下表现越好。

> 服务时内存峰值在六个计分请求期间测量，包含 30K 输入的 KV 缓存。加载模型和预热阶段的峰值：IronMLX 约 22.1 GiB，与服务时相当；oMLX 约 21.5 GiB，Splash 两种设置约 21.0 GiB。本页不比较加载阶段的内存。

### Splash 的两种设置

在 30K 输入下，Splash 两种设置的首字时间几乎相同（6.34 对 6.32 s）；Splash auto 的解码速度比 Splash all 高 9.7%（194.0 对 176.8 tok/s），完成时间短 1.7%（7.71 对 7.85 s）。30K 下完成时间的大部分是 prefill，所以解码速度的差别对完成时间影响较小。

- **oMLX 0.7.2：** 每个请求的日志都记录了推测解码的接受情况。
- **Splash 1.4.1 auto：** 状态接口中的草稿与接受计数随每个请求增加；启动日志写明按验证预算选择验证的行（`--verify-rows auto`）。
- **Splash 1.4.1 all：** 同上；启动日志写明每个周期验证草稿块的全部行（`--verify-rows all`）。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 28 日（UTC 10:25–11:15） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始。会话期间每秒采样一次热压力，所有计分请求期间都保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX dev (c6ef14ec2) | `dev` 分支提交 `c6ef14ec2` 的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结 | 按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 32768 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置（ANE 对这个模型不适用），不加任何调优开关 |
| oMLX 0.7.2 | 官方 App（`oMLX-0.7.2-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 32,768，DFlash2 草稿按 4-bit（group 64）量化，DFlash 验证模式保持默认的 `adaptive` |
| Splash 1.4.1 auto | 官方 bottle | `--max-context 32768`；KV 缓存保持默认的 int8；`--verify-rows` 保持默认的 `auto`；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每个请求都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| Splash 1.4.1 all | 同上 | 与 Splash 1.4.1 auto 相同，另加 `--verify-rows all`；启动后核对 Splash 引擎进程确实带有该参数（Splash 1.4.1 auto 的引擎进程不带） |
| TensorFold 1.1.6 | — | 未参测：按其 [1.1.6 文档](https://github.com/ashhart/TensorFold/blob/v1.1.6/docs/recipes/qwen3.6-moe.md)，Metal 原生引擎没有这个模型的家族（`qwen3_5_moe`），只能使用旧版 Python 引擎 |

所有应用的共同设置：草稿模型 4-bit、上下文 32,768 token、可配置容量的设为 4（测试客户端每次只发一个请求）、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。每个服务实际生效的上下文都在启动后从其接口或设置核对为 32,768。

### 模型

| 角色 | 模型 | 来源 | 版本 | 格式 |
|---|---|---|---|---|
| 目标模型 | `mlx-community/Qwen3.6-35B-A3B-4bit` | [Hugging Face](https://huggingface.co/mlx-community/Qwen3.6-35B-A3B-4bit/tree/38740b847e4cb78f352aba30aa41c76e08e6eb46) | `38740b847e4cb78f352aba30aa41c76e08e6eb46`（2026-04-16） | MLX safetensors，混合专家，4-bit affine 量化，group size 64（专家路由门控为 8-bit）；Apache-2.0 |
| 草稿模型 | `incoai/Qwen3.6-35B-A3B-DFlash2` | [Hugging Face](https://huggingface.co/incoai/Qwen3.6-35B-A3B-DFlash2/tree/51ef7b6923ad6c14cb1bb41c37a9041446496ab6) | `51ef7b6923ad6c14cb1bb41c37a9041446496ab6`（2026-09-25） | BF16 safetensors，6 层，block size 8；按 4-bit 草稿量化加载；Apache-2.0 |

> [!NOTE]
> 三个应用加载的是同一份模型文件，所有权重、配置和 tokenizer 文件都与上表的 Hugging Face 版本按 SHA-256 逐一核对一致。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次每个计分请求都因长度结束，服务端计数恰为 256。
- **Prompt：** 六个 30K prompt（三个编程、三个知识问答）。每个 prompt 由一段与问题相关的合成项目资料加末尾的问题组成，user 文本按 target tokenizer 计恰为 30,720 token，加上聊天模板后为 30,732 token。六个 prompt 互不相同，任意两个请求最多只共享开头 8 个 token（模板与标题）。
- **完整输入：** 每个请求的服务端 prompt token 数都是 30,732，与客户端按 target tokenizer 计算的值一致；没有截断、压缩或丢弃输入。所有应用使用完全相同的文本。
- **会话：** 每个会话启动全新服务，先发两个短 prompt 预热请求，再逐个发出六个 30K 计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。测试前事先规定先跑两轮（顺序 ABCS、SCBA，A 为 IronMLX，B 为 oMLX，C 为 Splash auto，S 为 Splash all），如果任一指标中相邻两名的先后在两轮中不一致、或两轮范围重叠，就紧接着按 BASC、CSAB 补跑两轮。本次首字时间中 Splash 两种设置的两轮范围重叠，因此补跑，共 4 轮 × 4 个配置 = 16 个会话，每个配置的平均位置相同。
- **缓存：** 每个请求都确认前缀缓存与磁盘缓存关闭或未被使用（服务端缓存命中 token 数为 0，命中计数不变）；每个请求都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容，包含传输、排队和读入完整长输入等时间，不等于单纯的 GPU prefill 时间；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取四轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。
- **有效性：** 16 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。
- **输出计数：** 服务端计数为准；客户端用 target tokenizer 对完整输出重新计数作核对，允许相差不超过 3 个 token。本次 96 个请求重新计数都恰为 256。
- **输出可复现性：** IronMLX 和 Splash all 的每个任务四轮输出逐字节相同。oMLX 在编程 3 和三个知识任务上、Splash auto 在全部六个任务上，四轮输出不完全相同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优（Splash all 是为输出可复现而另加的对照配置）；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。TensorFold 没有参测，是因为其当前版本不支持这个模型，这不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为开发版本。** 本页的 IronMLX 是 `dev` 分支的构建，不是正式发布版本；正式发布版本的表现可能不同。
- **Splash 两种设置的首字时间没有分出先后。** 两者相差 0.3%，四轮中各领先两轮。
- 其他输入长度、其他模型、并发请求或真实多用户负载下的表现。本页只测了约 30K token 一种长输入；四个 30K 请求同时到达的结果见[Qwen3.6 35B A3B B4 30K prompt 并发性能对比](qwen36-moe-b4-30k.md)，短 prompt 的结果见本页开头的链接。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量；也没有评估 Splash auto 和 oMLX 默认设置下输出的变化对回答质量有没有影响。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 多轮对话中的长上下文复用。每个计分请求都是全新的长输入且不使用前缀缓存；在多轮对话中复用已有上下文时，首字时间可能大不相同。
- 轮间波动。同一任务四轮之间，首字时间 oMLX 最多相差 783 ms（编程 1），IronMLX 386 ms，Splash all 294 ms，Splash auto 186 ms；解码速度 oMLX 最多相差 22.6%（知识 1：111.0 到 136.1 tok/s），Splash auto 15.6%，Splash all 7.8%，IronMLX 3.7%。

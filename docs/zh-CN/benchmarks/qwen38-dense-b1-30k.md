# Qwen3.8 27B B1 30K prompt 性能对比

[English](../../benchmarks/qwen38-dense-b1-30k.md)

> [!NOTE]
> 本页是 30K 长 prompt 的单请求性能对比；短 prompt 的对比见 [Qwen3.8 27B B1 单请求](qwen38-dense-b1-short.md)和 [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)。30K 长 prompt 性能对比测试系列：
>
> - Qwen3.8 27B B1 单请求
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-30k.md)

B1 单请求性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.8-27B 稠密模型，服务每次只处理一个请求。所有计分请求都使用约 30K token 的长 prompt（每个请求输入 30,732 token），输出上限为 256 token。这种负载对应把长文档、代码库片段或长对话一次性交给模型的场景，用户等待的主要是模型读完长输入的时间。本页结论只适用于这种负载。参与本次单请求性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

30K 长 prompt B1 单请求性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b1-30k -->

- **首字时间第二，略慢于 Splash。** 首字时间中位数为 35.84 s，第 1 轮第一，第 2–4 轮第二；Splash 为 35.41 s，比 IronMLX 短 1.2%，两者的四轮范围有重叠。oMLX 为 41.28 s，TensorFold 为 52.00 s。在 30K 输入下，首字时间的大部分是读入长输入的 prefill。
- **解码速度第二，与 Splash 几乎持平。** 解码速度中位数为 66.5 tok/s，第 1 轮第一，第 2–4 轮第二，只比 Splash（66.6）低 0.1%；两者的四轮范围有重叠。oMLX 为 60.1，TensorFold 为 57.8。
- **完成时间第二，略慢于 Splash。** 一个请求从发出到完成的时间中位数为 41.05 s，Splash 为 40.59 s，IronMLX 长 1.1%；IronMLX 在第 1 轮领先，Splash 在第 2–4 轮领先，范围重叠。oMLX 为 46.13 s，TensorFold 为 56.57 s。
- **内存最低。** 服务时内存峰值为 20.6 GiB，四轮都最低；oMLX 为 25.1 GiB，Splash 为 25.9 GiB，TensorFold 为 27.9 GiB。

### 解码速度与首字时间

解码速度是一个请求开始输出后每秒生成的 token 数，反映生成长回复时的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，在长 prompt 下主要反映读入长输入的时间。图中越靠右下表现越好。

### 各项指标对比

下表列出各参测应用在各项指标上的结果。表中数值为四轮测试的中位数，括号内为四轮中的最小值和最大值；每轮的数值取该轮六个任务的中位数。解码速度越高越好，其余时间和内存指标越低越好；每行最优的数值加粗显示。

| 指标 | IronMLX 0.2.0 | oMLX 0.7.3rc1 | Splash 1.5.0 | TensorFold 1.2.0 |
|---|---|---|---|---|
| 首字时间（s） | 35.84 (35.82–⁠36.39) | 41.28 (41.08–⁠41.32) | **35.41** (35.27–⁠36.20) | 52.00 (51.93–⁠52.36) |
| 解码速度（tok/s，越高越好） | 66.5 (66.1–⁠66.7) | 60.1 (58.9–⁠60.7) | **66.6** (66.4–⁠67.1) | 57.8 (57.4–⁠58.1) |
| 完成时间（s） | 41.05 (41.00–⁠41.38) | 46.13 (46.01–⁠46.33) | **40.59** (40.41–⁠41.29) | 56.57 (56.54–⁠57.13) |

内存的先后四轮完全一致：IronMLX、oMLX、Splash、TensorFold。首字时间、解码速度和完成时间三项都是 IronMLX 在第 1 轮领先，Splash 在第 2–4 轮领先，之后每轮都是 oMLX、TensorFold。

> [!NOTE]
> 服务时内存峰值在六个计分请求期间测量，包含 30K 输入的 KV 缓存。加载模型和预热阶段的峰值另有不同：IronMLX 约 28.2 GiB，高于其服务时峰值；oMLX 约 21.9 GiB，Splash 约 19.3 GiB，TensorFold 约 27.8 GiB。本页不比较加载阶段的内存。

> [!NOTE]
> ¹ IronMLX 在知识 3 上四轮都在第 235 个 token 处自然结束（模型输出结束符），其他应用都生成满 256 个 token，因此这一项的完成时间对 IronMLX 有利。知识 3 本来就是 IronMLX 六个任务中用时最长的（第 4 轮为第二长），所以它不影响六个任务的中位数，上表中的总体完成时间不受影响。

首字时间 IronMLX 在三个编程任务上最短，Splash 在三个知识任务上最短，两者每个任务相差 0.1–0.9 s。解码速度 IronMLX 在五个任务上最快，Splash 在知识 2 上最快。IronMLX 的总体解码速度仍排第二：每轮的数值取六个任务的中位数，两个应用的中位数都是编程 3 与知识 2 的平均值，而 IronMLX 在编程 3 上快 0.5 tok/s，在知识 2 上慢 0.8 tok/s。各应用的首字时间大体上从编程 1 到知识 3 变长（IronMLX 从编程 1 的 30.6 s 到知识 2 的 40.6 s；IronMLX 和 Splash 的知识 3 都略短于各自的知识 2，TensorFold 的三个知识任务都在 53.6–53.7 s）；六个输入一样长，这段时间里会话中的热压力也在升高，见[软硬件配置](#软硬件配置)中的温控说明。

各应用处理单个请求时都使用外部 DFlash2 草稿模型做推测解码，每个计分请求都有草稿被接受。从各服务自己的日志和状态接口看：

- **IronMLX 0.2.0：** 每个验证窗口用 15 节点的草稿树，一次验证 16 行，草稿预算固定为 7；全部窗口都是树验证。30K 输入的 prefill 按默认的 ANE `auto` 把部分 MLP 计算交给 ANE（状态接口显示 ANE 处于启用状态）。
- **oMLX 0.7.3rc1：** 每个请求的日志都记录了推测解码的接受情况。
- **Splash 1.5.0：** 状态接口中的草稿与接受计数随每个请求增加；长输入的 prefill 按其默认设置把部分 FFN 计算交给 Neural Engine（日志记录）。
- **TensorFold 1.2.0：** 原生引擎（`qwen27`）；服务端对每个请求报告的每轮最少行数随任务不同，在 6–12 之间，同一任务四轮都相同。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 31 日（UTC 15:29–17:22） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始。会话期间每秒采样一次热压力：30K 输入的 prefill 让机器明显发热：计分请求按编程 1 到知识 3 的固定顺序发出，各应用在前一两个请求期间正常，IronMLX 和 Splash 从编程 3 起、TensorFold 从编程 2 起升至较高水平，oMLX 在编程 2 时为中等、从编程 3 起升至较高水平 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX 0.2.0 | 标签 `v0.2.0-rc.4`（提交 `a0afebe55`）的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结。0.2.0 正式版本原样发布这份代码 | 按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 32768 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置（含 ANE `auto`，30K 输入会启用），不加任何调优开关 |
| oMLX 0.7.3rc1 | 官方 App（`oMLX-0.7.3rc1-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 32,768，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.5.0 | 官方 bottle | `--max-context 32768`；KV 缓存保持默认的 int8；Neural Engine 保持默认开启；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每个请求都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 1.2.0 | 官方原生发布包（sha256 `81fffaab…`），tag `v1.2.0` → `a388876` | `--drafter-bits 4 --parallel 4 --context 32768`，prompt 缓存与快照关闭，keep-warm 保持默认 |

所有应用的共同设置：草稿模型 4-bit、上下文 32,768 token、可配置容量的设为 4（测试客户端每次只发一个请求）、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。每个服务实际生效的上下文都在启动后从其接口或设置核对为 32,768。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次只有 IronMLX 的知识 3 自然结束（235 token），其余都因长度结束于 256。
- **Prompt：** 六个 30K prompt（三个编程、三个知识问答）。每个 prompt 由一段与问题相关的合成项目资料加末尾的问题组成，加上聊天模板后为 30,732 token。六个 prompt 互不相同，任意两个请求最多只共享开头 8 个 token（模板与标题）。
- **完整输入：** 每个请求的服务端 prompt token 数都是 30,732，与客户端按 target tokenizer 计算的值一致；没有截断、压缩或丢弃输入。所有应用使用完全相同的文本。
- **会话：** 每个会话启动全新服务，先发两个短 prompt 预热请求，再逐个发出六个 30K 计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。测试前事先规定先跑两轮（顺序 ABCE、ECBA），如果任一指标中相邻两名的先后在两轮中不一致、或两轮范围重叠，就紧接着按 BAEC、CEAB 补跑两轮。本次首字时间、解码速度和完成时间三项的 IronMLX 与 Splash 都在前两轮先后互换，因此补跑，共 4 轮 × 4 个应用 = 16 个会话，每个应用的平均位置相同。
- **缓存：** 每个请求都确认前缀缓存与磁盘缓存关闭或未被使用（服务端缓存命中 token 数为 0，命中计数不变）；每个请求都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容，包含传输、排队和读入完整长输入等时间，不等于单纯的 GPU prefill 时间；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取四轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。
- **有效性：** 16 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。IronMLX、Splash 和 TensorFold 的每个任务四轮输出逐字节相同；oMLX 在知识 1、知识 3 两个任务上四轮输出不完全相同。
- **输出计数：** 服务端计数为准；客户端用 target tokenizer 对完整输出重新计数作核对，允许相差不超过 3 个 token（重新编码时相邻 token 的切分可能与生成时不同）。本次 TensorFold 的知识 3 四轮重新计数都为 257、Splash 的知识 1 四轮都为 255，oMLX 的四次知识 1 中有两次为 255，服务端计数都是 256；IronMLX 知识 3 服务端计数 235，含结束符，输出文本为 234 个 token。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **首字时间、解码速度与完成时间和 Splash 的差距很小。** IronMLX 的首字时间比 Splash 长 1.2%，解码速度低 0.1%，完成时间长 1.1%；这三项 Splash 都在四轮中领先三轮，但四轮范围有重叠，这些差距都不应视为明确的优势或劣势。
- **ANE 会改变输出。** IronMLX 默认在 30K 输入的 prefill 中启用 ANE，数值与只用 GPU 时略有不同，贪心解码的输出也随之不同。
- 其他输入长度、其他模型、并发请求或真实多用户负载下的表现。本页只测了约 30K token 一种长输入；并发结果见[Qwen3.8 27B B4 30K prompt 并发性能对比](qwen38-dense-b4-30k.md)。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同。
- 机器发热时的表现。每个会话都从正常热压力开始，但 30K 输入让各应用的多数计分请求在较高热压力下完成；本页没有覆盖机器长时间持续高负载的情况。
- 多轮对话中的长上下文复用。每个计分请求都是全新的长输入且不使用前缀缓存；在多轮对话中复用已有上下文时，首字时间可能大不相同。
- 轮间波动。同一任务四轮之间，首字时间 TensorFold 最多相差 1,345 ms，Splash 1,277 ms，IronMLX 901 ms，oMLX 312 ms；解码速度 oMLX 最多相差 12.8%，Splash 4.7%，TensorFold 4.0%，IronMLX 2.5%。

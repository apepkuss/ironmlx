# IronMLX 长上下文性能（128K 与 256K prompt）

[English](../../benchmarks/ironmlx-long-context.md)

> [!NOTE]
> 本页只测量 IronMLX，不与其他应用对比。30K token prompt 的对比见 [Qwen3.8 27B B1 30K prompt 性能对比](qwen38-dense-b1-30k.md)和 [Qwen3.6 35B A3B B1 30K prompt 性能对比](qwen36-moe-b1-30k.md)。

本页展示单个请求带约 128K 或 256K token prompt 时 IronMLX 0.2.0 的表现，以及 prompt 变长时首字时间、解码速度和内存如何变化。测试覆盖 Qwen3.8-27B Dense 模型和 Qwen3.6-35B-A3B 混合专家（MoE）模型，服务每次只处理一个请求，输出上限为 256 token。128K 请求输入 131,084 token；256K 请求输入 261,132 token，加上 256 个输出 token，接近两个模型 262,144 token 的最大上下文。这种负载对应把很长的文档、代码库的大部分或很长的对话一次性交给模型的场景。关于测试环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

<!-- benchmark:scaling ironmlx-long-context -->

- **两个模型在两种长度下都能完整跑完。** 128K 与 256K 的 48 个计分请求全部读入完整输入并输出 256 个 token；在 128 GB 的 Mac 上，服务时内存峰值不超过 35.3 GiB。
- **首字时间比输入增长得更快。** 128K 时 Dense 模型首字时间为 272.15 s，MoE 模型为 68.93 s；256K 时为 802.34 s（约 13.4 分钟）和 243.94 s。输入从 128K 翻倍到 256K，Dense 模型的等待时间变为 2.95 倍，MoE 模型变为 3.54 倍。
- **上下文越长，解码越慢。** Dense 模型 128K 时解码 42.0 tok/s，256K 时 28.9 tok/s，30K 时为 66.5 tok/s；MoE 模型为 143.2 和 100.4 tok/s，30K 时为 189.3 tok/s。各任务差别很大：Dense 模型的编程任务保持在 35–65 tok/s，知识问答任务只有 15–30 tok/s。
- **内存增长温和。** 从 30K 到 256K，Dense 模型内存峰值从 20.6 GiB 增至 35.3 GiB，MoE 模型从 22.0 GiB 增至 26.5 GiB。
- **稳定且可复现。** 每个任务两轮输出逐字节相同；任一指标的两轮中位数最多相差 1.8%。

### 首字时间如何增长

下表把各长度与 30K 比较。

| 模型 | 输入 | 输入相对 30K | 首字时间相对 30K |
|---|---|---|---|
| Qwen3.8 27B | 30K | 1× | 1× |
| Qwen3.8 27B | 128K | 4.3× | 7.6× |
| Qwen3.8 27B | 256K | 8.5× | 22.4× |
| Qwen3.6 35B A3B | 30K | 1× | 1× |
| Qwen3.6 35B A3B | 128K | 4.3× | 10.7× |
| Qwen3.6 35B A3B | 256K | 8.5× | 37.7× |

从[各项指标](#各项指标)中的 prefill 速度可以看到，输入越长，每个 token 的 prefill 越慢。两个模型都混合了线性注意力层和完整注意力层（Dense 模型 64 层中有 16 层，MoE 模型 40 层中有 10 层）；完整注意力层中每个新 token 都要关注它之前的全部 token，计算量比输入增长得更快，输入越长，这部分占比越大。MoE 模型的其他层计算量小（每个 token 约 3B 激活参数），这很可能是它的这部分更早占主导、首字时间相对 30K 增长得比 Dense 模型更快的原因。另外有两项条件与 30K 测试不同：本页几乎所有请求都在较高热压力下完成（见[软硬件配置](#软硬件配置)）；Dense 模型的 ANE 只参与输入前 65,536 个位置的 prefill（见[应用与配置](#应用与配置)），而 30K 时覆盖整个输入。

- **解码速度取决于草稿接受程度。** 每个验证窗口都要让目标模型在整个上下文上运行一次，成本随上下文增长。草稿接受多的任务每个窗口产出的 token 多，解码就快。Dense 模型的编程任务每个窗口产出 5.4–8.0 个 token，知识问答任务只有 2.4–3.5 个，解码速度不到前者的一半。
- **编程 1 的首字时间较短。** 同一长度的六个 prompt token 数相同，但每个会话的第一个计分请求编程 1，在 Dense 模型 128K 和 MoE 模型两种长度下，首字时间比编程 3 到知识 3 短 12–20%。MoE 模型 128K 的编程 1 也是唯一热压力一直保持正常的请求；Dense 模型 256K 没有这个规律（编程 1 第一轮 818.7 s、第二轮 769.8 s）。一个可能的原因是第一个请求在热降频完全生效之前运行，但任务顺序固定，无法与任务内容本身完全区分。
- **推测解码。** 每个计分请求都有草稿被接受。Dense 模型的每个验证窗口都是树验证，草稿预算为 7，与 30K 页相同；MoE 模型的每个窗口都是线性草稿验证，每个窗口的草稿数由默认的窗口成本策略自动决定。

### 内存

内存峰值随上下文增长，主要来自完整注意力层的 KV 缓存：Dense 模型每个上下文 token 约 64 KiB（16 层、4 个 256 维 KV 头、BF16），MoE 模型约 20 KiB（10 层、2 个 KV 头）。按 30K 到 128K、128K 到 256K 增加的输入 token 计算，Dense 模型约增加 6.1 GiB 和 7.9 GiB，MoE 模型约增加 1.9 GiB 和 2.5 GiB。实测增量为 Dense 模型 6.2 GiB 和 8.5 GiB、MoE 模型 1.9 GiB 和 2.6 GiB，量级一致。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次所有计分请求都因长度结束，服务端计数恰为 256。
- **Prompt：** 每个长度六个 prompt（三个编程、三个知识问答），构造方法与 30K prompt 相同：一段与问题相关的合成项目资料加末尾的问题。更长的 prompt 用更多记录扩展资料，问题不变。按 target tokenizer 计，user 文本在 128K 时恰为 131,072 token、256K 时为 261,120 token，加上聊天模板后为 131,084 和 261,132 token。同一长度的六个 prompt 互不相同，任意两个只共享开头几个 token（模板与标题）。
- **完整输入：** 每个请求的服务端 prompt token 数都是 131,084 或 261,132，与客户端按 target tokenizer 计算的值一致；没有截断、压缩或丢弃输入。
- **会话：** 每个会话启动全新服务，先发两个短 prompt 预热请求，再逐个发出六个计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。每个模型、每种长度跑两轮，每轮一个会话，顺序为 MoE 128K、MoE 256K、Dense 128K、Dense 256K。测试前事先规定：如果首字时间、解码速度或完成时间的两轮中位数相差超过 5%，就补跑两轮；本次最大差异为 1.8%（Dense 模型 128K 的解码速度），没有补跑，共 8 个会话。
- **缓存：** 每个请求都确认前缀缓存关闭（服务端缓存命中 token 数为 0）；从服务日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容，包含传输、排队和读入完整长输入等时间，不等于单纯的 GPU prefill 时间；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取各轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。prefill 速度（服务端每秒处理的 prompt token 数）和每个验证窗口的 token 数来自服务日志，prefill 速度与其他指标取同样的中位数。
- **有效性：** 8 个会话、48 个计分请求全部通过所有检查；没有任何会话重试或剔除。
- **输出计数：** 服务端计数为准；客户端用 target tokenizer 对完整输出重新计数作核对，允许相差不超过 3 个 token。本次 48 次重新计数中 46 次恰为 256，另外两次（MoE 模型 256K 的知识 2，两轮）为 257，在允许范围内。
- **输出可复现：** 每个长度下，每个任务两轮输出逐字节相同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次测试没有覆盖或需要注意的地方：

- **不是对比。** 本页只测量 IronMLX，不说明其他应用在这些长度下的表现。
- **30K 行来自其他测试。** 它们是 30K 对比页中 IronMLX 的结果，使用同一构建，但在不同的会话中测得：四轮、上下文 32,768 token、热压力更低，Dense 模型的 ANE 覆盖整个 prefill。与 30K 的倍数描述的是整体变化，不能单独归因于输入长度。
- **机器发热时的表现。** 每个会话都从正常热压力开始，但几乎所有计分请求都在较高热压力下完成，结果包含了这部分降速。散热条件不同的 Mac，或已经持续高负载更久的机器，表现可能不同。
- 其他 Mac 与内存容量。Dense 模型 256K 的内存峰值达到 35.3 GiB；本页不说明内存更小的 Mac 能否服务这些长度。
- 其他输入长度、其他模型、并发请求或真实多用户负载下的表现。本页只测了约 128K 和 256K token 的单请求。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只测速度和内存，没有评估这些长度下的回答质量。
- 多轮对话中的长上下文复用。每个计分请求都是全新的长输入且不使用前缀缓存；在多轮对话中复用已有上下文时，首字时间可能大不相同。
- 轮间波动。同一任务两轮之间，首字时间在 Dense 模型 256K 最多相差 48.9 s（编程 1：769.8 至 818.7 s），Dense 模型 128K 为 7.9 s，MoE 模型 256K 为 2.9 s，MoE 模型 128K 为 0.3 s；解码速度在 Dense 模型 128K 最多相差 7.0%（知识 3），其余都不超过 2.4%。

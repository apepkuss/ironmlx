# Qwen3.8 27B B4 30K prompt 并发性能对比

[English](../../benchmarks/qwen38-dense-b4-30k.md)

> [!NOTE]
> 本页是 30K 长 prompt 的并发性能对比；短 prompt 的对比见 [Qwen3.8 27B B1 单请求](qwen38-dense-b1-short.md)和 [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)。30K 长 prompt 性能对比测试系列：
>
> - Qwen3.8 27B B4 并发
> - [Qwen3.8 27B B1 单请求](qwen38-dense-b1-30k.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.8-27B 稠密模型，四个请求同时到达服务。所有计分请求都使用约 30K token 的长 prompt（每个请求输入 30,732 token），输出上限为 256 token。这种负载对应几个用户或几个 Agent 同时把长文档、代码库片段交给同一个本地服务的场景；四个 30K 输入都要读完，等待时间以分钟计。本页结论只适用于这种负载。参与本次并发性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

30K 长 prompt B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b4-30k -->

- **首字时间中位数最短。** 四个请求首字时间的中位数为 83.7 s，两轮都第一；Splash 为 86.9 s，比 IronMLX 长 3.8%，两者的两轮范围没有重叠。TensorFold 为 136.2 s，oMLX 为 159.7 s。
- **完成时间中位数最短。** 四个请求完成时间的中位数为 87.2 s，两轮都第一，比 Splash（96.3 s）短 9.5%；oMLX 为 176.4 s，TensorFold 为 181.2 s。
- **prefill 速度最高。** 四个 30K 输入合计 122,928 个 token，IronMLX 的整批 prefill 速度为 858 tok/s，两轮都第一，比 Splash（826 tok/s）高 3.9%；oMLX 为 753，TensorFold 为 619。30K 下各应用约 90–97% 的整批时间花在读入四个输入上，所以 prefill 速度基本决定了等待时间。最慢请求的首字时间（143.3 s 对 Splash 的 148.9 s）和完成时间（148.9 s 对 153.9 s）也是 IronMLX 两轮都第一。
- **解码阶段输出速度最高。** 在有请求正在解码的时间里，IronMLX 每秒输出 67.6 个 token，两轮都第一，约为 Splash（32.3）的两倍；oMLX 为 23.5，TensorFold 为 7.2。IronMLX 的 24 个请求中有 22 个在出首字后 2–8 s 内完成；Splash 每个请求的解码要约 5–17 s。
- **30K 下基本没有合批。** IronMLX 和 Splash 的解码并发度都是 1.00（Splash 的 6 批都没有两个请求同时解码，IronMLX 只有第三组 prompt 的两批略有重叠，都是 1.02），TensorFold 为 1.05，只有 oMLX 为 1.63（后三个请求一起读入、一起解码）。四个输入是依次读入的，一个请求读完、解码完，下一个请求还在读入，请求之间基本碰不到一起解码。作为对照，短 prompt 下四个应用的解码并发度都在 2.7–3.5（见[短 prompt B4 页](qwen38-dense-b4-short.md)）。
- **内存最低。** 服务时内存峰值为 23.3 GiB，两轮都最低；Splash 为 23.7 GiB，TensorFold 为 34.8 GiB，oMLX 为 38.8 GiB。

### prefill 速度与首字时间

整批 prefill 速度是四个请求的输入 token 总数除以从最早发出请求到最后一个请求出首字的时间，反映服务读入长输入的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，在长 prompt 下主要反映读入长输入和排队等待的时间。图中越靠右下表现越好。

| 整批吞吐（输出 tok/s，辅助）² | 6.73 (6.70–⁠6.76) | 5.67 (5.63–⁠5.72) | 6.66 (6.65–⁠6.67) | 4.95 (4.95–⁠4.95) |
| 单请求解码速度（tok/s，辅助）³ | 82.0 (80.8–⁠83.3) | 15.1 (15.0–⁠15.2) | 35.3 (35.0–⁠35.6) | 5.7 (5.7–⁠5.7) |

表中每项指标，四个应用的先后两轮都一致。

> [!NOTE]
> ¹ 这三项是测试完成后，用每个计分批的客户端时间戳推导出的，不在事先写定的测试协议中，定义如下（都包含传输时间和第一个输出 token 的生成时间，不等于引擎内部的计时）：
>
> - 整批 prefill 速度：四个请求的输入 token 总数（服务端计数，共 122,928）÷ 从最早发出请求到最后一个请求收到第一个输出内容的时间。
> - 解码阶段输出速度：整批实际输出的 token 数 ÷ 至少有一个请求在解码的总时间（每个请求从收到第一个输出内容到 `[DONE]` 算作在解码，取四个区间的并集）。这段时间里可能同时在读入其他请求的输入，所以它是有负载时的有效解码速度。
> - 解码并发度：四个请求的解码时间之和 ÷ 上述并集。1 表示从没有两个请求同时解码，4 表示四个请求始终一起解码。

> [!NOTE]
> ² 整批吞吐为整批实际输出的 token 数 ÷ 整批完成时间（最早发出到最后一个 `[DONE]`）。30K 下整批时间主要花在读入输入上，这项基本只反映 prefill 速度，因此只作辅助参考。IronMLX 的知识 3 自然结束（服务端计数 235，含结束符；输出文本为 234 个 token），含知识 3 的批次实际输出 1,002 个 token；其余批次都是 1,024 个 token。整批完成时间与最慢请求的完成时间只差各请求发送时刻的差异（不超过 2.9 ms）。

> [!NOTE]
> ³ 单请求解码速度取决于各应用如何安排四个请求：先读完输入的请求如果在其他请求读入期间单独解码，速度接近单请求；如果和其他请求的 prefill 交替进行，速度会低很多。

> [!NOTE]
> 服务时内存峰值在计分批期间测量，包含四个 30K 输入的 KV 缓存。加载模型和预热阶段的峰值另有不同：IronMLX 约 27.9–28.2 GiB，高于其服务时峰值；Splash 约 19.5 GiB，oMLX 约 22.3–23.0 GiB，TensorFold 约 34.3–34.7 GiB。本页不比较加载阶段的内存。

### 请求响应时间线

下图展示四个请求同时发出后，每个请求的首字时间和完成时间，用于观察各应用在并发负载下如何安排四个请求的处理。横轴是从发出请求起经过的时间；竖线表示请求收到第一个输出内容的时间，圆点表示请求完成的时间。图中数值的取法是：在每个批次内，把四个请求的首字时间和完成时间分别按先后排序，再对 6 个批次同一位次的数值取中位数。因此竖线和圆点是分别排序的，同一位次的竖线和圆点不一定属于同一个请求。

<!-- benchmark:timeline qwen38-dense-b4-30k -->

客户端同时发出请求，不等于引擎内部会合批。从时间线和各服务自己的日志、状态接口看，四个请求的处理方式如下：

- **IronMLX 0.2.0：** 四个输入依次读入，首字约在 31、66、102、143 s 出现；多数请求出首字后 2–8 s 完成，但第三组 prompt 的两批中，第二个请求出首字后要约 38 s 才完成，期间下一个请求在读入。完成日志显示，这两批中第二、第三个请求有一段一起解码（批宽 2），一批为 19 个验证窗口，另一批为 21 个；其余时间每个请求都单独解码（批宽 1），每个验证窗口用 15 节点的草稿树。输出与 B1 页中逐个单独处理同样的 prompt 逐字节相同。
- **oMLX 0.7.3rc1：** 第一个请求单独读入，首字约在 36 s 出现；其余三个请求的输入一起读入，首字集中在 157–164 s。之后三个请求一起做批量推测解码（日志中这条批量路径名为 “Lightning MTP”）；每批都有请求改走一段标准解码，6 批中有 5 批的日志显示批量路径暂停（parked）了一段时间。
- **Splash 1.5.0：** 四个输入依次读入，首字约在 31、68、105、149 s 出现；解码批次的宽度统计全部为 1，即每次只解码一个请求。长输入的 prefill 按默认设置把部分 FFN 计算交给 Neural Engine。部分任务的输出与 B1 页中单独处理时不同。
- **TensorFold 1.2.0：** 原生引擎（`qwen27`），按 `--parallel 4` 建 4 个通道。四个输入依次读入，首字约在 57、113、160、199 s 出现；先读完的请求在后续请求读入期间继续解码，因此单请求解码速度只有约 5.7 tok/s，最后两个请求相隔不久完成（约 204 s 和 207 s）。输出与 B1 页中逐个单独处理同样的 prompt 逐字节相同。

### 参测应用与配置

| 应用 | 来源 | 配置 |

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次 IronMLX 的知识 3 每次都在 235 token 处自然结束，其余都因长度结束于 256。
- **Prompt：** 六个 30K prompt（三个编程、三个知识问答，与 B1 页相同），每个加上聊天模板后为 30,732 token；分成三组，每批四个 prompt 互不相同。每个请求的服务端 prompt token 数都核对为 30,732，没有截断或丢弃输入。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批（短 prompt），再同时发出一个四请求计分批（最大发送时间差 2.9 ms），然后关闭服务。2 轮 × 4 个应用 × 3 组 prompt = 24 个会话；两轮应用顺序为 ABCE、ECBA（互为倒序），每个应用的平均位置相同，三组 prompt 的先后按轮次轮换。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为实际输出 token 数（客户端按 target tokenizer 计数；因长度结束的请求计 256）除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。整批 prefill 速度、解码阶段输出速度和解码并发度是测试完成后用同一批时间戳推导的，定义见[各项指标对比](#各项指标对比)的注释。
- **有效性：** 24 个会话、96 个计分请求全部通过所有检查；没有任何会话剔除。oMLX 在批处理中可能把一个请求从推测解码切到标准解码完成，这一段不写推测解码的结束日志；正式运行前写定的检查把这样的请求视为以标准解码完成，其结束方式与计数仍按流式输出核对。本次 oMLX 的 6 批中有 5 批共 7 个请求以这种方式完成，客户端侧都正常完成。
- **输出计数：** 服务端计数为准；客户端用 target tokenizer 对完整输出重新计数作核对，允许相差不超过 3 个 token（重新编码时相邻 token 的切分可能与生成时不同）。本次 TensorFold 的知识 3 有 4 个请求重新计数为 257，服务端计数都是 256；Splash 的知识 1 有 1 个请求重新计数为 255，服务端计数为 256；IronMLX 的知识 3 服务端计数 235，含结束符，输出文本为 234 个 token。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **prefill 速度领先 Splash 的幅度很小。** IronMLX 的整批 prefill 速度比 Splash 高 3.9%，整批吞吐高 1.1%，两项都是 IronMLX 两轮领先，但幅度很小，且只基于单台机器上的两轮数据。
- **轮间波动。** 同一组 prompt 两轮之间，IronMLX 的整批吞吐第二轮比第一轮低 0.4–1.3%，oMLX 高 0.6–1.7%，Splash 变化不超过 0.9%，TensorFold 变化不超过 0.2%。
- **事后推导的指标。** 整批 prefill 速度、解码阶段输出速度和解码并发度是在测试完成后推导的，用的是测试中已记录的客户端时间戳，没有重跑；它们不在测试协议中，不是事先写定的比较项。
- **ANE 会改变输出。** IronMLX 默认在 30K 输入的 prefill 中启用 ANE，贪心解码的输出与只用 GPU 时不同；知识 3 的自然结束即出现在默认设置下（见 [B1 页](qwen38-dense-b1-30k.md)）。
- 其他输入长度、其他模型、其他并发度或真实多用户负载下的表现。本页只测了约 30K token 一种长输入，四个请求同时到达。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同。
- 机器发热时的表现。每个会话都从正常热压力开始，但所有计分批都在较高热压力下完成；本页没有覆盖机器长时间持续高负载的情况。
- 多轮对话中的长上下文复用。每个计分请求都是全新的长输入且不使用前缀缓存。

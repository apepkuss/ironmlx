# Qwen3.8 27B B4 30K prompt 并发性能对比

[English](../../benchmarks/qwen38-dense-b4-30k.md)

> [!NOTE]
> 本页是 30K 长 prompt 的并发性能对比；短 prompt 的对比见 [Qwen3.8 27B B1 单请求](qwen38-dense-b1-short.md)和 [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)。30K 长 prompt 性能对比测试系列：
>
> - Qwen3.8 27B B4 并发
> - [Qwen3.8 27B B1 单请求](qwen38-dense-b1-30k.md)
> - [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-30k.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.8-27B 稠密模型，四个请求同时到达服务。所有计分请求都使用约 30K token 的长 prompt（每个请求输入 30,732 token），输出上限为 256 token。这种负载对应几个用户或几个 Agent 同时把长文档、代码库片段交给同一个本地服务的场景；四个 30K 输入都要读完，等待时间以分钟计。本页结论只适用于这种负载。参与本次并发性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

30K 长 prompt B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b4-30k -->

- **首字时间中位数最短。** 四个请求首字时间的中位数为 84.7 s，两轮都第一；Splash 为 87.2 s，比 IronMLX 长 2.9%，两者的两轮范围略有重叠。TensorFold 为 131.1 s，oMLX 为 160.4 s。
- **完成时间中位数最短。** 四个请求完成时间的中位数为 88.4 s，两轮都第一，比 Splash（96.3 s）短 8.2%；oMLX 为 177.1 s，TensorFold 为 179.2 s。
- **整批吞吐与 Splash 持平。** 四个请求一起完成的吞吐为 6.63 tok/s，Splash 为 6.56 tok/s；两轮中两者各领先一轮，范围重叠。oMLX 为 5.63，TensorFold 为 4.84。30K 下整批吞吐只有个位数，因为整批时间主要花在读入四个 30K 输入上。最慢请求的首字时间（146.3 s 对 149.7 s）和完成时间（151.8 s 对 156.1 s）也是两者各领先一轮。
- **内存最低。** 服务时内存峰值为 23.3 GiB，两轮都最低；Splash 为 23.6 GiB，TensorFold 为 28.0 GiB，oMLX 为 52.9 GiB。

### 吞吐与首字时间

整批吞吐是四个请求实际输出的 token 总数除以整批完成时间（从最早发出请求到最后一个请求结束），反映服务在并发负载下的总处理能力；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，在长 prompt 下主要反映读入长输入和排队等待的时间。图中越靠右下表现越好。

### 各项指标对比

下表列出各参测应用在各项指标上的结果。表中数值为两轮测试的中位数，括号内为两轮中的最小值和最大值；每轮的数值取该轮三个批次（三组不同的 prompt）的中位数。整批吞吐越高越好，其余时间和内存指标越低越好；前六项指标每行最优的数值加粗显示。

| 指标 | IronMLX dev (c6ef14ec2) | oMLX 0.7.2 | Splash 1.4.1 | TensorFold 1.1.6 |
|---|---|---|---|---|
| 整批吞吐（tok/s，越高越好）¹ | **6.63** (6.21–⁠7.04) | 5.63 (5.40–⁠5.85) | 6.56 (6.42–⁠6.71) | 4.84 (4.84–⁠4.84) |
| 首字时间中位数（s） | **84.7** (83.3–⁠86.1) | 160.4 (155.3–⁠165.5) | 87.2 (85.9–⁠88.4) | 131.1 (130.8–⁠131.5) |
| 最慢请求的首字时间（s） | **146.3** (138.2–⁠154.3) | 163.8 (160.2–⁠167.5) | 149.7 (147.8–⁠151.6) | 204.9 (204.7–⁠205.1) |
| 完成时间中位数（s） | **88.4** (87.1–⁠89.6) | 177.1 (170.9–⁠183.3) | 96.3 (96.2–⁠96.3) | 179.2 (178.5–⁠179.9) |
| 最慢请求的完成时间（s）¹ | **151.8** (142.4–⁠161.2) | 182.0 (174.5–⁠189.6) | 156.1 (152.6–⁠159.6) | 211.7 (211.7–⁠211.7) |
| 服务时内存峰值（GiB） | **23.3** (23.2–⁠23.3) | 52.9 (52.7–⁠53.0) | 23.6 (23.6–⁠23.6) | 28.0 (28.0–⁠28.0) |
| 单请求解码速度（tok/s，辅助）² | 83.1 (81.5–⁠84.7) | 15.4 (14.3–⁠16.6) | 37.6 (36.4–⁠38.8) | 5.6 (5.6–⁠5.6) |

首字时间中位数、内存和单请求解码速度的先后两轮一致；完成时间中位数两轮都是 IronMLX、Splash 领先；整批吞吐、最慢请求的首字时间和完成时间，IronMLX 与 Splash 在两轮中先后互换，之后的先后两轮一致。

> [!NOTE]
> ¹ 整批吞吐由整批完成时间换算得出（实际输出 token 数 ÷ 整批完成时间），而整批完成时间与最慢请求的完成时间只差各请求发送时刻的差异（不超过 2.4 ms），因此这两项反映的是同一结果，比较时不应视为两项独立的优势。IronMLX 的知识 3 在第 235 个 token 处自然结束，含知识 3 的批次实际输出 1,002 个 token；oMLX 有一批的知识 3 在第 250 个 token 处自然结束；其余批次都是 1,024 个 token。
>
> ² 单请求解码速度取决于各应用如何安排四个请求：先读完输入的请求如果在其他请求读入期间单独解码，速度接近单请求；如果和其他请求的 prefill 交替进行，速度会低很多。它不反映整批处理能力，只作辅助参考。

> [!NOTE]
> 服务时内存峰值在计分批期间测量，包含四个 30K 输入的 KV 缓存。加载模型和预热阶段的峰值另有不同：IronMLX 约 27.9–28.2 GiB，高于其服务时峰值；Splash 约 19.4 GiB，oMLX 约 22.3–22.9 GiB，TensorFold 约 28.0–28.2 GiB。本页不比较加载阶段的内存。

### 请求响应时间线

下图展示四个请求同时发出后，每个请求的首字时间和完成时间，用于观察各应用在并发负载下如何安排四个请求的处理。横轴是从发出请求起经过的时间；竖线表示请求收到第一个输出内容的时间，圆点表示请求完成的时间。图中数值的取法是：在每个批次内，把四个请求的首字时间和完成时间分别按先后排序，再对 6 个批次同一位次的数值取中位数。因此竖线和圆点是分别排序的，同一位次的竖线和圆点不一定属于同一个请求。

<!-- benchmark:timeline qwen38-dense-b4-30k -->

客户端同时发出请求，不等于引擎内部会合批。从时间线和各服务自己的日志、状态接口看，四个请求的处理方式如下：

- **IronMLX dev (c6ef14ec2)：** 四个输入依次读入，首字约在 31、67、103、146 s 出现；每个请求出首字后 2–7 s 完成。完成日志显示每个请求都单独解码（批宽 1），每个验证窗口用 15 节点的草稿树。输出与 B1 页中逐个单独处理同样的 prompt 逐字节相同。
- **oMLX 0.7.2：** 第一个请求单独读入，首字约在 36 s 出现；其余三个请求的输入一起读入，首字集中在 156–164 s。之后三个请求一起做批量推测解码（日志中这条批量路径名为 “Lightning MTP”），个别请求有一段改走标准解码。
- **Splash 1.4.1：** 四个输入依次读入，首字约在 32、69、107、151 s 出现；解码批次的宽度统计全部为 1，即每次只解码一个请求。长输入的 prefill 按默认设置把部分 FFN 计算交给 Neural Engine。部分任务的输出与 B1 页中单独处理时不同。
- **TensorFold 1.1.6：** 原生引擎（`qwen27`），按 `--parallel 4` 建 4 个通道。四个输入依次读入，首字约在 42、104、159、205 s 出现；先读完的请求在后续请求读入期间继续解码，因此单请求解码速度只有约 5.6 tok/s，最后两个请求几乎同时完成（约 211 s）。输出与 B1 页中逐个单独处理同样的 prompt 逐字节相同。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 电源 | 每个会话都接交流电 |
| 测试时间 | 2026 年 10 月 28 日（UTC 00:36–02:46） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始。会话期间每秒采样一次热压力：预热批期间都正常；四个 30K 输入的 prefill 让机器明显发热，所有应用的每个计分批期间热压力都升至较高水平 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX dev (c6ef14ec2) | `dev` 分支提交 `c6ef14ec2` 的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结 | 按 App 的方式启动；`--dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 32768 --kv-quant none`；M5 默认配置（含 ANE `auto`，30K 输入会启用），不加任何调优开关 |
| oMLX 0.7.2 | 官方 App（`oMLX-0.7.2-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 32,768，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.4.1 | 官方 bottle | `--max-context 32768`；KV 缓存保持默认的 int8；Neural Engine 保持默认开启；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每批都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 1.1.6 | 官方原生发布包（sha256 `0cd208ba…`），tag `v1.1.6` → `eea9dc9` | `--drafter-bits 4 --parallel 4 --context 32768`，prompt 缓存与快照关闭，keep-warm 保持默认 |

所有应用的共同设置：草稿模型 4-bit、上下文 32,768 token、可配置容量的设为 4、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。每个服务实际生效的上下文都在启动后从其接口或设置核对为 32,768。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次 IronMLX 的知识 3 每次都在 235 token 处自然结束，oMLX 的知识 3 有一次在 250 token 处自然结束，其余都因长度结束于 256。
- **Prompt：** 六个 30K prompt（三个编程、三个知识问答，与 B1 页相同），每个加上聊天模板后为 30,732 token；分成三组，每批四个 prompt 互不相同。每个请求的服务端 prompt token 数都核对为 30,732，没有截断或丢弃输入。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批（短 prompt），再同时发出一个四请求计分批（最大发送时间差 2.4 ms），然后关闭服务。2 轮 × 4 个应用 × 3 组 prompt = 24 个会话；两轮应用顺序为 ABCE、ECBA（互为倒序），每个应用的平均位置相同，三组 prompt 的先后按轮次轮换。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为实际输出 token 数（客户端按 target tokenizer 计数）除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。
- **有效性：** 24 个会话、96 个计分请求全部通过所有检查；没有任何会话剔除。第一次正式运行在第 5 个会话时被检查拦下：oMLX 把批中一个请求从推测解码切到标准解码完成，这一段不写推测解码的结束日志，而检查原本要求每个请求都有这条日志。客户端侧该批四个请求都正常完成。修正检查后，经决定从头完整重跑了全部 24 个会话；本页只使用重跑的数据。
- **输出计数：** 服务端计数为准；客户端用 target tokenizer 对完整输出重新计数作核对，允许相差不超过 3 个 token（重新编码时相邻 token 的切分可能与生成时不同）。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为开发版本。** 本页的 IronMLX 是 `dev` 分支的构建，不是正式发布版本；正式发布版本的表现可能不同。
- **吞吐与 Splash 没有分出先后。** 两者的整批吞吐只差 1.0%，两轮各领先一轮。
- **轮间波动。** 同一组 prompt 两轮之间，IronMLX 的整批吞吐第二轮比第一轮低 9.8–12.3%，oMLX 低 5.2–8.0%，Splash 低 4.3–5.4%，TensorFold 变化不超过 2.3%。本页没有确定 IronMLX 第二轮下降的原因。
- **ANE 会改变输出。** IronMLX 默认在 30K 输入的 prefill 中启用 ANE，贪心解码的输出与只用 GPU 时不同；知识 3 的自然结束即出现在默认设置下（见 [B1 页](qwen38-dense-b1-30k.md)）。
- 其他输入长度、其他模型、其他并发度或真实多用户负载下的表现。本页只测了约 30K token 一种长输入，四个请求同时到达。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同。
- 机器发热时的表现。每个会话都从正常热压力开始，但所有计分批都在较高热压力下完成；本页没有覆盖机器长时间持续高负载的情况。
- 多轮对话中的长上下文复用。每个计分请求都是全新的长输入且不使用前缀缓存。

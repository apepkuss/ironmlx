# Qwen3.6 35B A3B B1 短 prompt 单请求性能对比

[English](../../benchmarks/qwen36-moe-b1-short.md)

> [!NOTE]
> 本页是短 prompt 的单请求性能对比；30K 长 prompt 的对比见 [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-30k.md)和 [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-30k.md)。短 prompt 性能对比测试系列：
>
> - Qwen3.6 35B A3B B1 单请求
> - [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-short.md)

B1 单请求性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.6-35B-A3B 混合专家（MoE）模型，服务每次只处理一个请求。所有请求都使用短 prompt（输入 40–83 token），输出上限为 256 token；本页结论只适用于这种负载。参与本次单请求性能对比的本地推理应用有 oMLX、Splash 和 IronMLX，其中 Splash 测了两种设置（见下方说明和 [Splash 的两种设置](#splash-的两种设置)）。TensorFold 1.1.6 不支持这个模型，没有参测。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

> [!NOTE]
> 本页 Splash 测了两种设置，以 `--verify-rows` 的取值区分：
>
> - **Splash auto**：默认设置（`--verify-rows auto`）。速度更快，但在这个模型上，贪心输出每次运行可能不同。
> - **Splash all**：`--verify-rows all`，每个周期验证整个草稿块，输出可复现。

## 结论

短 prompt B1 单请求性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下（名次在 4 个配置之间排列）：

<!-- benchmark:kpis qwen36-moe-b1-short -->

- **内存最低。** 服务时内存峰值为 20.0 GiB，四轮都最低；Splash 两种设置都是 21.1 GiB，oMLX 为 21.6 GiB。
- **解码速度与 Splash auto 并列第一。** 解码速度中位数为 249.7 tok/s，Splash auto 为 253.6 tok/s，四轮中两者各领先两轮；Splash auto 的四轮在 225.1–263.1 之间，IronMLX 在 248.8–251.5 之间。IronMLX 比 Splash all（242.4）高 3.0%，四轮都更快；oMLX 为 236.1。
- **完成时间第二。** 一个请求从发出到完成的时间中位数为 1.090 s，比 Splash auto（1.082 s）长 0.7%，四轮中 Splash auto 领先三轮；比 Splash all（1.162 s）短 6.2%，四轮都更短；oMLX 为 1.260 s。
- **首字时间第三，差距只有几毫秒。** 首字时间中位数为 50 ms，Splash auto 为 47 ms，Splash all 为 48 ms，三者的四轮范围互相重叠；oMLX 为 102 ms。
- **输出可复现。** IronMLX 和 Splash all 的每个任务四轮输出都逐字节相同；Splash auto 有 5 个任务、oMLX 有 4 个任务的四轮输出不完全相同。

### 解码速度与首字时间

解码速度是一个请求开始输出后每秒生成的 token 数，反映生成长回复时的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

内存四轮都是 IronMLX 最低、oMLX 最高。首字时间 oMLX 四轮都最慢，其余三个配置每轮的先后都在变。完成时间前三轮都是 Splash auto、IronMLX、Splash all、oMLX；第四轮 Splash auto 明显变慢（解码速度 225.1 tok/s），IronMLX 第一。解码速度 IronMLX 在第 1、4 轮第一，Splash auto 在第 2、3 轮第一。

> [!NOTE]
> 服务时内存峰值在六个计分请求期间测量。加载模型和预热阶段，IronMLX 的峰值（约 22.1 GiB）高于服务时；本页不比较加载阶段的内存。

### Splash 的两种设置

在 MoE 模型上，Splash 1.4.1 默认（`--verify-rows auto`）由一个从之前周期学到的"验证预算"决定每个解码周期验证草稿块中的哪些行；它的说明写明这样更快，但贪心解码的输出每次运行可能不同。`--verify-rows all` 则每个周期验证整个草稿块，输出可复现（稠密模型上两种设置相同）。本页把两种设置都列出：默认设置反映开箱即用的速度，`--verify-rows all` 反映在输出可复现的条件下的速度。

本次实测中，Splash auto 比 Splash all 的解码速度高 4.6%（253.6 对 242.4 tok/s），完成时间短 6.9%（1.082 对 1.162 s），但四轮之间的波动也更大。oMLX 0.7.2 也有类似的机制：DFlash 验证模式默认为 `adaptive`，按实测耗时和接受率决定每个周期验证几个草稿；本页 oMLX 使用默认设置。IronMLX 没有这类设置，输出始终可复现。

### 各任务结果

六个任务的输出长度相同（256 token），但各应用的草稿命中情况随内容变化，所以各任务的快慢不同。下表为每个任务四轮测试的中位数，每行最优的数值加粗显示。

| 编程 2（54） | 0.761 | 0.861 | 0.718 | **0.699** |

|---|---|---|---|---|

各配置处理单个请求时都使用外部 DFlash2 草稿模型做推测解码，每个计分请求都有草稿被接受。从各服务自己的日志和状态接口看：

- **IronMLX dev (c6ef14ec2)：** 线性草稿验证（这个模型不使用草稿树），每个窗口的草稿数量由默认的窗口成本策略自动调整；全部窗口都带草稿。
- **oMLX 0.7.2：** 每个请求的日志都记录了推测解码的接受情况。
- **Splash 1.4.1 auto：** 状态接口中的草稿与接受计数随每个请求增加；启动日志写明按验证预算选择验证的行（`--verify-rows auto`）。
- **Splash 1.4.1 all：** 同上；启动日志写明每个周期验证草稿块的全部行（`--verify-rows all`）。

| 项目 | 配置 |

| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 28 日（UTC 05:55–06:32） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始；两次正式运行各自的第一个会话例外，只按热压力条件等待，开始时距上一次运行的服务退出分别约 100 s 和 82 s。会话期间每秒采样一次热压力，全程保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX dev (c6ef14ec2) | `dev` 分支提交 `c6ef14ec2` 的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结 | 按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置（ANE 对这个模型不适用），不加任何调优开关 |
| oMLX 0.7.2 | 官方 App（`oMLX-0.7.2-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化，DFlash 验证模式保持默认的 `adaptive` |
| Splash 1.4.1 auto | 官方 bottle | `--max-context 8192`；KV 缓存保持默认的 int8；`--verify-rows` 保持默认的 `auto`；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每个请求都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| Splash 1.4.1 all | 同上 | 与 Splash 1.4.1 auto 相同，另加 `--verify-rows all`；启动后核对 Splash 引擎进程确实带有该参数（Splash 1.4.1 auto 的引擎进程不带） |
| TensorFold 1.1.6 | — | 未参测：按其 [1.1.6 文档](https://github.com/ashhart/TensorFold/blob/v1.1.6/docs/recipes/qwen3.6-moe.md)，Metal 原生引擎没有这个模型的家族（`qwen3_5_moe`），只能使用旧版 Python 引擎 |

所有应用的共同设置：草稿模型 4-bit、上下文 8,192 token、可配置容量的设为 4（测试客户端每次只发一个请求）、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次每个计分请求都因长度结束，服务端计数恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），互不相同，也不同于预热 prompt。
- **会话：** 每个会话启动全新服务，先发两个预热请求，再逐个发出六个计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。测试前事先规定先跑两轮（顺序 ABCS、SCBA，A 为 IronMLX，B 为 oMLX，C 为 Splash auto，S 为 Splash all），如果任一指标中相邻两名的先后在两轮中不一致、或两轮范围重叠，就紧接着按 BASC、CSAB 补跑两轮。本次首字时间（Splash 两种设置）和解码速度（Splash auto 与 IronMLX）在前两轮先后互换，完成时间（Splash auto 与 IronMLX）和内存（Splash 两种设置）的两轮范围重叠，因此补跑，共 4 轮 × 4 个配置 = 16 个会话，每个配置的平均位置相同。
- **缓存：** 每个请求都确认前缀缓存与磁盘缓存关闭或未被使用；每个请求都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取四轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。
- **有效性：** 16 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。
- **输出可复现性：** IronMLX 和 Splash all 的每个任务四轮输出逐字节相同。Splash auto 在编程 1、编程 3 和三个知识任务上、oMLX 在编程 1 和三个知识任务上，四轮输出不完全相同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优（Splash all 是为输出可复现而另加的对照配置）；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。TensorFold 没有参测，是因为其当前版本不支持这个模型，这不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为开发版本。** 本页的 IronMLX 是 `dev` 分支的构建，不是正式发布版本；正式发布版本的表现可能不同。
- **差距较小的项目。** IronMLX 与 Splash auto 的解码速度四轮各领先两轮，完成时间只差 0.7%；首字时间三个配置之间只差几毫秒，四轮范围互相重叠。这些项目不应视为明确的优势或劣势。
- 长输入、其他模型、并发请求或真实多用户负载下的表现。并发结果见[Qwen3.6 35B A3B B4 短 prompt 并发性能对比](qwen36-moe-b4-short.md)；约 30K token 长输入的单请求结果见[Qwen3.6 35B A3B B1 30K prompt 性能对比](qwen36-moe-b1-30k.md)。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量；也没有评估 Splash auto 和 oMLX 默认设置下输出的变化对回答质量有没有影响。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 轮间波动。同一任务四轮之间，首字时间 oMLX 最多相差 80 ms（编程 3：116 到 196 ms），Splash all 39 ms，IronMLX 26 ms，Splash auto 16 ms；解码速度 Splash auto 最多相差 32.4%（编程 3：241.4 到 319.6 tok/s），oMLX 23.2%，Splash all 19.8%，IronMLX 3.9%。

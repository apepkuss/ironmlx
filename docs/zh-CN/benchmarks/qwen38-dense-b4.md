# Qwen3.8 27B B4 并发性能对比

[English](../../benchmarks/qwen38-dense-b4.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

参与本次并发性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b4 -->

- **首字最快。** 看到第一个字的等待时间中位数为 251 ms，四轮都第一；第二名 TensorFold 0.6.6 为 276 ms。
- **最慢请求的首字也最快。** 四个请求中最慢的一个在 430 ms 出现第一个字，四轮都第一；TensorFold 0.6.6 为 441 ms。
- **吞吐第三。** 四个请求一起完成的吞吐为 146.8 tok/s，比 Splash（153.3）低 4.2%，比 TensorFold 0.6.6（150.4）低 2.4%；Splash 四轮都第一。
- **内存第三。** 服务时内存峰值为 21.9 GiB；Splash 最低（19.3 GiB）。

### 吞吐与首字时间

整批吞吐是四个请求的输出 token 总数除以整批完成时间（从最早发出请求到最后一个请求结束），反映服务在并发负载下的总处理能力；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

客户端同时发出请求，不等于引擎内部会合批。从各服务自己的日志和状态接口看，四个请求的处理方式如下：

- **IronMLX 0.2.0-rc.2：** 使用外部 DFlash2 草稿模型；有两个及以上请求可以合批时，把它们放在一起做 ragged 线性批量验证；只剩一个请求，或某个请求临近输出长度上限时，该请求单独用 15 节点的草稿树验证。输出与逐个单独处理同样的 prompt 逐字节相同。
- **oMLX 0.7.0：** 使用外部 DFlash2 草稿模型，对四个请求做批量推测解码（日志中这条批量路径名为 “Lightning MTP”）。
- **Splash 1.3.0：** 使用外部 DFlash2 草稿模型；四个请求在最多四行的共享批次中解码；每批有一个请求先出首字（约 0.4 s），其余三个请求在同一时刻出首字（约 0.64 s）。
- **TensorFold 0.6.6：** Python 引擎，使用外部 DFlash2 草稿模型；最多四个请求共享每一轮验证。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 电源 | 每个会话都接交流电 |
| 测试时间 | 2026 年 10 月 13 日（UTC 04:04–07:25） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，然后等到 macOS 热压力连续 60 秒处于正常水平才开始。会话期间每秒采样一次热压力，全程保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX 0.2.0-rc.2 | 官方发布包 `IronMLX.dmg`（sha256 `55a37763…`），tag `v0.2.0-rc.2` → `0ef3c55` | 使用包内服务程序和 Metal 运行时，按 App 的方式启动；`--dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`；M5 默认配置，不加任何调优开关 |
| oMLX 0.7.0 | 官方 App | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.3.0 | 官方 bottle | `--kv-format bf16 --max-context 8192`，SSD 缓存关闭；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 0.6.6 | 源码 tag（`cb2ebf05`） | `--drafter-bits 4 --lane-kernels on --parallel 4`，prompt 缓存与快照关闭 |
| TensorFold 1.0.5 | 官方原生发布包（sha256 `0fa38f57…`），tag `v1.0.5` → `bec00ae` | `--drafter-bits 4 --parallel 4`，prompt 缓存与快照关闭，keep-warm 保持默认 |

所有应用的共同设置：草稿模型 4-bit、BF16 KV 缓存、上下文 8,192 token、可配置容量的设为 4；其余保持各应用自己的默认策略。

> 五个应用加载的是同一份模型文件，所有权重、配置和 tokenizer 文件都与上表的 Hugging Face 版本按 SHA-256 逐一核对一致。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。每个计分请求都因长度结束，服务端计数和 target tokenizer 计数都恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），分成三组，每批四个 prompt 互不相同。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批，再同时发出一个四请求计分批（最大发送时间差 1.4 ms），然后关闭服务。4 轮 × 5 个应用 × 3 组 prompt = 60 个会话，顺序均衡，每个应用的平均位置相同。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为 1,024 token 除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。
- **有效性：** 60 个会话、240 个计分请求全部通过所有检查；没有任何会话重试或剔除。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。例如 TensorFold 1.0.5 的原生引擎对这个 27B 模型不支持并发处理，这是该版本对这个模型的实现方式，不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- 长输入、其他模型、其他并发度或真实多用户负载下的表现。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同，每个计分请求都生成 256 个 token。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 批次间波动。工作量完全相同的批次之间，IronMLX 的吞吐波动比其他应用都大：同一组 prompt 四轮之间相差约 10%（例如 145 到 161 tok/s），其他应用不超过 6.5%。五个应用的先后没有因此改变。

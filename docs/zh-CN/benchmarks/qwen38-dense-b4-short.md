# Qwen3.8 27B B4 短 prompt 并发性能对比

[English](../../benchmarks/qwen38-dense-b4-short.md)

> [!NOTE]
> 本页是短 prompt 的并发性能对比；30K 长 prompt 的对比见 [Qwen3.8 27B B1 单请求](qwen38-dense-b1-30k.md)和 [Qwen3.8 27B B4 并发](qwen38-dense-b4-30k.md)。短 prompt 性能对比测试系列：
>
> - Qwen3.8 27B B4 并发
> - [Qwen3.8 27B B1 单请求](qwen38-dense-b1-short.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.8-27B 稠密模型，四个请求同时到达服务。所有请求都使用短 prompt（输入 40–83 token），输出上限为 256 token；本页结论只适用于这种负载。参与本次并发性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

短 prompt B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b4-short -->

- **吞吐第一，但领先幅度小。** 四个请求一起完成的吞吐为 195.5 tok/s，两轮都第一；比 Splash（191.7）高 2.0%，比 TensorFold（162.7）高 20.2%。
- **首字时间第二。** 首字时间中位数为 224 ms，两轮都第二；TensorFold 两轮都最快（190 ms）。
- **最慢请求的首字时间第二。** 四个请求中最慢的一个在 376 ms 出现第一个字；TensorFold 为 329 ms。
- **内存最低。** 服务时内存峰值为 19.4 GiB，两轮都最低；Splash 为 20.1 GiB。

### 吞吐与首字时间

整批吞吐是四个请求的输出 token 总数除以整批完成时间（从最早发出请求到最后一个请求结束），反映服务在并发负载下的总处理能力；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

### 各项指标对比

下表列出各参测应用在各项指标上的结果。表中数值为两轮测试的中位数，括号内为两轮中的最小值和最大值；每轮的数值取该轮三个批次（三组不同的 prompt）的中位数。整批吞吐越高越好，其余时间和内存指标越低越好；前六项指标每行最优的数值加粗显示。在前六项主要指标上，各应用的排名在两轮测试中都保持一致。

| 指标 | IronMLX 0.2.0-rc.3 | oMLX 0.7.2 | Splash 1.4.1 | TensorFold 1.1.6 |
|---|---|---|---|---|
| 整批吞吐（tok/s，越高越好）¹ | **195.5** (194.2–⁠196.8) | 103.4 (102.4–⁠104.4) | 191.7 (189.8–⁠193.6) | 162.7 (159.4–⁠166.0) |
| 首字时间中位数（ms） | 224 (215–⁠234) | 667 (660–⁠673) | 500 (499–⁠501) | **190** (189–⁠191) |
| 最慢请求的首字时间（ms） | 376 (369–⁠383) | 822 (804–⁠839) | 500 (499–⁠502) | **329** (328–⁠330) |
| 完成时间中位数（s） | 4.32 (4.30–⁠4.34) | 8.29 (8.07–⁠8.51) | **4.16** (4.13–⁠4.20) | 4.64 (4.62–⁠4.66) |
| 最慢请求的完成时间（s）¹ | **5.24** (5.20–⁠5.27) | 9.90 (9.80–⁠10.00) | 5.34 (5.29–⁠5.39) | 6.30 (6.17–⁠6.43) |
| 服务时内存峰值（GiB） | **19.4** (19.4–⁠19.4) | 22.8 (22.8–⁠22.8) | 20.1 (20.1–⁠20.1) | 22.5 (22.4–⁠22.6) |
| 单请求解码速度（tok/s，辅助） | 62.6 (61.7–⁠63.5) | 33.6 (32.9–⁠34.3) | 70.8 (70.6–⁠71.0) | 59.7 (59.7–⁠59.8) |
| 解码并发度（辅助）² | 3.46 (3.46–⁠3.46) | 3.19 (3.16–⁠3.21) | 3.03 (3.00–⁠3.05) | 3.11 (3.11–⁠3.12) |

> [!NOTE]
> ¹ 整批吞吐由整批完成时间换算得出（1,024 token ÷ 整批完成时间），而整批完成时间与最慢请求的完成时间只差各请求发送时刻的差异（不超过 1.5 ms），因此这两项反映的是同一结果，比较时不应视为两项独立的优势。

> [!NOTE]
> ² 解码并发度是测试完成后，用每个计分批的客户端时间戳推导出的，不在事先写定的测试协议中：四个请求的解码时间之和 ÷ 至少有一个请求在解码的总时间（每个请求从收到第一个输出内容到 `[DONE]` 算作在解码）。1 表示从没有两个请求同时解码，4 表示四个请求始终一起解码。四个应用都在 3.0–3.5，说明短 prompt 下四个请求基本是一起解码的；30K 长 prompt 下的对照见 [Qwen3.8 27B B4 30K prompt 并发性能对比](qwen38-dense-b4-30k.md)。

> [!NOTE]
> 服务时内存峰值在计分批期间测量。加载模型和预热阶段，IronMLX 的峰值（约 28.1–28.2 GiB）明显高于服务时，也高于其他应用服务时的峰值；oMLX 约 22.4–23.0 GiB，Splash 约 19.4 GiB，TensorFold 约 22.0–22.1 GiB。本页不比较加载阶段的内存。

### 请求响应时间线

下图展示四个请求同时发出后，每个请求的首字时间和完成时间，用于观察各应用在并发负载下如何安排四个请求的处理。横轴是从发出请求起经过的时间；竖线表示请求收到第一个输出内容的时间，圆点表示请求完成的时间。图中数值的取法是：在每个批次内，把四个请求的首字时间和完成时间分别按先后排序，再对 6 个批次同一位次的数值取中位数。因此竖线和圆点是分别排序的，同一位次的竖线和圆点不一定属于同一个请求。

<!-- benchmark:timeline qwen38-dense-b4-short -->

客户端同时发出请求，不等于引擎内部会合批。从各服务自己的日志和状态接口看，四个请求的处理方式如下：

- **IronMLX 0.2.0-rc.3：** 使用外部 DFlash2 草稿模型；有两个及以上请求可以合批时，把它们放在一起做 ragged 线性批量验证；只剩一个请求时，该请求单独用 15 节点的草稿树验证。输出与逐个单独处理同样的 prompt 逐字节相同。
- **oMLX 0.7.2：** 使用外部 DFlash2 草稿模型，对四个请求做批量推测解码（日志中这条批量路径名为 “Lightning MTP”）；批处理中会做批量与标准解码的校准，个别请求会有一段改走标准解码。
- **Splash 1.4.1：** 使用外部 DFlash2 草稿模型；四个请求在最多四行的共享批次中解码；每批有一个请求先出首字（约 0.14 s），其余三个请求在同一时刻出首字（约 0.50 s）。输出与逐个单独处理同样的 prompt 逐字节相同。
- **TensorFold 1.1.6：** 原生引擎（`qwen27`），按 `--parallel 4` 建 4 个通道，四个请求共享每一轮验证，每个请求都使用 DFlash2 草稿。输出与逐个单独处理同样的 prompt 逐字节相同。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 27 日（UTC 12:08–13:03） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始。会话期间每秒采样一次热压力，全程保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX 0.2.0-rc.3 | 提交 `c6ef14ec2` 的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结。该提交到 `v0.2.0-rc.3` 标签（`2d5186bb0`）之间只删除了从未启用的实验开关并更新了文档，测量的代码路径与 0.2.0-rc.3 相同 | 按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置（含 ANE `auto`；短 prompt 不触发 ANE），不加任何调优开关 |
| oMLX 0.7.2 | 官方 App（`oMLX-0.7.2-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.4.1 | 官方 bottle | `--max-context 8192`；KV 缓存保持默认的 int8；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每批都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 1.1.6 | 官方原生发布包（sha256 `0cd208ba…`），tag `v1.1.6` → `eea9dc9` | `--drafter-bits 4 --parallel 4 --context 8192`，prompt 缓存与快照关闭，keep-warm 保持默认 |

所有应用的共同设置：草稿模型 4-bit、上下文 8,192 token、可配置容量的设为 4、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。每个计分请求都因长度结束，服务端计数和 target tokenizer 计数都恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），分成三组，每批四个 prompt 互不相同。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批，再同时发出一个四请求计分批（最大发送时间差 1.5 ms），然后关闭服务。2 轮 × 4 个应用 × 3 组 prompt = 24 个会话；两轮应用顺序为 ABCE、ECBA（互为倒序），每个应用的平均位置相同，三组 prompt 的先后按轮次轮换。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为 1,024 token 除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。解码并发度是测试完成后用同一批时间戳推导的，没有重跑，定义见[各项指标对比](#各项指标对比)的注释。
- **有效性：** 24 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为候选发布版本。** 0.2.0-rc.3 是预发布版本，不是 0.2.0 正式版本；正式版本的表现可能不同。
- 长输入、其他模型、其他并发度或真实多用户负载下的表现。约 30K token 长输入的并发结果见[Qwen3.8 27B B4 30K prompt 并发性能对比](qwen38-dense-b4-30k.md)。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同，每个计分请求都生成 256 个 token。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 吞吐差距较小。IronMLX 与 Splash 的整批吞吐只差 2.0%；两轮范围不重叠，先后在两轮中一致，但差距接近批次之间的波动。
- 批次间波动。同一组 prompt 两轮之间，oMLX 的吞吐最多相差约 8%（第二组：102 到 111 tok/s），TensorFold 约 4%，IronMLX 与 Splash 不超过 2%。各应用的先后没有因此改变。

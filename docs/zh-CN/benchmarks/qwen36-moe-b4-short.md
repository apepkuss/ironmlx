# Qwen3.6 35B A3B B4 短 prompt 并发性能对比

[English](../../benchmarks/qwen36-moe-b4-short.md)

> [!NOTE]
> 短 prompt 性能对比测试系列：
>
> - Qwen3.6 35B A3B B4 并发
> - [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)
> - [Qwen3.8 27B B1 单请求](qwen38-dense-b1-short.md)
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.6-35B-A3B 混合专家（MoE）模型，四个请求同时到达服务。所有请求都使用短 prompt（输入 40–83 token），输出固定为 256 token；本页结论只适用于这种负载。参与本次并发性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

短 prompt B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen36-moe-b4-short -->

- **首字最快。** 看到第一个字的等待时间中位数为 158 ms，四轮都第一；第二名 TensorFold 0.6.6 为 174 ms。
- **最慢请求的首字第二，与 Splash 接近。** 四个请求中最慢的一个在 260 ms 出现第一个字；Splash 为 256 ms，快 1.3%，四轮中三轮领先。
- **吞吐第二。** 四个请求一起完成的吞吐为 304.7 tok/s，比 Splash（347.5）低 12.3%，高于 TensorFold 0.6.6（289.0）和 oMLX（195.7）；Splash 四轮都第一。
- **内存最低。** 服务时内存峰值为 20.9 GiB，四轮都最低；第二名 TensorFold 0.6.6 为 21.2 GiB。

### 吞吐与首字时间

整批吞吐是四个请求的输出 token 总数除以整批完成时间（从最早发出请求到最后一个请求结束），反映服务在并发负载下的总处理能力；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

> [!NOTE]
> 未包含 TensorFold 1.0.5：按其 [1.0.5 文档](https://github.com/ashhart/TensorFold/blob/v1.0.5/README.md#qualified-models)，原生引擎对 Qwen3.6 仍在认证中；原生引擎只对 Qwen3.8-27B 类 checkpoint 接受外部 DFlash2 草稿模型（[源码](https://github.com/ashhart/TensorFold/blob/v1.0.5/zig/src/native/metal.zig#L101-L105)）。

### 各项指标对比

下表列出各参测应用在各项指标上的结果。表中数值为四轮测试的中位数，括号内为四轮中的最小值和最大值；每轮的数值取该轮三个批次（三组不同的 prompt）的中位数。整批吞吐越高越好，其余时间和内存指标越低越好；前六项指标每行最优的数值加粗显示。在前六项主要指标上，各应用的排名在四轮测试中都保持一致，只有“最慢请求的首字时间”一项，IronMLX 在四轮中有一轮领先 Splash。

| 指标 | IronMLX 0.2.0-rc.2 | oMLX 0.7.0 | Splash 1.3.0 | TensorFold 0.6.6 |
|---|---|---|---|---|
| 整批吞吐（tok/s，越高越好）¹ | 304.7 (303.9–⁠305.3) | 195.7 (188.8–⁠201.5) | **347.5** (342.2–⁠352.5) | 289.0 (285.5–⁠295.5) |
| 首字时间中位数（ms） | **158** (155–⁠162) | 309 (288–⁠347) | 256 (233–⁠263) | 174 (166–⁠182) |
| 最慢请求的首字时间（ms） | 260 (256–⁠267) | 458 (422–⁠479) | **256** (234–⁠263) | 303 (298–⁠333) |
| 完成时间中位数（s） | 3.24 (3.23–⁠3.27) | 4.21 (4.07–⁠4.43) | **2.31** (2.28–⁠2.33) | 2.81 (2.78–⁠2.87) |
| 最慢请求的完成时间（s）¹ | 3.36 (3.35–⁠3.37) | 5.23 (5.08–⁠5.42) | **2.95** (2.91–⁠2.99) | 3.54 (3.46–⁠3.59) |
| 服务时内存峰值（GiB） | **20.9** (20.8–⁠20.9) | 23.7 (23.2–⁠24.1) | 21.5 (21.3–⁠21.5) | 21.2 (21.1–⁠21.3) |
| 单请求解码速度（tok/s，辅助） | 82.6 (81.8–⁠82.7) | 66.8 (63.0–⁠70.0) | 128.1 (127.2–⁠128.5) | 99.1 (97.7–⁠101.8) |

> [!NOTE]
> ¹ 整批吞吐由整批完成时间换算得出（1,024 token ÷ 整批完成时间），而整批完成时间与最慢请求的完成时间只差各请求发送时刻的差异（不超过 1.3 ms），因此这两项反映的是同一结果，比较时不应视为两项独立的优势。

> [!NOTE]
> 服务时内存峰值在计分批期间测量。加载模型和预热阶段，IronMLX 的峰值（约 21.8 GiB）高于服务时；本页不比较加载阶段的内存。

### 请求响应时间线

下图展示四个请求同时发出后，每个请求的首字时间和完成时间，用于观察各应用在并发负载下如何安排四个请求的处理。横轴是从发出请求起经过的时间；竖线表示请求收到第一个输出内容的时间，圆点表示请求完成的时间。图中数值的取法是：在每个批次内，把四个请求的首字时间和完成时间分别按先后排序，再对 12 个批次同一位次的数值取中位数。因此竖线和圆点是分别排序的，同一位次的竖线和圆点不一定属于同一个请求。

<!-- benchmark:timeline qwen36-moe-b4-short -->

客户端同时发出请求，不等于引擎内部会合批。从各服务自己的日志和状态接口看，四个请求的处理方式如下：

- **IronMLX 0.2.0-rc.2：** 使用外部 DFlash2 草稿模型，把四个请求放在一起做 ragged 线性批量验证（这个模型不使用草稿树）。四个请求的首字依次到达，间隔约 60–75 ms；之后四个请求在约 0.17 s 内先后完成。在该模型的默认草稿预算策略下，约 93–95% 的批量步骤不使用草稿、每个请求前进一个 token。输出与逐个单独处理同样的 prompt 逐字节相同。
- **oMLX 0.7.0：** 使用外部 DFlash2 草稿模型，对四个请求做批量推测解码（日志中这条批量路径名为 “Lightning MTP”，每批先对两个、再对四个请求启用）。同一 prompt 在不同批次中的输出有变化。
- **Splash 1.3.0：** 使用外部 DFlash2 草稿模型；每批有一个请求先出首字（约 0.17 s），其余三个请求在同一时刻出首字（约 0.26 s）。
- **TensorFold 0.6.6：** Python 引擎，用并行 lane（`--parallel 4`）处理请求；使用外部 DFlash2 草稿模型，在这个模型上还同时使用其内置的 copy proposer。每个请求都接受了 DFlash2 草稿。

| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 13 日（UTC 12:26–14:58） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX 0.2.0-rc.2 | 官方发布包 `IronMLX.dmg`（sha256 `55a37763…`），tag `v0.2.0-rc.2` → `0ef3c55` | 使用包内服务程序和 Metal 运行时，按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`；M5 默认配置，不加任何调优开关 |
| oMLX 0.7.0 | 官方 App | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.3.0 | 官方 bottle | `--kv-format bf16 --max-context 8192`，SSD 缓存关闭；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 0.6.6 | 源码 tag（`cb2ebf05`） | `--drafter-bits 4 --lane-kernels on --parallel 4`，prompt 缓存与快照关闭 |

所有应用的共同设置：草稿模型 4-bit、BF16 KV 缓存、上下文 8,192 token、可配置容量的设为 4；其余保持各应用自己的默认策略。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。每个计分请求都因长度结束，服务端计数和 target tokenizer 计数都恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），分成三组，每批四个 prompt 互不相同。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批，再同时发出一个四请求计分批（最大发送时间差 1.3 ms），然后关闭服务。4 轮 × 4 个应用 × 3 组 prompt = 48 个会话，顺序均衡，每个应用的平均位置相同。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为 1,024 token 除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。
- **有效性：** 48 个会话、192 个计分请求全部通过所有检查，每个请求的两种 token 计数都是 256；本次运行没有任何会话重试或剔除。

> [!NOTE]
> 此前的运行：有两次运行因一个 oMLX 请求的输出按 target tokenizer 重新计数只有 255 个 token（oMLX 自报 256）而停止。之后对所有应用统一修订计数规则（服务端自报 256，tokenizer 重新计数可为 255 或 256），并从头重跑。另有一次会话之间不做降温等待的完整运行，各项指标的先后与本页相同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。例如 TensorFold 1.0.5 没有参测，是因为其原生引擎尚未认证 Qwen3.6，这不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- 长输入、其他模型、其他并发度或真实多用户负载下的表现。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同，每个计分请求都生成 256 个 token。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 批次间波动。工作量完全相同的批次之间，同一组 prompt 四轮之间的吞吐差异：IronMLX 不超过 2.0%，Splash 不超过 3.0%，TensorFold 0.6.6 不超过 6.4%，oMLX 不超过 7.0%。四个应用的先后没有因此改变。

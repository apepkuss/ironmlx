# Qwen3.6 35B A3B B4 短 prompt 并发性能对比

[English](../../benchmarks/qwen36-moe-b4-short.md)

> [!NOTE]
> 短 prompt 性能对比测试系列：
>
> - Qwen3.6 35B A3B B4 并发
> - [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)
> - [Qwen3.8 27B B1 单请求](qwen38-dense-b1-short.md)
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.6-35B-A3B 混合专家（MoE）模型，四个请求同时到达服务。所有请求都使用短 prompt（输入 40–83 token），输出上限为 256 token；本页结论只适用于这种负载。参与本次并发性能对比的本地推理应用有 oMLX、Splash 和 IronMLX，其中 Splash 与 [B1 页](qwen36-moe-b1-short.md)一样测了两种设置（见下方说明）。TensorFold 1.1.6 不支持这个模型，没有参测。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

> [!NOTE]
> 本页 Splash 测了两种设置，以 `--verify-rows` 的取值区分：
>
> - **Splash auto**：默认设置（`--verify-rows auto`）。速度更快，但在这个模型上，贪心输出每次运行可能不同。
> - **Splash all**：`--verify-rows all`，每个周期验证整个草稿块，输出可复现。

## 结论

短 prompt B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下（名次在 4 个配置之间排列）：

<!-- benchmark:kpis qwen36-moe-b4-short -->

- **吞吐第一。** 四个请求一起完成的吞吐为 427.0 tok/s，两轮都第一；比 Splash auto（410.5）高 4.0%，比 Splash all（373.4）高 14.4%，oMLX 为 243.8。按 prompt 组看，第一组 Splash 两种设置的吞吐都高于 IronMLX，IronMLX 的领先来自第二、三组（见[适用范围与局限](#适用范围与局限)）。
- **首字时间中位数最短。** 四个请求首字时间的中位数为 109 ms，两轮都第一；Splash 两种设置约 150 ms，oMLX 为 331 ms。
- **最慢请求的首字时间第三。** 四个请求中最慢的一个在 167 ms 出现第一个字，比 Splash all（150 ms）慢 11.5%，比 Splash auto（151 ms）慢 10.2%，两轮都是如此。
- **完成时间：整批最先完成，中位请求较慢。** 最慢请求的完成时间为 2.40 s，两轮都最短（Splash auto 2.50 s）；但四个请求完成时间的中位数为 2.05 s，比 Splash auto（1.86 s）长 10.6%，与 Splash all（2.04 s）接近。
- **内存最低。** 服务时内存峰值为 20.5 GiB，两轮都最低；Splash 两种设置约 21.5–21.6 GiB，oMLX 为 24.5 GiB。

### 吞吐与首字时间

整批吞吐是四个请求实际输出的 token 总数除以整批完成时间（从最早发出请求到最后一个请求结束），反映服务在并发负载下的总处理能力；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

### 各项指标对比

下表列出各参测配置在各项指标上的结果。表中数值为两轮测试的中位数，括号内为两轮中的最小值和最大值；每轮的数值取该轮三个批次（三组不同的 prompt）的中位数。速度越高越好，时间和内存越低越好；前六项指标每行最优的数值加粗显示，后两项为辅助指标。前六项指标中，各配置的先后两轮都相同。

| 指标 | IronMLX dev (c6ef14ec2) | oMLX 0.7.2 | Splash 1.4.1 auto | Splash 1.4.1 all |
|---|---|---|---|---|
| 整批吞吐（tok/s，越高越好）¹ | **427.0** (423.8–⁠430.3) | 243.8 (241.0–⁠246.6) | 410.5 (401.3–⁠419.7) | 373.4 (372.3–⁠374.5) |
| 首字时间中位数（ms） | **109** (105–⁠112) | 331 (316–⁠346) | 151 (150–⁠152) | 149 (149–⁠149) |
| 最慢请求的首字时间（ms） | 167 (164–⁠170) | 410 (387–⁠433) | 151 (150–⁠153) | **150** (150–⁠150) |
| 完成时间中位数（s） | 2.05 (2.04–⁠2.07) | 3.79 (3.76–⁠3.82) | **1.86** (1.83–⁠1.88) | 2.04 (2.04–⁠2.05) |
| 最慢请求的完成时间（s）¹ | **2.40** (2.38–⁠2.42) | 4.20 (4.15–⁠4.25) | 2.50 (2.44–⁠2.55) | 2.74 (2.73–⁠2.75) |

| 单请求解码速度（tok/s，辅助） | 131.0 (130.1–⁠131.9) | 73.1 (71.7–⁠74.6) | 155.9 (152.8–⁠159.0) | 136.3 (135.9–⁠136.7) |
| 解码并发度（辅助）² | 3.37 (3.36–⁠3.37) | 3.51 (3.50–⁠3.52) | 2.84 (2.81–⁠2.88) | 2.95 (2.92–⁠2.97) |

> [!NOTE]
> ¹ 整批吞吐由整批完成时间换算得出（实际输出 token 数 ÷ 整批完成时间；本次每批都是 1,024 token），而整批完成时间与最慢请求的完成时间只差各请求发送时刻的差异（不超过 1.3 ms），因此这两项反映的是同一结果，比较时不应视为两项独立的优势。

> [!NOTE]
> ² 解码并发度是测试完成后，用每个计分批的客户端时间戳推导出的，不在事先写定的测试协议中：四个请求的解码时间之和 ÷ 至少有一个请求在解码的总时间（每个请求从收到第一个输出内容到 `[DONE]` 算作在解码）。1 表示从没有两个请求同时解码，4 表示四个请求始终一起解码。

> [!NOTE]
> 服务时内存峰值在计分批期间测量。加载模型和预热阶段，IronMLX 的峰值（约 22.1 GiB）高于服务时；本页不比较加载阶段的内存。

### Splash 的两种设置

Splash 两种设置的含义见 [B1 页](qwen36-moe-b1-short.md#splash-的两种设置)。在四个请求并发时，Splash auto 比 Splash all 的整批吞吐高 9.9%（410.5 对 373.4 tok/s），完成时间中位数短 9.1%（1.86 对 2.04 s）。

### 请求响应时间线

下图展示四个请求同时发出后，每个请求的首字时间和完成时间，用于观察各应用在并发负载下如何安排四个请求的处理。横轴是从发出请求起经过的时间；竖线表示请求收到第一个输出内容的时间，圆点表示请求完成的时间。图中数值的取法是：在每个批次内，把四个请求的首字时间和完成时间分别按先后排序，再对 6 个批次同一位次的数值取中位数。因此竖线和圆点是分别排序的，同一位次的竖线和圆点不一定属于同一个请求。

<!-- benchmark:timeline qwen36-moe-b4-short -->

客户端同时发出请求，不等于引擎内部会合批。从时间线和各服务自己的日志、状态接口看，四个请求的处理方式如下：

- **IronMLX dev (c6ef14ec2)：** 四个请求的首字依次在约 48、87、125、167 ms 出现；之后把正在解码的请求放在一起做 ragged 线性批量验证（这个模型不使用草稿树），全部验证窗口中约 96% 是多个请求合批的窗口，其余是只剩一个请求时的单独窗口，所有窗口都带草稿。四个请求在约 1.8–2.4 s 之间先后完成。
- **oMLX 0.7.2：** 对四个请求做批量推测解码（日志中这条批量路径名为 “Lightning MTP”），首字在约 177–410 ms 之间出现，解码并发度最高（3.51）；批处理中会做批量与标准解码的校准，个别请求有一段改走标准解码，本次有 3 个请求在停放后以标准解码收尾。
- **Splash 1.4.1 auto 与 all：** 每批有一个请求先出首字（约 45 ms），其余三个请求在同一时刻出首字（约 150 ms）；第一个请求最早完成，整批在约 2.5 s（默认设置）和 2.7 s（`--verify-rows all`）完成。

| 项目 | 配置 |

| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 28 日（UTC 07:29–08:21） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始。会话期间每秒采样一次热压力，全程保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX dev (c6ef14ec2) | `dev` 分支提交 `c6ef14ec2` 的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结 | 按 App 的方式启动；`--dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`；M5 默认配置（ANE 对这个模型不适用），不加任何调优开关 |
| oMLX 0.7.2 | 官方 App（`oMLX-0.7.2-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化，DFlash 验证模式保持默认的 `adaptive` |
| Splash 1.4.1 auto | 官方 bottle | `--max-context 8192`；KV 缓存保持默认的 int8；`--verify-rows` 保持默认的 `auto`；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每批都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| Splash 1.4.1 all | 同上 | 与 Splash 1.4.1 auto 相同，另加 `--verify-rows all`；启动后核对 Splash 引擎进程确实带有该参数（Splash 1.4.1 auto 的引擎进程不带） |
| TensorFold 1.1.6 | — | 未参测：按其 [1.1.6 文档](https://github.com/ashhart/TensorFold/blob/v1.1.6/docs/recipes/qwen3.6-moe.md)，Metal 原生引擎没有这个模型的家族（`qwen3_5_moe`），只能使用旧版 Python 引擎 |

所有应用的共同设置：草稿模型 4-bit、上下文 8,192 token、可配置容量的设为 4、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。

### 模型

| 角色 | 模型 | 来源 | 版本 | 格式 |
|---|---|---|---|---|
| 目标模型 | `mlx-community/Qwen3.6-35B-A3B-4bit` | [Hugging Face](https://huggingface.co/mlx-community/Qwen3.6-35B-A3B-4bit/tree/38740b847e4cb78f352aba30aa41c76e08e6eb46) | `38740b847e4cb78f352aba30aa41c76e08e6eb46`（2026-04-16） | MLX safetensors，混合专家，4-bit affine 量化，group size 64（专家路由门控为 8-bit）；Apache-2.0 |

> 三个应用加载的是同一份模型文件，所有权重、配置和 tokenizer 文件都与上表的 Hugging Face 版本按 SHA-256 逐一核对一致。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次每个计分请求都因长度结束，服务端计数恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），分成三组，每批四个 prompt 互不相同。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批，再同时发出一个四请求计分批（最大发送时间差 1.3 ms），然后关闭服务。2 轮 × 4 个配置 × 3 组 prompt = 24 个会话；两轮顺序为 ABCS、SCBA（互为倒序；A 为 IronMLX，B 为 oMLX，C 为 Splash auto，S 为 Splash all），每个配置的平均位置相同，三组 prompt 的先后按轮次轮换。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为实际输出 token 数（客户端按 target tokenizer 计数）除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。解码并发度是测试完成后用同一批时间戳推导的，没有重跑，定义见[各项指标对比](#各项指标对比)的注释。
- **有效性：** 24 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。
- **输出可复现性：** 同一组 prompt 在两轮中的输出，IronMLX 12 个请求全部逐字节相同；Splash all 有 2 个、Splash auto 有 9 个、oMLX 有 11 个两轮不同。IronMLX 的输出也不受同批其他请求的影响（同一 prompt 在不同组合的批次中输出相同），但在这个模型上与 [B1 页](qwen36-moe-b1-short.md)中单独处理时的输出不完全相同（6 个任务中 4 个不同）：IronMLX 在这个模型上为多请求合批验证使用的计算方式与单请求不同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优（Splash all 是为输出可复现而另加的对照配置）；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。TensorFold 没有参测，是因为其当前版本不支持这个模型，这不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为开发版本。** 本页的 IronMLX 是 `dev` 分支的构建，不是正式发布版本；正式发布版本的表现可能不同。
- **完成时间的两个口径结论不同。** IronMLX 整批最先完成（最慢请求的完成时间最短），但中位请求的完成时间比 Splash auto 长；两者分别反映"四个请求全部完成"和"典型请求完成"，应结合起来看。
- 长输入、其他模型、其他并发度或真实多用户负载下的表现。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- **吞吐领先依赖 prompt 组。** 三组 prompt 中，第一组 Splash all（两轮 462.2、454.6 tok/s）和 Splash auto（442.0、455.6）都不低于 IronMLX（442.0、448.0）；第二、三组 IronMLX 领先 Splash 两种设置。换用其他 prompt，吞吐的先后可能不同。
- 批次间波动。同一组 prompt 两轮之间，oMLX 的整批吞吐最多相差 12.6%（第一组：219.9 到 251.5 tok/s），Splash auto 4.4%，IronMLX 与 Splash all 不超过 1.6%。

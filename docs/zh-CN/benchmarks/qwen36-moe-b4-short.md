# Qwen3.6 35B A3B B4 短 prompt 并发性能对比

[English](../../benchmarks/qwen36-moe-b4-short.md)

> [!NOTE]
> 本页是短 prompt 的并发性能对比；30K 长 prompt 的对比见 [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-30k.md)和 [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-30k.md)。短 prompt 性能对比测试系列：
>
> - Qwen3.6 35B A3B B4 并发
> - [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)

B4 并发性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.6-35B-A3B 混合专家（MoE）模型，四个请求同时到达服务。所有请求都使用短 prompt（输入 40–83 token），输出上限为 256 token；本页结论只适用于这种负载。参与本次并发性能对比的本地推理应用有 oMLX、Splash 和 IronMLX，其中 Splash 与 [B1 页](qwen36-moe-b1-short.md)一样测了两种设置（见下方说明）。TensorFold 1.1.6 不支持这个模型，没有参测。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

> [!NOTE]
> 本页 Splash 测了两种设置，以 `--verify-rows` 的取值区分：
>
> - **Splash auto**：默认设置（`--verify-rows auto`）。速度更快，但在这个模型上，贪心输出每次运行可能不同。
> - **Splash all**：`--verify-rows all`，每个周期验证整个草稿块；单请求时输出可复现，本页的并发负载下输出不完全可复现（见[负载与流程](#负载与流程)）。

## 结论

短 prompt B4 并发性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下（名次在 4 个配置之间排列）：

<!-- benchmark:kpis qwen36-moe-b4-short -->

- **吞吐第一。** 四个请求一起完成的吞吐为 428.9 tok/s，两轮都第一，三组 prompt 上都第一；比 Splash auto（414.6）高 3.5%，比 Splash all（390.6）高 9.8%，oMLX 为 242.5。
- **首字时间中位数最短。** 四个请求首字时间的中位数为 92 ms，两轮都第一；Splash auto 为 147 ms，Splash all 为 155 ms，oMLX 为 348 ms。
- **最慢请求的首字时间与 Splash auto 没有分出先后。** 四个请求中最慢的一个在 146 ms 出现第一个字，Splash auto 为 148 ms，两轮各领先一轮；Splash all 为 155 ms，oMLX 为 424 ms。
- **完成时间：整批最先完成，中位请求较慢。** 最慢请求的完成时间为 2.39 s，两轮都最短（Splash auto 2.47 s）；但四个请求完成时间的中位数为 1.97 s，比 Splash auto（1.87 s）长 5.5%，与 Splash all（2.01 s）接近。
- **内存最低。** 服务时内存峰值为 20.5 GiB，两轮都最低；Splash 两种设置约 21.5 GiB，oMLX 为 24.4 GiB。

### 吞吐与首字时间

整批吞吐是四个请求实际输出的 token 总数除以整批完成时间（从最早发出请求到最后一个请求结束），反映服务在并发负载下的总处理能力；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

整批吞吐、首字时间中位数、最慢请求的完成时间（IronMLX、Splash auto、Splash all、oMLX）、内存（IronMLX、Splash all、Splash auto、oMLX）和单请求解码速度（Splash auto、Splash all、IronMLX、oMLX）的先后两轮都相同。最慢请求的首字时间第一轮 IronMLX 领先、第二轮 Splash auto 领先；完成时间中位数两轮都是 Splash auto 领先，IronMLX 第一轮第二、第二轮落到 Splash all 之后第三。

> [!NOTE]
> ¹ 整批吞吐由整批完成时间换算得出（实际输出 token 数 ÷ 整批完成时间；本次每批都是 1,024 token），而整批完成时间与最慢请求的完成时间只差各请求发送时刻的差异（不超过 1.3 ms），因此这两项反映的是同一结果，比较时不应视为两项独立的优势。

> [!NOTE]
> ² 解码并发度是测试完成后，用每个计分批的客户端时间戳推导出的，不在事先写定的测试协议中：四个请求的解码时间之和 ÷ 至少有一个请求在解码的总时间（每个请求从收到第一个输出内容到 `[DONE]` 算作在解码）。1 表示从没有两个请求同时解码，4 表示四个请求始终一起解码。

> [!NOTE]
> 服务时内存峰值在计分批期间测量。加载模型和预热阶段，IronMLX 的峰值（约 22.1 GiB）高于服务时；本页不比较加载阶段的内存。

### Splash 的两种设置

Splash 两种设置的含义见 [B1 页](qwen36-moe-b1-short.md#splash-的两种设置)。在四个请求并发时，Splash auto 比 Splash all 的整批吞吐高 6.1%（414.6 对 390.6 tok/s），完成时间中位数短 7.1%（1.87 对 2.01 s）。

### 请求响应时间线

下图展示四个请求同时发出后，每个请求的首字时间和完成时间，用于观察各应用在并发负载下如何安排四个请求的处理。横轴是从发出请求起经过的时间；竖线表示请求收到第一个输出内容的时间，圆点表示请求完成的时间。图中数值的取法是：在每个批次内，把四个请求的首字时间和完成时间分别按先后排序，再对 6 个批次同一位次的数值取中位数。因此竖线和圆点是分别排序的，同一位次的竖线和圆点不一定属于同一个请求。

<!-- benchmark:timeline qwen36-moe-b4-short -->

客户端同时发出请求，不等于引擎内部会合批。从时间线和各服务自己的日志、状态接口看，四个请求的处理方式如下：

- **IronMLX 0.2.0-rc.4：** 四个请求的首字依次在约 41、77、109、147 ms 出现；之后把正在解码的请求放在一起做 ragged 线性批量验证（这个模型不使用草稿树），按窗口计约 84% 是多个请求合批验证的窗口（按各请求的验证次数计约 95%），其余是只剩一个请求时的单独窗口，所有窗口都带草稿。四个请求在约 1.8–2.4 s 之间先后完成。
- **oMLX 0.7.2：** 对四个请求做批量推测解码（日志中这条批量路径名为 "Lightning MTP"），首字在约 182–424 ms 之间出现，解码并发度最高（3.46）；批处理中会做批量与标准解码的校准并把整批停放，本次每批都停放了一次，24 个请求中有 5 个在停放后以标准解码收尾。
- **Splash 1.4.1 auto 与 all：** 每批有一个请求先出首字（约 46 ms），其余三个请求在同一时刻出首字（默认设置约 147 ms，`--verify-rows all` 约 155 ms）；第一个请求最早完成，整批在约 2.5 s（默认设置）和 2.6 s（`--verify-rows all`）完成。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`（oMLX 不支持）。计分请求可以因长度结束（服务端计数恰为 256），也可以自然结束（服务端计数在 200–256 之间）；本次每个计分请求都因长度结束，服务端计数恰为 256（客户端用 target tokenizer 重新计数、允许相差不超过 3 个 token：oMLX 有一个请求为 255，Splash all 有一个请求为 257）。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），分成三组，每批四个 prompt 互不相同。
- **会话：** 每个会话启动全新服务，先发一个四请求预热批，再同时发出一个四请求计分批（最大发送时间差 1.3 ms），然后关闭服务。2 轮 × 4 个配置 × 3 组 prompt = 24 个会话；两轮顺序为 ABCS、SCBA（互为倒序；A 为 IronMLX，B 为 oMLX，C 为 Splash auto，S 为 Splash all），每个配置的平均位置相同，三组 prompt 的先后按轮次轮换。
- **缓存：** 每批都确认前缀缓存与磁盘缓存关闭或未被使用；每批都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个内容；完成时间从发出算到 `[DONE]`，含排队；整批吞吐为实际输出 token 数（客户端按 target tokenizer 计数；因长度结束的请求计 256）除以最早发出到最后一个 `[DONE]` 的时间。内存为计分批期间每 50 ms 采样的服务进程树物理内存占用（footprint）。解码并发度是测试完成后用同一批时间戳推导的，没有重跑，定义见[各项指标对比](#各项指标对比)的注释。
- **有效性：** 24 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。
- **输出可复现性：** 同一组 prompt 在两轮中的输出，IronMLX 12 个请求全部逐字节相同；Splash all 有 4 个、Splash auto 有 5 个、oMLX 有 6 个两轮不同。IronMLX 的输出也不受同批其他请求的影响（同一 prompt 在不同组合的批次中输出相同），但在这个模型上与 [B1 页](qwen36-moe-b1-short.md)中单独处理时的输出不完全相同（6 个任务中 4 个不同）：IronMLX 在这个模型上为多请求合批验证使用的计算方式与单请求不同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优（Splash all 是另加的对照配置，每个周期验证整个草稿块）；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。TensorFold 没有参测，是因为其当前版本不支持这个模型，这不代表它在其他模型上的表现。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为候选发布版本。** 0.2.0-rc.4 是预发布版本，不是 0.2.0 正式版本；正式版本的表现可能不同。
- **完成时间的两个口径结论不同。** IronMLX 整批最先完成（最慢请求的完成时间最短），但中位请求的完成时间比 Splash auto 长；两者分别反映"四个请求全部完成"和"典型请求完成"，应结合起来看。
- **差距较小的项目。** 第一组 prompt 上，Splash all 有一轮的吞吐只比 IronMLX 低 0.4%（463.1 对 465.0 tok/s）；最慢请求的首字时间 IronMLX 与 Splash auto 只差 1.4%，两轮各领先一轮；完成时间中位数 IronMLX 与 Splash all 只差 2.0%，两轮先后互换。这些项目不应视为明确的优势或劣势。
- 长输入、其他模型、其他并发度或真实多用户负载下的表现。约 30K token 长输入的并发结果见[Qwen3.6 35B A3B B4 30K prompt 并发性能对比](qwen36-moe-b4-30k.md)。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 批次间波动。同一组 prompt 两轮之间，oMLX 的整批吞吐最多相差 19.2%（第一组：223.3 到 266.2 tok/s），Splash all 6.7%（第一组：433.9 到 463.1 tok/s），Splash auto 4.0%，IronMLX 0.8%。

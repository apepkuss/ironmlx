# Qwen3.8 27B B1 短 prompt 单请求性能对比

[English](../../benchmarks/qwen38-dense-b1-short.md)

> [!NOTE]
> 短 prompt 性能对比测试系列：
>
> - Qwen3.8 27B B1 单请求
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)
> - [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)
> - [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-short.md)

B1 单请求性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.8-27B 稠密模型，服务每次只处理一个请求。所有请求都使用短 prompt（输入 40–83 token），输出固定为 256 token；本页结论只适用于这种负载。参与本次单请求性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

短 prompt B1 单请求性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b1-short -->

- **解码速度第一。** 解码速度中位数为 89.6 tok/s，两轮都第一；比第二名 Splash（78.2）高 14.6%，比 TensorFold（74.1）高 21.0%。
- **完成时间最短。** 一个请求从发出到完成的时间中位数为 2.98 s，两轮都第一；Splash 为 3.48 s，TensorFold 为 3.56 s。
- **首字时间第二。** 首字时间中位数为 105 ms，两轮都第二；TensorFold 两轮都最快（81 ms）。
- **内存最低。** 服务时内存峰值为 17.9 GiB，两轮都最低；Splash 为 19.3 GiB。

### 解码速度与首字时间

解码速度是一个请求开始输出后每秒生成的 token 数，反映生成长回复时的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

### 各项指标对比

下表列出各参测应用在各项指标上的结果。表中数值为两轮测试的中位数，括号内为两轮中的最小值和最大值；每轮的数值取该轮六个任务的中位数。解码速度越高越好，其余时间和内存指标越低越好；每行最优的数值加粗显示。

| 指标 | IronMLX dev (c6ef14ec2) | oMLX 0.7.2 | Splash 1.4.1 | TensorFold 1.1.6 |
|---|---|---|---|---|
| 首字时间（ms） | 105 (95–⁠116) | 193 (191–⁠195) | 146 (140–⁠152) | **81** (76–⁠85) |
| 解码速度（tok/s，越高越好） | **89.6** (89.3–⁠89.9) | 68.3 (67.8–⁠68.8) | 78.2 (78.1–⁠78.3) | 74.1 (74.0–⁠74.1) |
| 完成时间（s） | **2.98** (2.97–⁠2.99) | 3.99 (3.97–⁠4.02) | 3.48 (3.48–⁠3.49) | 3.56 (3.56–⁠3.57) |
| 服务时内存峰值（GiB） | **17.9** (17.9–⁠18.0) | 21.7 (21.7–⁠21.8) | 19.3 (19.2–⁠19.3) | 19.8 (19.8–⁠19.8) |

四项指标中，各应用的先后在两轮中完全一致：解码速度、完成时间和内存都是 IronMLX、Splash、TensorFold、oMLX；首字时间是 TensorFold、IronMLX、Splash、oMLX。

### 各任务结果

六个任务的输出长度相同（256 token），但各应用的草稿命中情况随内容变化，所以各任务的快慢不同。下表为每个任务两轮测试的中位数，每行最优的数值加粗显示。

完成时间（s，越低越好）：

|---|---|---|---|---|

| 编程 2（54） | 2.67 | 3.19 | 2.62 | **1.93** |
| 编程 3（83） | **2.75** | 3.75 | 3.05 | 3.27 |

解码速度（tok/s，越高越好）：

| 任务（输入 token） | IronMLX dev (c6ef14ec2) | oMLX 0.7.2 | Splash 1.4.1 | TensorFold 1.1.6 |
|---|---|---|---|---|
| 编程 1（62） | **158.3** | 105.9 | 129.4 | 112.9 |

IronMLX 在五个任务上完成最快、解码最快；TensorFold 在编程 2 上最快。

各应用处理单个请求时都使用外部 DFlash2 草稿模型做推测解码。从各服务自己的日志和状态接口看：

- **IronMLX dev (c6ef14ec2)：** 每个验证窗口用 15 节点的草稿树，一次验证 16 行，草稿预算固定为 7；全部窗口都是树验证。
- **oMLX 0.7.2：** 每个请求的日志都记录了推测解码的接受情况。
- **Splash 1.4.1：** 状态接口中的草稿与接受计数随每个请求增加。
- **TensorFold 1.1.6：** 原生引擎（`qwen27`）；每轮验证 16 行。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 27 日（UTC 10:57–11:18） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始。会话期间每秒采样一次热压力，全程保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX dev (c6ef14ec2) | `dev` 分支提交 `c6ef14ec2` 的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结 | 按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置（含 ANE `auto`；短 prompt 不触发 ANE），不加任何调优开关 |
| oMLX 0.7.2 | 官方 App（`oMLX-0.7.2-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.4.1 | 官方 bottle | `--max-context 8192`；KV 缓存保持默认的 int8；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每个请求都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 1.1.6 | 官方原生发布包（sha256 `0cd208ba…`），tag `v1.1.6` → `eea9dc9` | `--drafter-bits 4 --parallel 4`，prompt 缓存与快照关闭，keep-warm 保持默认 |

所有应用的共同设置：草稿模型 4-bit、上下文 8,192 token、可配置容量的设为 4（测试客户端每次只发一个请求）、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。

|---|---|---|---|---|

> 四个应用加载的是同一份模型文件，所有权重、配置和 tokenizer 文件都与上表的 Hugging Face 版本按 SHA-256 逐一核对一致。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。每个计分请求都因长度结束，服务端计数和 target tokenizer 计数都恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），互不相同，也不同于预热 prompt。
- **会话：** 每个会话启动全新服务，先发两个预热请求，再逐个发出六个计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。2 轮 × 4 个应用 = 8 个会话，两轮顺序为 ABCE、ECBA（互为倒序），每个应用的平均位置相同。测试前事先规定：如果任一指标中相邻两名的先后在两轮中不一致、或两轮范围重叠，就紧接着按 BAEC、CEAB 补跑两轮；本次两轮的先后与范围都可以区分，没有补跑。
- **缓存：** 每个请求都确认前缀缓存与磁盘缓存关闭或未被使用；每个请求都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取两轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。
- **有效性：** 8 个会话、48 个计分请求全部通过所有检查；没有任何会话重试或剔除。IronMLX、Splash 和 TensorFold 的每个任务两轮输出逐字节相同；oMLX 在知识 2、知识 3 两个任务上两轮输出不同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- **IronMLX 为开发版本。** 本页的 IronMLX 是 `dev` 分支的构建，不是正式发布版本；正式发布版本的表现可能不同。
- 长输入、其他模型、并发请求或真实多用户负载下的表现。并发结果见[Qwen3.8 27B B4 短 prompt 并发性能对比](qwen38-dense-b4-short.md)；约 30K token 长输入的单请求结果见[Qwen3.8 27B B1 30K prompt 性能对比](qwen38-dense-b1-30k.md)。
- 尾延迟或统计显著性：单台机器上的两轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同，每个计分请求都生成 256 个 token。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 轮间波动。工作量完全相同的请求之间，IronMLX 首字时间的波动比其他应用都大：同一任务两轮之间最多相差 50 ms（编程 1：93 到 143 ms），Splash 最多相差 32 ms，oMLX 和 TensorFold 不超过 16 ms。解码速度方面，IronMLX 同一任务两轮最多相差 5.7%，其他应用不超过 2.5%。各应用的先后没有因此改变。

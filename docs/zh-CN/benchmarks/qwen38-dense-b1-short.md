# Qwen3.8 27B B1 短 prompt 单请求性能对比

[English](../../benchmarks/qwen38-dense-b1-short.md)

> [!NOTE]
> 短 prompt 性能对比测试系列：
>
> - Qwen3.8 27B B1 单请求
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)
> - [Qwen3.6 35B A3B B1 单请求](qwen36-moe-b1-short.md)
> - [Qwen3.6 35B A3B B4 并发](qwen36-moe-b4-short.md)

B1 单请求性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.8-27B 稠密模型，服务每次只处理一个请求。所有请求都使用短 prompt（输入 40–83 token），输出固定为 256 token；本页结论只适用于这种负载。参与本次单请求性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

短 prompt B1 单请求性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b1-short -->

- **首字时间与 TensorFold 1.0.5 并列第二。** 首字时间中位数为 123 ms，TensorFold 1.0.5 为 131 ms，两者四轮中各有两轮排在第二；TensorFold 0.6.6 四轮都最快（111 ms）。
- **解码速度第三。** 解码速度中位数为 73.9 tok/s，比 Splash（81.5）低 9.2%，比 TensorFold 1.0.5（75.3）低 1.8%；Splash 四轮都第一。IronMLX 四轮都快于 oMLX 和 TensorFold 0.6.6。
- **完成时间第三。** 一个请求从发出到完成的时间中位数为 3.61 s，比 Splash（3.38 s）长 6.5%，比 TensorFold 1.0.5（3.54 s）长 1.8%；Splash 四轮都第一。
- **内存第二。** 服务时内存峰值为 18.9 GiB；Splash 最低（18.6 GiB），比 IronMLX 少约 1.5%。四轮先后完全一致。

### 解码速度与首字时间

解码速度是一个请求开始输出后每秒生成的 token 数，反映生成长回复时的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

### 各项指标对比

下表列出各参测应用（TensorFold 列出 0.6.6 和 1.0.5 两个版本）在各项指标上的结果。表中数值为四轮测试的中位数，括号内为四轮中的最小值和最大值；每轮的数值取该轮六个任务的中位数。解码速度越高越好，其余时间和内存指标越低越好；每行最优的数值加粗显示。

| 指标 | IronMLX 0.2.0-rc.2 | oMLX 0.7.0 | Splash 1.3.0 | TensorFold 0.6.6 | TensorFold 1.0.5 |
|---|---|---|---|---|---|
| 首字时间（ms） | 123 (115–⁠129) | 199 (195–⁠201) | 228 (222–⁠228) | **111** (107–⁠112) | 131 (118–⁠140) |
| 解码速度（tok/s，越高越好） | 73.9 (73.9–⁠76.0) | 72.8 (71.8–⁠73.0) | **81.5** (80.7–⁠81.8) | 68.4 (67.5–⁠68.5) | 75.3 (74.5–⁠75.9) |
| 完成时间（s） | 3.61 (3.51–⁠3.62) | 3.77 (3.76–⁠3.82) | **3.38** (3.37–⁠3.41) | 3.86 (3.86–⁠3.91) | 3.54 (3.50–⁠3.59) |
| 服务时内存峰值（GiB） | 18.9 (18.9–⁠18.9) | 19.1 (19.0–⁠19.1) | **18.6** (18.6–⁠18.6) | 20.3 (20.2–⁠20.3) | 41.1 (41.1–⁠41.1) |

各应用的先后在四轮中大部分一致：内存四轮完全一致；解码速度和完成时间 Splash 四轮都第一，oMLX、TensorFold 0.6.6 四轮都是第四、第五，TensorFold 1.0.5 三轮第二、IronMLX 一轮第二；首字时间 TensorFold 0.6.6 四轮都第一，IronMLX 与 TensorFold 1.0.5 两轮互换第二、第三。

|---|---|---|---|---|---|

IronMLX 只在编程 1 上完成最快；Splash 在三个任务上最快，TensorFold 1.0.5 在两个任务上最快，oMLX 在知识 1 上最快。

各应用处理单个请求时都使用外部 DFlash2 草稿模型做推测解码。从各服务自己的日志和状态接口看：

- **IronMLX 0.2.0-rc.2：** 每个验证窗口用 15 节点的草稿树，一次验证 16 行，草稿预算固定为 7；全部窗口都是树验证。
- **oMLX 0.7.0：** 每个请求的日志都记录了推测解码的接受情况。
- **Splash 1.3.0：** 状态接口中的草稿与接受计数随每个请求增加。
- **TensorFold 0.6.6：** Python 引擎；个别任务中另有少量草稿来自其文本复制候选，其余来自 DFlash2 草稿模型。
- **TensorFold 1.0.5：** 原生引擎（`qwen27`）；每轮验证 16 行（15 个草稿节点）。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 电源 | 每个会话都接交流电 |
| 测试时间 | 2026 年 10 月 14 日（UTC 02:15–03:28） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，然后等到 macOS 热压力连续 60 秒处于正常水平才开始。会话期间每秒采样一次热压力，全程保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX 0.2.0-rc.2 | 官方发布包 `IronMLX.dmg`（sha256 `55a37763…`），tag `v0.2.0-rc.2` → `0ef3c55` | 使用包内服务程序和 Metal 运行时，按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置，不加任何调优开关 |
| oMLX 0.7.0 | 官方 App | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.3.0 | 官方 bottle | `--kv-format bf16 --max-context 8192`，SSD 缓存关闭；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 0.6.6 | 源码 tag（`cb2ebf05`） | `--drafter-bits 4 --lane-kernels on --parallel 4`，prompt 缓存与快照关闭 |
| TensorFold 1.0.5 | 官方原生发布包（sha256 `0fa38f57…`），tag `v1.0.5` → `bec00ae` | `--drafter-bits 4`，prompt 缓存与快照关闭，keep-warm 保持默认；该版本对这个模型一次只处理一个请求，未设置 `--parallel` |

所有应用的共同设置：草稿模型 4-bit、BF16 KV 缓存、上下文 8,192 token、可配置容量的设为 4（测试客户端每次只发一个请求）；其余保持各应用自己的默认策略。

### 模型

| 角色 | 模型 | 来源 | 版本 | 格式 |
|---|---|---|---|---|
| 目标模型 | `mlx-community/Qwen3.8-27B-4bit` | [Hugging Face](https://huggingface.co/mlx-community/Qwen3.8-27B-4bit/tree/3e6447f082e89cc7f0bc6e5441afd38dfce760ff) | `3e6447f082e89cc7f0bc6e5441afd38dfce760ff`（2026-08-14） | MLX safetensors，4-bit affine 量化，group size 64；Apache-2.0 |

> [!NOTE]
> 五个应用加载的是同一份模型文件，所有权重、配置和 tokenizer 文件都与上表的 Hugging Face 版本按 SHA-256 逐一核对一致。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。每个计分请求都因长度结束，服务端计数和 target tokenizer 计数都恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），互不相同，也不同于预热 prompt。
- **会话：** 每个会话启动全新服务，先发两个预热请求，再逐个发出六个计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。4 轮 × 5 个应用 = 20 个会话，四轮顺序为 ABCDE、EDCBA、BCDEA、AEDCB，每个应用的平均位置相同。
- **缓存：** 每个请求都确认前缀缓存与磁盘缓存关闭或未被使用；每个请求都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取四轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。
- **有效性：** 20 个会话、120 个计分请求全部通过所有检查；没有任何会话重试或剔除。每个应用的每个任务四轮输出逐字节相同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- 长输入、其他模型、并发请求或真实多用户负载下的表现。并发结果见[Qwen3.8 27B B4 短 prompt 并发性能对比](qwen38-dense-b4-short.md)。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同，每个计分请求都生成 256 个 token。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 差距较小的项目。首字时间上 IronMLX 与 TensorFold 1.0.5 两轮互换第二；这一先后在四轮数据中不能可靠区分。
- 轮间波动。工作量完全相同的请求之间，IronMLX 的波动比其他应用都大：同一任务四轮之间，首字时间最多相差 75 ms（知识 1：105 到 180 ms），解码速度最多相差 7.9%；其他应用的首字时间最多相差 48 ms，解码速度不超过 3.0%。

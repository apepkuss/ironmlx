# Qwen3.8 27B B1 短 prompt 单请求性能对比

[English](../../benchmarks/qwen38-dense-b1-short.md)

> [!NOTE]
> 本页是短 prompt 的单请求性能对比；30K 长 prompt 的对比见 [Qwen3.8 27B B1 单请求](qwen38-dense-b1-30k.md)和 [Qwen3.8 27B B4 并发](qwen38-dense-b4-30k.md)。短 prompt 性能对比测试系列：
>
> - Qwen3.8 27B B1 单请求
> - [Qwen3.8 27B B4 并发](qwen38-dense-b4-short.md)

B1 单请求性能对比验证的目的是，通过与当前 Apple Silicon 平台最优秀推理应用的对比，一方面，帮助开发者定位 IronMLX 的优势和劣势，为后续优化提供方向；另一方面，让用户更了解 IronMLX 实际表现，判断是否适合他们的使用场景。

本页针对 Qwen3.8-27B 稠密模型，服务每次只处理一个请求。所有请求都使用短 prompt（输入 40–83 token），输出上限为 256 token；本页结论只适用于这种负载。参与本次单请求性能对比的本地推理应用有 oMLX、Splash、TensorFold 和 IronMLX。各应用的具体信息见[参测应用与配置](#参测应用与配置)。关于本次性能对比验证的环境搭建、测试方法等信息，请详见[方法](#方法)。

## 结论

短 prompt B1 单请求性能对比验证中，综合验证所得数据，IronMLX 的总体性能表现如下：

<!-- benchmark:kpis qwen38-dense-b1-short -->

- **解码速度第一。** 解码速度中位数为 89.4 tok/s，四轮都第一；比第二名 Splash（80.3）高 11.3%，比 TensorFold（75.9）高 17.7%。
- **完成时间最短。** 一个请求从发出到完成的时间中位数为 3.00 s，四轮都第一；Splash 为 3.37 s，TensorFold 为 3.51 s。
- **首字时间第二。** 首字时间中位数为 107 ms，仅次于 TensorFold（102 ms）；两者在各轮中轮流第一，IronMLX 在第 1、3 轮第一，TensorFold 在第 2、4 轮第一。
- **内存最低。** 服务时内存峰值为 18.0 GiB，四轮都最低；Splash 为 19.3 GiB。

### 解码速度与首字时间

解码速度是一个请求开始输出后每秒生成的 token 数，反映生成长回复时的速度；首字时间（TTFT）是从发出请求到收到第一个输出内容的时间，反映用户感知到的响应延迟。图中越靠右下表现越好。

### 各项指标对比

下表列出各参测应用在各项指标上的结果。表中数值为四轮测试的中位数，括号内为四轮中的最小值和最大值；每轮的数值取该轮六个任务的中位数。解码速度越高越好，其余时间和内存指标越低越好；每行最优的数值加粗显示。

| 指标 | IronMLX 0.2.0 | oMLX 0.7.3rc1 | Splash 1.5.0 | TensorFold 1.2.0 |
|---|---|---|---|---|
| 首字时间（ms） | 107 (100–⁠136) | 198 (193–⁠199) | 149 (149–⁠150) | **102** (102–⁠104) |
| 解码速度（tok/s，越高越好） | **89.4** (89.0–⁠90.0) | 68.9 (68.1–⁠69.1) | 80.3 (79.7–⁠82.2) | 75.9 (75.7–⁠76.1) |
| 完成时间（s） | **3.00** (2.97–⁠3.02) | 3.97 (3.96–⁠4.02) | 3.37 (3.29–⁠3.38) | 3.51 (3.50–⁠3.52) |
| 服务时内存峰值（GiB） | **18.0** (18.0–⁠18.0) | 21.7 (21.7–⁠21.9) | 19.3 (19.3–⁠19.3) | 26.3 (26.3–⁠26.3) |

解码速度、完成时间和内存三项指标中，各应用的先后在四轮中完全一致：解码速度和完成时间都是 IronMLX、Splash、TensorFold、oMLX；内存是 IronMLX、Splash、oMLX、TensorFold。首字时间方面，Splash 和 oMLX 每轮都是第三和第四，IronMLX 与 TensorFold 则轮流第一：IronMLX 在第 1、3 轮第一，TensorFold 在第 2、4 轮第一。

> [!NOTE]
> 服务时内存峰值在六个计分请求期间测量。加载模型和预热阶段，IronMLX 的峰值（约 28.2 GiB）明显高于服务时，也高于其他应用服务时的峰值；oMLX 约 22.0 GiB，Splash 约 19.4 GiB，TensorFold 约 26.3 GiB。本页不比较加载阶段的内存。

### 各任务结果

六个任务的输出长度相同（256 token），但各应用的草稿命中情况随内容变化，所以各任务的快慢不同。下表为每个任务四轮测试的中位数，每行最优的数值加粗显示。

完成时间（s，越低越好）：

| 任务（输入 token） | IronMLX 0.2.0 | oMLX 0.7.3rc1 | Splash 1.5.0 | TensorFold 1.2.0 |
|---|---|---|---|---|
| 编程 1（62） | **1.73** | 2.63 | 2.17 | 2.26 |
| 编程 2（54） | 2.62 | 3.17 | 2.61 | **1.91** |
| 编程 3（83） | **2.79** | 3.72 | 3.12 | 3.18 |
| 知识 1（46） | **3.34** | 4.47 | 4.70 | 4.09 |
| 知识 2（40） | **3.21** | 4.22 | 3.61 | 3.84 |
| 知识 3（49） | **3.56** | 4.52 | 4.69 | 4.49 |

解码速度（tok/s，越高越好）：

| 任务（输入 token） | IronMLX 0.2.0 | oMLX 0.7.3rc1 | Splash 1.5.0 | TensorFold 1.2.0 |
|---|---|---|---|---|
| 编程 1（62） | **157.5** | 105.0 | 127.6 | 118.7 |
| 编程 2（54） | 102.7 | 85.8 | 103.5 | **141.1** |
| 编程 3（83） | **96.8** | 74.5 | 86.7 | 83.6 |
| 知识 1（46） | **78.8** | 59.6 | 56.1 | 64.0 |
| 知识 2（40） | **82.6** | 63.3 | 74.0 | 68.3 |
| 知识 3（49） | **74.0** | 58.9 | 56.2 | 58.1 |

IronMLX 在五个任务上完成最快、解码最快；TensorFold 在编程 2 上最快。

各应用处理单个请求时都使用外部 DFlash2 草稿模型做推测解码。从各服务自己的日志和状态接口看：

- **IronMLX 0.2.0：** 每个验证窗口用 15 节点的草稿树，一次验证 16 行，草稿预算固定为 7；全部窗口都是树验证。
- **oMLX 0.7.3rc1：** 每个请求的日志都记录了推测解码的接受情况。
- **Splash 1.5.0：** 状态接口中的草稿与接受计数随每个请求增加。
- **TensorFold 1.2.0：** 原生引擎（`qwen27`）；服务端对每个请求报告的每轮最少验证行数，随请求不同在 6 到 12 之间。

## 方法

### 软硬件配置

| 项目 | 配置 |
|---|---|
| 计算机 | MacBook Pro（Mac17,6），Apple M5 Max，40 核 GPU，128 GB 统一内存 |
| 操作系统 | macOS 26.4（25E246） |
| 测试时间 | 2026 年 10 月 31 日（UTC 14:21–15:02） |
| 运行隔离 | 同一时间只运行一个推理服务；测试期间没有其他推理服务或 GPU 计算任务。测试客户端运行在同一台 Mac 上，通过 `127.0.0.1` 连接 |
| 温控 | 每个会话前，机器在上一个服务退出后至少空闲两分钟，并且最近连续 60 秒的 macOS 热压力都处于正常水平才开始。唯一的例外是第 3、4 轮的第一个会话（oMLX）：它是补跑那次运行的第一个会话，只适用热压力条件，在上一个服务退出约 82 秒后开始。会话期间每秒采样一次热压力，全程保持正常 |

### 参测应用与配置

| 应用 | 来源 | 配置 |
|---|---|---|
| IronMLX 0.2.0 | 标签 `v0.2.0-rc.4`（提交 `a0afebe55`）的 release 构建（`cargo build --locked --release`），服务程序与 MLX Metal 运行时一起冻结。0.2.0 正式版本原样发布这份代码 | 按 App 的方式启动；`--dflash2-block-size 8 --dflash2-draft-bits 4 --max-sequences 4 --max-cache-cap 8192 --kv-quant none`（block size 8 与不设置时相同：默认取草稿模型自身的 block size 8）；M5 默认配置（含 ANE `auto`；短 prompt 不触发 ANE），不加任何调优开关 |
| oMLX 0.7.3rc1 | 官方 App（`oMLX-0.7.3rc1-macos26-27.dmg`） | `--no-cache --max-concurrent-requests 4`；设置中上下文 8,192，DFlash2 草稿按 4-bit（group 64）量化 |
| Splash 1.5.0 | 官方 bottle | `--max-context 8192`；草稿验证保持默认的 `--verify-rows auto`；KV 缓存保持默认的 int8；默认 32 GiB 非持久磁盘 KV 缓存保持开启（每个会话都是新进程，每个请求都核对缓存命中计数不变）；草稿模型在加载时固定量化为 4-bit（Splash 内置行为，无需设置） |
| TensorFold 1.2.0 | 官方原生发布包（sha256 `81fffaab…`），tag `v1.2.0` → `a388876` | `--drafter-bits 4 --parallel 4 --context 8192`，prompt 缓存与快照关闭，keep-warm 保持默认 |

所有应用的共同设置：草稿模型 4-bit、上下文 8,192 token、可配置容量的设为 4（测试客户端每次只发一个请求）、可跨请求复用的前缀缓存关闭；KV 缓存除 Splash 使用其默认 int8 外均为 BF16；其余保持各应用自己的默认策略。

### 负载与流程

- **请求：** 流式 `/v1/chat/completions`，单条 user 消息，temperature 0，关闭思考，`max_tokens` 256，不用 `ignore_eos`。每个计分请求都因长度结束，服务端计数和 target tokenizer 计数都恰为 256。
- **Prompt：** 六个短 prompt（三个编程、三个知识问答；输入 40–83 token），互不相同，也不同于预热 prompt。
- **会话：** 每个会话启动全新服务，先发两个预热请求，再逐个发出六个计分请求（上一个请求结束 1 秒后发下一个），然后关闭服务。前两轮顺序为 ABCE、ECBA（互为倒序），每个应用的平均位置相同。测试前事先规定：如果任一指标中相邻两名的先后在两轮中不一致、或两轮范围重叠，就紧接着按 BAEC、CEAB 补跑两轮。首字时间中，TensorFold 与 IronMLX 的先后在两轮中不一致（第 1 轮 IronMLX 第一，第 2 轮 TensorFold 第一），两轮范围也重叠，因此补跑了第 3、4 轮：4 轮 × 4 个应用 = 16 个会话，每个应用在每个位置各运行一次。
- **缓存：** 每个请求都确认前缀缓存与磁盘缓存关闭或未被使用；每个请求都从服务计数或日志确认推测解码在运行。
- **指标：** 首字时间从发出算到第一个非空内容；解码速度为（输出 token 数 − 第一个内容包含的 token 数）÷（最后一个与第一个内容之间的时间），在客户端按 target tokenizer 计数；完成时间从发出算到 `[DONE]`。每轮取六个任务的中位数，再取四轮的中位数。内存为六个计分请求期间（含请求间隔）每 50 ms 采样的服务进程树物理内存占用（footprint）峰值。
- **有效性：** 16 个会话、96 个计分请求全部通过所有检查；没有任何会话重试或剔除。IronMLX、Splash 和 TensorFold 的每个任务四轮输出逐字节相同；oMLX 在知识 1、知识 2、知识 3 三个任务上各轮输出不完全相同。

## 适用范围与局限

本页结论只适用于[方法](#方法)中描述的条件。以下是这次对比没有覆盖或需要注意的地方：

- **不代表各应用的整体水平。** 本页结果只反映上述版本在这个模型、这种负载和这台机器上的表现，不能据此判断任何应用整体性能的高低。除方法中列出的共同设置外，各应用都使用默认策略，没有针对本测试调优；换用其他模型、其他负载或各应用推荐的配置，结果和先后都可能不同。如果你认为某个应用的配置不公平，欢迎通过 [GitHub Issues](https://github.com/apepkuss/ironmlx/issues) 反馈。
- 长输入、其他模型、并发请求或真实多用户负载下的表现。并发结果见[Qwen3.8 27B B4 短 prompt 并发性能对比](qwen38-dense-b4-short.md)；约 30K token 长输入的单请求结果见[Qwen3.8 27B B1 30K prompt 性能对比](qwen38-dense-b1-30k.md)。
- 尾延迟或统计显著性：单台机器上的四轮数据不足以支持这两类结论。
- 回答质量。本测试只比较速度和内存，没有评估回答质量。各应用的输出不完全相同，每个计分请求都生成 256 个 token。
- 机器发热时的表现。本页每个会话都从正常热压力开始，没有覆盖机器持续发热时的情况。
- 轮间波动。工作量完全相同的请求之间，IronMLX 首字时间的波动比其他应用都大：同一任务四轮之间最多相差 76 ms（编程 2：91 到 167 ms），Splash 最多相差 63 ms，oMLX 14 ms，TensorFold 3 ms。解码速度方面，IronMLX 同一任务四轮最多相差 3.0%，oMLX 最多相差 6.8%，Splash 4.6%，TensorFold 0.8%。解码速度、完成时间和内存的先后没有改变；首字时间方面，IronMLX 各轮的中位数在 100 到 136 ms 之间，TensorFold 在 102 到 104 ms 之间，因此两者在各轮中轮流第一。

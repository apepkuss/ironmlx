# Gemma4 Drafter Attribution Notes

## Scope

This note records the correctness attribution for Gemma4 12B assistant-drafter
acceptance drops observed on synthetic long prompts. The goal is to separate
IronMLX implementation errors from model/prompt-distribution effects.

## Evidence

The Python reference path used `mlx-vlm` with:

- base: `mlx-community/gemma-4-12B-it-4bit`
- drafter: `mlx-community/gemma-4-12B-it-assistant-4bit`
- greedy sampling
- `draft_tokens=2`
- `prefill_step_size=2048`

For the repeated quick-brown-fox benchmark prompt, Python reference first-round
tokens matched the IronMLX trace:

| prompt tokens | target first token | drafter tokens | verifier tokens |
| --- | --- | --- | --- |
| 4000 | `236772` | `[239441, 236772]` | `[236772, 236772, 236772]` |
| 24000 | `236761` | `[107, 236865]` | `[236761, 236761, 236761]` |

For the agent-trace prompt family generated by
`ironmlx/tests/fixtures/gemma4_long_context/gen_reference.py`, target-only
after-append argmax matched the Python reference at 18K, 19.9K, 20K, and 24K.
The 24K case has a small top-5 edge drift, but the greedy argmax remains
aligned and does not explain the synthetic prompt's zero first-token acceptance.

The drafter first round also matches on the first proposed token. In the 24K
agent-trace case, the second proposed token differs between Python and IronMLX,
but the Python logits show a near tie: token `236812` scores `4.65625` and token
`1904` scores `4.625`. The IronMLX token is therefore inside the Python
reference top-2, consistent with a small quantized-kernel numerical drift rather
than a position or KV wiring error.

## Conclusion

The synthetic quick-brown-fox acceptance collapse is reproducible in the Python
reference implementation. The current evidence points to drafter quality under
that prompt distribution, not an IronMLX-specific MTP round-loop, position, or
shared-KV bug.

The production policy implication is to treat Gemma4 drafter speedup as
prompt-distribution dependent and keep observability enabled through trace
windows and MTP acceptance counters. The default `draft_tokens=2` remains the
right starting point, but deployment should monitor acceptance and fall back to
base generation when a workload consistently rejects the first draft token.

# P6 — Qwen3.5 VL (Vision-Language) 多模态推理 Design

**Goal**: 在 ironmlx 的 P4 Dense（已完成的文本路径）基础上，加上 Vision Tower + image preprocessing + cross-modal token routing，让 Qwen3.5-4B-MLX-4bit 这个本质 multimodal 的模型能正确处理图文混合输入。

**Background**: 见 `memory/project_p8a_stage9_findings.md`（stage 9 prefill 优化已完成）+ `memory/MEMORY.md` 索引。

P3-P4 已完成的关键事实：

- `mlx-community/Qwen3.5-4B-MLX-4bit` 模型文件本身**就是 multimodal**（`Qwen3_5ForConditionalGeneration` 架构，含 `vision_config` + 297 个 `vision_tower.*` weight tensors）
- 现有 ironmlx P4 Dense 实现只用了 `language_model.*` weights，把 `vision_tower.*` **完全忽略**
- 模型已含 image/video special token IDs（image=248056, video=248057, vision_start=248053, vision_end=248054），tokenizer + vocab 都齐备
- Qwen3.5 跟 Qwen3-VL 共享同一 vision encoder 结构（mlx-vlm 的 `qwen3_5/vision.py` 是 5 行直接继承 `Qwen3VLVisionModel`）

P6 的核心论点：**Qwen3.5 架构本质是 multimodal，P4 Dense 是 text-only 退化路径；P6 = 完整 Qwen3.5 推理**。不引入新模型文件，复用已下载的 `Qwen3.5-4B-MLX-4bit`。

## 1. Scope

| 维度 | P6 范围 | P6 不做（deferred） |
|---|---|---|
| 输入模态 | Image（静态图片，单张） | Video → P6.1，Audio → P6.2+，多图同请求 → P6.1 |
| Video 接口 | 留 `temporal_patch_size` + `video_token_id` 路径但不 wire | 端到端 video 推理 → P6.1 |
| 图像预处理 | 纯 Rust（`image` crate）— decode/smart_resize/normalize/patchify | Python fallback、batched preprocessing → 不需要 |
| 模型 target | Qwen3.5-4B-MLX-4bit（本地已有） | Qwen3.5-VL 其他 size、Qwen3-VL → 同架构自动支持 |
| Quant | 沿用 P4 的 4-bit affine（vision_tower 权重也是 4-bit） | 其他 quant scheme → P6.1+ |
| API | OpenAI multimodal `content` array (含 `image_url`) | Anthropic multimodal、video_url、audio_url → 后续 |
| 性能 | 功能正确 + logits 跟 mlx-vlm 对齐 | vision encoder 用 self_qmm 加速 → stage 10+ |

## 3. Module 组织

扩展 `models/qwen3_5/` 而不是新建 `models/qwen3_5_vl/`。理由见 Background — Qwen3.5 本质 multimodal，P4 Dense 是子集。

| `qwen3_5/image_processor.rs` | 纯 Rust 图像预处理 | ~200 |
| `qwen3_5/cross_modal.rs` | image_token_id 替换逻辑 | ~60 |

**修改**：
| 文件 | 改动 |
|---|---|
| `qwen3_5/mod.rs` | re-export 新模块 |
| `qwen3_5/model.rs` | 加 `vision: Option<VisionTower>` 字段；新方法 `forward_vl(input_ids, position_ids, pixel_values, ...)` |

## 4. 数据流细节

### 4.1 Image preprocessing (`qwen3_5/image_processor.rs`)

输入：`img_bytes: &[u8]`（JPEG/PNG/WebP 任意）。输出：`(pixel_values: Array, grid_thw: (i32, i32, i32))`。

```
1. decode → RgbImage  (image crate)
2. smart_resize(orig_h, orig_w) → (h2, w2)
   - 总像素 ≤ longest_edge=16777216
   - 总像素 ≥ shortest_edge=65536（不够则放大）
   - h2 / w2 各自 round 到 32 (= patch=16 × merge=2) 倍数
   - 必须跟 HF Qwen2VLImageProcessorFast 字节级一致（见风险点 R1）
3. normalize：(px/255 - 0.5) / 0.5  →  [-1, 1]
4. patchify：[3, h2, w2]
   - reshape → [3, grid_h, patch=16, grid_w, patch=16]
   - permute → [grid_h * grid_w, 3, 16, 16]
   - 单帧 image：temporal_patch_size=2 通过把同帧重复 2 次实现
     输出最终形状 [grid_h * grid_w * 1 (T=1), 2 (temporal), 3, 16, 16]
   - flatten 最外两轴 → [grid_h * grid_w, 2, 3, 16, 16]
     再扁平 → [grid_h * grid_w, 2 * 3 * 16 * 16] = [N_patches, 1536]
5. grid_thw 返回 (T=1, grid_h, grid_w) 给 vision 模块构造 2D pos_embed
```

`smart_resize` 算法精确参考 mlx-vlm `mlx_vlm/models/qwen3_vl/image_processor.py`（pure Python 实现，5 行可逐行翻译）。

### 4.2 Vision Tower (`qwen3_5/vision/mod.rs`)

```rust
pub struct VisionTower {
    patch_embed: PatchEmbed,
    pos_embed: Array,            // learned [num_position_embeddings=2304, hidden=1024]
    rotary_theta: f32,           // 10000 (固定)
    rotary_dim: i32,             // head_dim / 2 = 32（vision rotary 用半个 head）
    blocks: Vec<VitBlock>,       // 24 blocks
    merger: Merger,
}

impl VisionTower {
    pub fn forward(
        &self,
        pixel_values: &Array,      // [N_patches, temporal*3*16*16=1536]
        grid_thw: &[(i32, i32, i32)],
    ) -> Result<Array> {
        // 1. patch_embed: [N, 1536] → [N, 1024]
        let mut x = self.patch_embed.forward(pixel_values)?;
        // 2. add 2D learned pos_embed (per (h, w) grid position, shared across T)
        x = self.add_pos_embed(&x, grid_thw)?;
        // 3. compute rotary_pos_emb per grid (cos/sin tables for vision attention)
        //    跟 attention 内 q/k 旋转用
        let rotary_pos_emb = self.compute_rotary_pos_emb(grid_thw)?;
        // 4. compute cu_seqlens (per-image segment boundaries; P6 单图：[0, N])
        let cu_seqlens = self.compute_cu_seqlens(grid_thw);
        // 5. 24 ViT blocks
        for blk in &self.blocks {
            x = blk.forward(&x, &rotary_pos_emb, &cu_seqlens)?;
        }
        // 6. merger: spatial 2×2 merge + project 1024 → 2560
        self.merger.forward(&x, grid_thw)
    }
}
```

**位置编码双层**（关键，跟 mlx-vlm 一致）：
- **Learned `pos_embed` 在输入级加** — `nn.Embedding(2304, 1024)`，按 (t, h, w) grid 位置查表
- **Rotary pos emb 在 attention 内对 q/k 旋转** — `inv_freq = 1/(10000^(2i/dim_rot))`，dim_rot = head_dim/2 = 32
- **cu_seqlens 段化 attention** — P6 单图就是 `[0, N_total_patches]`（单段，等价 full self-attention），多图时按 grid_thw 累加分段（每段 `T*H*W` 长度）。多图分段是 P6.1 完整支持。

### 4.3 ViT block (`qwen3_5/vision/block.rs`)

```rust
pub struct VitBlock {
    norm1: LayerNorm,        // weight [1024], bias [1024]
    attn: VitAttention,
    norm2: LayerNorm,
    mlp: VitMLP,
}

pub struct VitAttention {
    qkv: Linear,             // 1024 → 3072 (含 bias)
    proj: Linear,            // 1024 → 1024 (含 bias)
    num_heads: i32,          // 16
    head_dim: i32,           // 64
}

pub struct VitMLP {
    linear_fc1: Linear,      // 1024 → 4096 (含 bias)
    linear_fc2: Linear,      // 4096 → 1024 (含 bias)
    // hidden_act = gelu_pytorch_tanh
}

// VitBlock::forward(x, rotary_pos_emb, cu_seqlens)
//   x = x + attn(norm1(x), rotary_pos_emb, cu_seqlens)
//   x = x + mlp(norm2(x))
//
// VitAttention::forward(x, rotary_pos_emb, cu_seqlens)
//   1. qkv = self.qkv(x).reshape(seq_len, 3, num_heads, head_dim).transpose(...)
//   2. split → q, k, v
//   3. **apply_rotary_pos_emb_vision(q, rotary_pos_emb)** ← 关键，对 q/k 旋转位置编码
//      apply_rotary_pos_emb_vision(k, rotary_pos_emb)
//   4. SDPA per segment（按 cu_seqlens 拆 — 多图时每张图独立 attention 不互相看见）
//      P6 范围：单图 = cu_seqlens = [0, N_total_patches]，单段 SDPA 等价 full self-attn
//   5. proj
//
// VitMLP::forward
//   linear_fc1 → GELU(approx="tanh") → linear_fc2
//
// 注意 vision attention 跟 text attention 双重位置编码：
//   - 输入级：learned pos_embed (per grid position, 详见 4.4)
//   - attention 级：rotary pos emb 在每 block 的 attention 内对 q/k 旋转
```

### 4.4 PatchEmbed (`qwen3_5/vision/patch_embed.rs`)

输入 `[N_patches, 2, 3, 16, 16]`（temporal=2 × channels=3 × patch H×W=16×16）。
输出 `[N_patches, 1024]`。

权重布局（实测从 safetensors 读出）：
- `vision_tower.patch_embed.proj.weight: shape=(1024, 2, 16, 16, 3), dtype=bf16`
- `vision_tower.patch_embed.proj.bias: shape=(1024,), dtype=bf16`

这是 **Conv3D-equivalent** 结构：out_channels=1024, kernel=(temporal=2, h=16, w=16), in_channels=3。等价于把每 patch 的 (2 × 16 × 16 × 3 = 1536) 元素跟 weight 各 1024 个 (2 × 16 × 16 × 3) kernel 内积。

实现：把 weight reshape 成 `(1024, 1536)`、把每 patch flatten 成 `1536` 向量、做 `matmul(patch, weight^T) + bias`。**注意 flatten 顺序必须跟 weight 后 4 维 (2, 16, 16, 3) 一致**，否则结果错。即 patch flatten 顺序是 `(t, h, w, c)`（c 在最内）。

2D pos_embed 加法：
```
for each patch at (t=0, h=row, w=col):
    pos_idx = h * grid_w + w   (or 2D-factorized indexing per Qwen3-VL conv)
    x[i] += pos_embed[pos_idx]
```

### 4.5 Merger (`qwen3_5/vision/merger.rs`)

权重布局（实测）：
- `vision_tower.merger.norm.weight/bias: shape=(1024,), dtype=bf16` — 在 1024 维上做 LayerNorm（**逐 patch token 做，merge 之前**）
- `vision_tower.merger.linear_fc1.weight: shape=(4096, 4096), dtype=bf16` — 4096 → 4096
- `vision_tower.merger.linear_fc2.weight: shape=(2560, 4096), dtype=bf16` — 4096 → 2560

```rust
pub struct Merger {
    norm: LayerNorm,        // [1024]
    fc1: Linear,            // 4096 → 4096
    fc2: Linear,            // 4096 → 2560
}
```

forward 算法：
1. 输入 `[N_patches=grid_h*grid_w, 1024]`（来自 ViT block 输出，跨 24 层后的 patch tokens）
2. `norm(x)` —— per-token LayerNorm on 1024 dim
3. spatial 2×2 merge：reshape 把每 2×2 邻居 patches 拼成一个 4×1024=4096 向量
   - `[grid_h, grid_w, 1024]` → reshape → `[grid_h/2, 2, grid_w/2, 2, 1024]` → transpose → `[grid_h/2, grid_w/2, 2, 2, 1024]` → flatten → `[N_merged, 4096]`
4. `fc1(x)` → GELU → `fc2(x)` → `[N_merged, 2560]`

GELU 的近似类型：vision_config 写 `hidden_act: gelu_pytorch_tanh`（精确 tanh-approximation 版本），跟 ViT block 内的 mlp 用同一个。

### 4.6 Cross-modal Token Routing (`qwen3_5/cross_modal.rs`)

```rust
pub fn replace_image_tokens(
    text_embeds: &Array,      // [B=1, S, 2560]
    input_ids: &Array,        // [B=1, S]  i32
    vision_embeds: &Array,    // [N_merged, 2560]
    image_token_id: i32,      // 248056
) -> Result<Array> {
    // 找 input_ids 中 == image_token_id 的所有位置（按 prompt 顺序）
    // 把 text_embeds 那些位置一一替换成 vision_embeds 顺序填入
    // 用 mlx where + scatter 实现，避免 CPU 循环
}
```

约束：input_ids 中 image_token_id 的出现次数必须等于 vision_embeds.shape[0]（chat template 在 vision_start/vision_end 之间插的 placeholder 数量由 grid_thw 决定）。

### 4.7 MRoPE position_ids 扩展

P4 Dense 的 `build_position_ids(start, len)` 给所有 3 个 mrope stream 同样的 [start, start+1, ..., start+len-1]（text-only 退化情况）。

VL 的 input_ids 含混合 (text token, image token) 序列，每个 image token 占据 2D grid 中一个 (h, w) 位置。MRoPE 三个 stream 的语义：

| stream | text token | image token |
|---|---|---|
| 0 (temporal) | 同 t (= 当前序列累积长度的 t 推进) | t = 当前 image 的 t (单图 t=0) |
| 1 (height) | 同 t | h = patch grid 中的行索引 |
| 2 (width) | 同 t | w = patch grid 中的列索引 |

具体生成函数（暂名 `build_position_ids_vl`）：
```
对每个位置 i in [0, S):
    if input_ids[i] == image_token_id (placeholder for some image at (T, H, W) grid):
        计算这个 token 在 image grid 中的 (t_idx, h_idx, w_idx)
        position_ids[0, i] = sequence_t  // 相对当前 image 起点的 base
        position_ids[1, i] = sequence_t + h_idx
        position_ids[2, i] = sequence_t + w_idx
        (sequence_t 跨 token 推进策略：image 整块算一个 t step；image 后的 text 接续)
    else (text token):
        position_ids[0, i] = position_ids[1, i] = position_ids[2, i] = current_pos
```

精确算法对照 mlx-vlm `qwen3_vl/language.py` 的 `get_rope_index` 函数实现。

## 5. Server API

OpenAI multimodal chat completion 格式（HTTP 请求 body 部分）：

```json
{
  "model": "qwen3_5",
  "messages": [{
    "role": "user",
    "content": [
      {"type": "text", "text": "What's in this image?"},
      {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,/9j/4AAQ..."}}
    ]
  }],
  "max_tokens": 128
}
```

`core/server/openai.rs` 解析逻辑：
- `content` 既支持 string（现有，文本-only）又支持 array of parts
- array 形式逐一处理 part：
  - `type: "text"` → 拼到 prompt 文本
  - `type: "image_url"` → 解 url（`data:image/...;base64,...` 或 `http(s)://...` URL）→ image_processor → 拿到 pixel_values + grid_thw → 在当前 prompt 文本对应位置插 N 个 image_token_id（N = grid_h × grid_w / 4，因为 2×2 merge）
- chat template 应用 `vision_start_token / vision_end_token` 包围

`http URL` fetch 用 `reqwest` blocking 同步调用（仅在 prefill 一次性，不影响 hot loop）。

## 8. 风险点

**R1：smart_resize 跟 HF Qwen2VLImageProcessorFast 字节级对齐**
- 一像素差异让 patch token 全错，logits diff 爆炸
- 缓解：详细对照 mlx-vlm `qwen3_vl/image_processor.py` 逐行翻译；写 unit test 用 100+ 个不同 size 输入跟 HF processor 输出对比 max_diff = 0
- 风险等级：中

**R2：MRoPE position_ids 对 image 区段 (t, h, w) triple 计算**
- Qwen3.5 用了 mrope_section=[11, 11, 10] 把 hidden_size 切给 t/h/w 三 stream
- VL position_ids 跟 P4 现有逻辑差异大，t/h/w 推进规则要严格对齐 mlx-vlm 的 `get_rope_index`
- 缓解：写独立 unit test 用 mock input_ids 跟 mlx-vlm 输出比对；先不做 video（只 image 单帧 t=0 简化）
- 风险等级：高

**R3：vision_tower 权重是 bf16 dense（不是 4-bit quant）**
- 实测确认：`vision_tower.*.weight` 均为 bf16 dense，**没有** `.scales` / `.biases` 伴生（不像 `language_model.*` 是 4-bit quant）
- Loader 改动：`vision_tower.*` 走 dense fp/bf16 加载路径，跟 `language_model.*` 的 quant 路径**分开**处理；`Linear::from_loader` 现有逻辑（probe `{prefix}.scales` 决定 dense/quant）天然兼容，但要确保 vision keys 不误进 quant 分支
- 风险等级：低（已确认）

**R4：Qwen2VLImageProcessorFast 边界条件**
- 极端长宽比（如 1×4096 / 4096×1）、极小 image（< shortest_edge=65536 px）需要触发 upsample
- 缓解：单测覆盖各种边界；遇到则按 HF 实现行为兜底
- 风险等级：低

**R5：mlx-vlm 0.5.0 vs ironmlx link 的 mlx 版本差**
- mlx-vlm venv 拉的 mlx 0.31.2 vs ironmlx link 的 `/Users/sam/.local/mlx`（可能版本不同）
- bf16 数值精度跨版本差异通常 < 1 ulp，max_diff 0.5 容忍内
- 缓解：若超 0.5，确认两版 mlx 同步
- 风险等级：低

## 9. 不在 P6 范围（后续阶段）

- **Video**：temporal_patch_size > 1 处理路径 + video_token_id token routing → P6.1
- **多图同请求**：单 prompt 含多张 image → P6.1
- **Image streaming**：upload 大文件 → P6.2
- **Vision encoder 自研 kernel**：vision_tower 也走 self_qmm 加速 → 不需要（vision encoder 是 prefill 一次性，不是性能瓶颈）
- **Audio**：audio_url + audio encoder → 单独 stage（Qwen3.5 没 audio_config）
- **OCR / 结构化输出**：模型层面已支持，API 层不需要新接口

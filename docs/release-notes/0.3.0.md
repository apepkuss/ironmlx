# IronMLX 0.3.0

[简体中文](../zh-CN/release-notes/0.3.0.md)

## Changes since 0.2.0

This release line adds native speech recognition and realtime audio APIs, and
improves model-component downloads, chat request compatibility and memory recovery.
Publication status and downloads are listed on [GitHub Releases](https://github.com/apepkuss/ironmlx/releases).

<!-- release-summary:stable -->
- Add local Qwen3-ASR 0.6B/1.7B transcription, long-recording segmentation, streaming results and per-model audio limits.
- Add Qwen3 ForcedAligner timestamps and SRT/VTT subtitles, plus Nemotron 3 speaker diarization and optional realtime speaker labels.
- Add realtime transcription through WebSocket and WebRTC audio tracks, with optional server VAD and documented upstream-client examples.
- Improve independent model-component downloads and repair, including auxiliary checkpoints and file-only snapshots that become runnable after validation.
- Support Chat Completions `max_completion_tokens`, `frequency_penalty` and `presence_penalty`, and use the selected model's default output budget when request limits are omitted.
- Fix memory accounting during model loading and first use, and stop idle-model eviction once measured usage recovers below the recovery watermark.

## Speech recognition and realtime audio

Qwen3-ASR runs through the native Rust/MLX engine on the App-managed backend and
CLI model pool. File transcription supports JSON, text and SSE, with automatic
segmentation for long recordings. Each ASR model has independently persisted
duration and output-token limits.

Qwen3 ForcedAligner enables standalone alignment, timestamped transcription and
SRT/VTT subtitles. Nemotron 3 adds independent diarization, speaker-labelled
transcripts and optional continuous speaker labels on realtime sessions.
WebSocket and WebRTC share bounded session admission, optional CPU server VAD,
and cancellation and cleanup behavior. WebRTC uses audio tracks for media and a
DataChannel for session configuration and transcription events.

The Dashboard manages models, settings and service status; recording and result
display belong to upstream clients. Recognition does not translate recordings
or synthesize speech. Denoising is outside this release's scope. Speaker labels
are session-local and do not identify people. See the
[speech recognition, alignment and diarization API](../audio-transcriptions-api.md)
for supported checkpoints, formats, resource limits and protocol extensions.

## Downloads and repair

Downloads can select and validate independent weight components rather than
requiring an unrelated main weight set. Repair handles missing or invalid model
components, while native preflight determines whether a completed snapshot can
run in this version. See [model management](../user-guide.md).

## Chat parameters and memory recovery

Chat output budgets follow `max_completion_tokens`, then `max_tokens`, then the
selected model's configured default, then 256. Explicit limits must be positive;
input plus output must still fit the configured context. Request-local frequency
and presence penalties support values in [-2, 2]; nonzero penalties are rejected
for DiffusionGemma. See the [text and vision API](../text-vision-api.md) and
[parameter validation record](../validation/chat-completions-parameters.md).

Model-load reservations still guard admission, but do not count progressively
allocated weights twice when classifying memory pressure. Already allocated
weights do not require a duplicate first-use reservation. Cache reclamation and
idle-model eviction resample memory before deciding whether further eviction is
needed. Existing pressure hysteresis and degraded-telemetry protection remain
active. See [memory management](../engine-pool.md).

## Compatibility and validation

Requires Apple Silicon and macOS 26.4 or newer. Model weights are downloaded
separately and retain their upstream license requirements. See the
[supported models](../supported-models.md), [known limitations](../known-issues.md)
and [release preparation record](0.3.0-validation.md).

Development tests and historical audio evidence do not establish acceptance of
the final signed installer or production update. The preparation record states
which checks have run and which release gates remain open.

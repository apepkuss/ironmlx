# 0.2.0 build 9 local installation and upgrade acceptance

[简体中文](../zh-CN/release-notes/0.2.0-validation.md)

## Result and scope

On November 1, 2026 (Asia/Tokyo), the full local `0.2.0` build `9` App passed
fresh ZIP/DMG installation, manual replacement upgrades from published `v0.1.0`
and `v0.2.0-rc.4`, pinned-model restoration, real inference, backend crash recovery,
normal App restart and scoped data-preservation checks.

This is functional acceptance of a local ad-hoc-signed App, not acceptance of the
final signed stable release or its production Sparkle upgrade. The candidate was
built from `bae5027eaeefdf0eb295b7efcb2318adbfbaab38` with the build-number change
in the working tree; its Bundle honestly records `IronMLXSourceTreeState=dirty`.
No Rust or Swift runtime source was changed for this preparation. The complete
Bundle manifest, archive checksums, input identities and raw results are retained
locally under `.build/release-readiness/stable/`; generated binaries and models
are not tracked in Git.

## Reproduction and evidence

The reusable acceptance command requires macOS, no running IronMLX instance,
an existing managed model snapshot and an output directory that does not exist:

```bash
python3 scripts/validate-app-installation.py \
  --candidate dist/IronMLX.app \
  --baseline v0.1.0=/absolute/path/to/published-v0.1.0/IronMLX.app \
  --baseline v0.2.0-rc.4=/absolute/path/to/published-rc4/IronMLX.app \
  --model /absolute/path/to/existing/managed/model/snapshot \
  --output .build/release-readiness/stable/installation
```

`installation/results.json` records the per-case Bundle metadata, health, process
identities, inference responses and cleanup. Its adjacent before/after manifests
record each selected file's hash; backend and App logs retain the real recovery
sequence. `installation/candidate-manifest.json`, the generated archive
`SHA256SUMS`, `published/downloads.json` and `build.log` bind the result to the
tested inputs and local candidate.

## Full-App Sparkle acceptance entry point

`scripts/validate-full-app-update.py` additionally exercises actual Sparkle
installation, tampered archives and interrupted downloads using complete Apps.
It requires a Developer ID candidate, published baselines and their Sparkle
helpers signed by the same team, plus the matching local signing identity.
Mixing an ad-hoc outer App signature with a Developer ID Sparkle helper is not a
valid acceptance setup: Sparkle rejects its updater connection before installation.

The tool makes test-only derivatives with a private Bundle ID, Foundation home,
loopback HTTPS feed and ephemeral update key. It verifies that executable code
and other payloads match their inputs, allowing only Bundle metadata and signing
changes. The private Bundle ID also isolates CFPreferences, which is not fully
isolated by `CFFIXED_USER_HOME` alone. Normal installation must replace the App,
relaunch, restore the pinned real model and infer; failure cases must preserve
the old App and data and retain inference. A caller may supply one already-trusted
TLS certificate/key for several runs and must remove that trust after the session.
Without those optional TLS arguments, macOS may require user authorization for
temporary trust creation and cleanup.

The command is for maintainers and never publishes an update:

```bash
python3 scripts/validate-full-app-update.py \
  --candidate /absolute/path/to/signed/IronMLX.app \
  --baseline v0.1.0=/absolute/path/to/published-v0.1.0/IronMLX.app \
  --baseline v0.2.0-rc.4=/absolute/path/to/published-rc4/IronMLX.app \
  --model /absolute/path/to/existing/managed/model/snapshot \
  --signing-identity 'Developer ID Application: Name (TEAMID)' \
  --output .build/release-readiness/stable-preparation/full-app-updates-signed
```

Later preparation results belong in the local
`.build/release-readiness/stable-preparation/readiness.json` evidence index,
including exact source/CI identity, signed artifact hashes, notarization receipts
and the final full-App update result. This initial build-9 record does not claim
those later gates passed without their corresponding evidence.

## Remaining stable-release gates

The build-number and local manual installation/recovery/data-preservation gaps
are closed for the above configuration. The version consistency, distribution
authorization, deterministic SBOM, static Bundle and model distribution gates
passed. Release-identity behavior tests (15), release failure-boundary tests (10)
real Sparkle signature/update-policy tests (5), release-note rendering tests (11)
and Swift Release tests (508) passed; those tests do not publish a release or
validate a production upgrade.

The preparation still needs a committed final source snapshot and successful
CI for that exact commit. Creating the immutable `v0.2.0` tag and completing
stable-channel Bundle identity, Developer ID signing, App/DMG notarization,
Gatekeeper and final stable artifact acceptance remain separate release steps.
The local candidate has updates disabled and must not be relabeled or uploaded
as the official release. Production Sparkle installation from the stable
baseline also remains unverified by this manual-upgrade run. No branch movement,
tag creation, public Release or update-feed publication was performed.

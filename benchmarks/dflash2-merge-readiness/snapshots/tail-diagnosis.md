# DFlash2 长尾解码：诊断

2026-10-08。诊断不作验收。先回答长尾里有没有可以消除的额外开销，再决定是否实施候选。

## 1. 基线与代码路径核对（只读）

- **基线：** `perf/dflash2-b4-throughput` 7669ac04；冻结二进制 `ironmlx-fixed256-fix-8271e413`，sha256 8271e41393de7ff4ba7d7497b87f69239b539201899bf3fef9d0987f009b0ef6，与 `perf-dflash2-b4-throughput/reports/four-app-b1-fixed256-preflight/MANIFEST.sha256` 中登记的一致。
- **工作区：** `/Users/xin/workspace/perf-dflash2-tail-decoding`，分支 `perf/dflash2-tail-decoding`，基于 7669ac04。不含已放弃的预算候选。

**各活跃宽度走的路径（`dflash2_actor.rs` 调度步，产品默认 M5 profile）：**
- **活跃行 ≥2：**
  - 每行把整个已提交窗口一次发布完（`publish_whole_windows`），让各行一起到达窗口边界；
  - 满足资格的行（贪心、无约束、固定预算 7、剩余可生成数 >7、没有待发布 token）组成 ragged 线性组，同组一次窗口；
  - 不满足资格或单独剩下的行，各自走单行树窗口（tree 15 节点）。这些单行窗口在同一步里**串行**执行。
- **组成员变化（有行结束或资格改变）：**
  - 先把整个组缓存散回各行（`scatter_ragged_group`，按行切片后写入行缓存，惰性执行）；
  - 再为新成员建组（`make_cache` 加逐行 adopt，惰性执行）。
  - 这些复制的 GPU 工作会推迟到下一个窗口里执行。
- **只剩一行：**
  - `publish_whole_windows` 为 false，每步只发布一个 token（与单独的 B1 请求相同）；
  - 待发布 token 清空后，才建下一个单行树窗口。
  - 与 B1 单请求完全是同一条代码路径；行缓存是 scatter 写入的普通行缓存，不保留对组缓存的引用。
- **请求完成：** 完成阶段只计数和记账，代码里没有同步或缓存清理。但历史 step log 中，有请求结束的步骤 `complete` 阶段出现过约 44 ms，需要实测确认这是什么。

**据此列出的待查疑点：**
1. 长尾单行的每 token 耗时，是否高于同一任务单独解码同一段 token 的耗时（状态残留、缓存布局等额外开销）；
2. 宽度下降时的切换成本：组缓存散回、重新建组，以及之后第一个窗口的额外耗时；
3. 活跃行 ≥2 时没组成 ragged 组、单行树窗口在同一步里串行的情况，在自然结束负载下有多少；
4. 有请求结束的步骤中 `complete` 阶段的耗时。

## 2. 第一阶段诊断运行（登记于运行前）

- **二进制：** `perf-dflash2-b4-throughput/reports/dflash2-b4-drift-diagnosis/binaries/ironmlx-drift-diag2`，sha256 698e5790…。
  - 它基于 7669ac04，产品行为与基线相同，只多了默认关闭的观测。这里只开已有的 step log，为的是取得每步的绝对时间戳；ragged 主机时间线不开。
  - 观测扰动已在漂移诊断中测过：ragged 窗口耗时不超过 +1.4%，计数不变。
- **会话：** 2 个，每个都是新进程，容量 4、8192，端口 18490，App 环境。每个会话：
  1. 直接调用已提交的 `run_formal.b4_session`：预热批 → 三个批次组合（起始组合按会话序号轮换，批次间隔 2 s）→ 同一进程中依次发 B1 短输入 code-1、knowledge-1、code-3；
  2. 再依次发 code-2、knowledge-2、knowledge-3，间隔 1 s，作为每个任务单独解码时的参照。
- **工作负载：** 原协议的自然结束负载，max_tokens 4096，greedy，关闭思考。每组 2 次计分批次。
- **起始条件：** 与上一轮相同：会话之间至少 10 s，然后等到最近连续 5 个设备采样同时满足压力原始值 0、PMU tdie 最高温度 ≤45.0 °C；最长等待 600 s。
- **采样：** 设备状态每 200 ms 一次，系统遥测每 5 s 一次，footprint 每 50 ms 一次。
- **规则：** 不补跑；任何失败都停止并保留记录。
- **分析方法：**
  - 宽度只用服务端 step log 的 `width`（活跃行数）以及执行路径（ragged 组行数、单行树窗口数）；
  - 时间用服务端的步起点和步耗时；
  - token 数用 SSE 事件计数。SSE 只用来数 token，不用来推断宽度。

**6. 未计入的项（每批）：**
- 请求完成阶段（`complete`）：36.8–41.9 ms，占 0.12–0.15%。
- 多行步骤的 `next_tokens`：231.7–415.9 ms，占 0.86–1.39%。它与 GPU 串行，属于多行调度，消除它需要调度流水线重构，超出本项范围。
- 单行步骤的 `next_tokens` 和 `publish`：19.3–124.8 ms，占 0.06–0.46%。这是"只剩一行时每步发布一个 token"的主机循环，B1 单请求也走同一路径，改动会影响 B1 的发布行为。
- 即使把上述各项全部视为可以消除，每批合计也只有约 1.7%–2.0%。这只是数字上的极端假设：其中大部分不属于长尾，也不能确定可以消除。

## 4. 实施决定：不实施

**本次有限诊断未找到足以支撑 3% 整批收益的、明确可消除的长尾开销，因此不实施。**

- 去重后的长尾和切换相关估算为每批 0.24%–0.60%。
- 主要原因：长尾占整批 5%–33%，主体是最后一个请求剩余工作的单行解码。本次没有找到其中可以明确消除的部分。由于设备状态不同，与单请求参照的对比也不能证明二者等价。
- 已识别的其他开销要么量级很小，要么不属于长尾，要么需要超出本项范围的调度重构。
- 因此不修改产品代码，不进入正确性检查和正式验收阶段，不写正式验收协议。
- **限制：**
  - 只有 2 个会话、6 个计分批次；
  - 使用的是诊断二进制（产品行为与基线相同，step log 扰动不超过 1.4%）；
  - 没有 GPU 命令缓冲区的执行时间；
  - 长尾与参照的设备状态不同。

**现有数据无法回答的问题：**
- 会话 0 S1 首个单行树窗口多出 100.64 ms 的原因：是惰性复制、内存分配、设备状态，还是别的；为什么只出现一次。
- 长尾单行解码与单独解码在相同设备状态下是否等价。
- 切换开销里，有多少是真实的 GPU 工作，有多少是同步等待或可以重叠的主机时间。
- 惰性执行把开销推迟到后续窗口后，有没有被观测到或被算到别处的部分。

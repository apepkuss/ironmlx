# DFlash2 commit/rollback 评估（修订版）

2026-10-08。只读评估：没有修改产品代码，没有构建、运行服务或 GPU 实验。基线工作区为 `perf-dflash2-b4-throughput`，HEAD 7669ac046045d0195537d755da6f23775bab047e，产品代码没有改动。修订前的版本见 `README.v1.md`，改动见 `revision-notes.md`。

## 1. 决定：本轮不继续投入，不实施，也不追加实验

已发现可以进一步精简的工作，但现有证据不足以可靠预测整批收益。本轮决定不继续投入，不实施，也不追加实验。这个决定不代表已证明收益低于 3%：现在只是还没证明值得做，并不是已经证明不值得做。下文第 4 节的未知问题保留，不作为必须继续的阻塞项。

## 2. 已核实的代码事实

**调用链（ragged 线性窗口，`ironmlx-runtime/src/core/dflash2.rs`）：**
1. 验证前对每层做事务快照（第 1794 行），并为线性层开启前缀捕获（第 1797 行）；
2. 验证前向；
3. 按行恢复已接受的前缀（第 1843 行）；
4. 对上下文按已接受长度做惰性切片（第 1852 行）。

树窗口和张量批窗口用的是同一组函数（第 2067–2247、2510 行一带）。

| `ironmlx-lm/src/models/dflash2/attention.rs` 中的 `DFlash2KvCache` | 草稿缓存只追加已接受的上下文 | 不需要回滚 |
| `ironmlx-lm/src/nn/gated_delta_net.rs:889` 起 `restore_speculative_prefix_rows_on` | 每次验证只记录一次前向（`prefix_states` 只有 1 项，少于序列长度），所以先 `restore(base)`（第 949 行），再用带掩码的 gated-delta 内核一次重放所有行的已接受前缀，然后切出新的 conv 状态 | **状态重放本身是正确性所必需的**：不保存逐位置状态，每行每层每个位置约 4 MiB，是有意的取舍 |

| `ironmlx-lm/src/nn/gated_delta_net.rs:385–387`、`647`、`741–758` | `defer_captured_state_commit` 只对树验证和 affine8 b4 q2 开启。Qwen3.8 的 ragged 线性验证（q8）仍输出并写入最终递归状态，还会推进偏移 | **可以精简（一）**：ragged 按行回滚总是先 `restore(base)` 再重放（窗口中每行至少接受 1 个，不会走保留状态的分支），这份最终状态随即被覆盖，期间没有其他读取者 |
| `ironmlx-lm/src/nn/gated_delta_net.rs:1329` 起 `build_gated_delta_kernel_impl`；第 870、991、1120 行 | 重放调用的是通用内核 `build_gated_delta_kernel`（输出 y 和 new_state）。内核对每个位置都计算 `out`（q 与状态的乘加和 `simd_sum` 归约）并写出 y；被掩码的位置还由 32 个线程都写一次 0。三个重放调用点（单行恢复第 870 行，也用于树和单行路径；ragged 按行带掩码重放第 991 行；逐行重放辅助函数第 1120 行）都把 y 取出为 `_unused_output` 后丢弃 | **可以精简（二）**：重放只需要 new_state，但当前的通用内核还包含这些调用者不使用的输出计算、归约和写出。现有的 `build_gated_delta_no_state_kernel` 去掉的是状态输出，不是 y；目前没有只输出状态的内核 |
| 上下文切片（`dflash2.rs:1852`） | 惰性切片，在下一个窗口的草稿依赖中才执行 | 必需 |

所以不能说"最终状态写出是唯一冗余，其余工作全部必要"。状态重放是必需的，但当前的重放内核里也有不被使用的工作。以上两处都是代码事实，还没有验证去掉它们后的效果。

## 4. 带假设的推算（不是上限，也不能用来排除 3%）

修订前的报告把"省掉的最终状态写出量，约为重放读写流量的一半"换算成"耗时最多一半，整批收益约 1–2%"。这一推导的依据不足：
- 流量比例不等于耗时比例。缓存命中、内核中的计算（包括可以精简（二）中的输出计算）、分配，以及与其他工作的执行重叠，都会影响实际耗时。
- 旧基线的屏障计时不能直接换算成当前基线的非屏障收益：版本不同，屏障又改变了执行重叠。
- 推导还漏掉了可以精简（二），它的成本同样没有测量。

如果保留"约 1–2%"这个粗估，它依赖以下假设，任何一条不成立，数字都可能偏高或偏低：
1. 最终状态写出的耗时与它占重放读写流量的比例相同；
2. 旧屏障模式下 commit 占 ragged 窗口 3.5% 的比例适用于当前基线；
3. 去掉这次写出不会改变其余工作的重叠；
4. 不计入可以精简（二）。

这个粗估不能作为收益上限，也不能作为"达不到 3%"的依据。本轮没有可靠预测，因此不做收益估算。

**未知问题（保留，不阻塞）：**
- 当前基线中 commit/rollback 的 GPU 执行成本；
- 可以精简（一）和（二）各自的实际耗时，以及它们与其他工作的重叠；
- 去掉它们后的整批收益，可能低于、接近或高于 3%。

## 5. 本轮停止投入的决定

决定依据是第 1 节：发现了可以精简的工作，但没有可靠的收益预测。本轮的追加优化清单到此结束，不实现只输出状态的内核，不在 ragged 线性验证中启用 `defer_captured_state_commit`，也不追加测量。

**如果以后重新考虑（仅记录）：**
- 可以精简（一）：ragged 线性验证启用 `defer_captured_state_commit`；
- 可以精简（二）：为重放调用者提供只输出状态的内核。
- **正确性要点：**
  - 不输出状态时，缓存不推进偏移，`record_speculative_replay` 记录的 `prefix_state` 是旧状态，必须确认没有调用者使用它；
  - 张量批窗口和单行线性窗口要排除或单独核对；
  - 整窗口全部接受、部分接受和掩码行这三种情况的输出和缓存，都要与基线逐位一致。

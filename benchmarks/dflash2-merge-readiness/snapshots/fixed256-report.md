# 四应用短 prompt B1/B4 固定 256 token 性能对照

**测试时间：** 2026-10-08，UTC 03:47–04:29（正式运行 `formal-v1`）。

**测试条件：**
- 一台 M5 Max 128 GB，接交流电；
- 协议见 `docs/protocol.md`（sha256 ce0cf0fa…，含预检结果与定稿）；
- 运行完整：64 个会话、288 个计分请求，全部有效，0 失败。

**参测版本：**
- IronMLX：修复提交 5273c0b6，二进制 8271e413；
- oMLX 0.7.0；
- Splash 1.3.0（`--kv-format bf16`）；
- TensorFold 0.6.6。1.0.2 不支持本轮指定的模型与外部 drafter，因此经用户明确决定，参测版本为 0.6.6。

**共同条件：**
- 同一模型快照：Qwen3.8-27B-4bit（3e6447f0），DFlash2 drafter（50307d4c）；
- 模型 block_size 8，KV 为 bf16；
- greedy，关闭思考；
- 上下文 8192，请求容量 4；
- 计分请求都输出 256 个 token、以 length 结束，不启用 ignore_eos；
- 零缓存命中，每步都有推测证据。

**单位与读法：**
- 时间单位为秒，速率单位为 tok/s，内存单位为 GiB；
- 主表取四轮中位数，最优值加粗；
- 每个计分请求的原生计数和统一 tokenizer 重计数都是 256，所以两种口径的 Decode 数值相同，表中只列一次。

**修订：** 2026-10-08 修订了 B4 漂移、S1 统计结论、首个内容事件、oMLX verify mode 和内存采样间隔的文字说明（见 `docs/revision-notes.md`）。改动只涉及解释，原始数据、主表和所有数值没有改变。

## 3. 简短结论

**B1 首 token：**
- IronMLX 与 TensorFold 并列最快，0.104–0.146 s，多数任务上只差几毫秒。两项有方向一致的差别：knowledge-1 上 IronMLX 快约 11 ms（TensorFold / IronMLX 为 1.11 [1.09, 1.15]），code-3 上 TensorFold 快约 6 ms（0.96 [0.86, 0.98]）。其余四个任务的区间都跨过 1，不能确定谁领先。
- oMLX 慢约 0.07–0.15 s（0.19–0.30 s），Splash 慢约 0.10–0.12 s（0.226–0.247 s）。四轮方向一致。

**B1 Decode：**
- Splash 在 code-1、code-2、code-3、knowledge-2 上最快。
  - code-2 领先 IronMLX 30.7 tok/s（117.6 对 86.9），比值 1.35 [1.30, 1.45]，四轮一致；
  - code-1 领先 3.3 tok/s，knowledge-2 领先 0.2 tok/s，都在波动范围内；
  - code-3 领先 5.9 tok/s，区间 [0.96, 1.11] 跨过 1。
- IronMLX 在 knowledge-3 上最快（59.0，Splash 58.2，相差 0.8）。
- oMLX 在 knowledge-1 上最快（64.5 对 IronMLX 60.5），比值 1.07 [1.005, 1.10]。
- TensorFold 在 6 个任务上都低于 IronMLX，比值 0.81–0.93，区间都在 1 以下。

**B1 E2E：** 输出长度都是 256，所以 E2E 由首 token 和 decode 共同决定。
- IronMLX 在 code-1、knowledge-2、knowledge-3 上最短；
- Splash 在 code-2（2.39 对 IronMLX 3.06，少 0.67 s）和 code-3 上最短；
- oMLX 在 knowledge-1 上最短（4.15 对 4.32）。

**B4 吞吐和整批耗时：**
- **S1：** IronMLX 吞吐最高（145.7），高于 TensorFold 4.6、Splash 9.2、oMLX 34.9 tok/s。
  - 高于 Splash：Splash / IronMLX 为 0.937 [0.857, 0.994]，区间未跨 1。但区间上限接近 1，只有四轮，IronMLX 本组吞吐又随轮次下降，第 4 轮两者只差 0.8 tok/s（137.9 对 137.1）。
  - 与 TensorFold 的先后不确定：TensorFold / IronMLX 为 0.97 [0.86, 1.04]，区间跨过 1。
- **S2：** Splash 最高（154.3，比 IronMLX 高 17.4），比值 1.13 [1.03, 1.17]；TensorFold 146.9。
- **S3：** TensorFold 最高（135.7，比 IronMLX 高 12.8），比值 1.10 [0.98, 1.14]，区间跨过 1。
- oMLX 在三组中都最低，整批比 IronMLX 慢 1.8–2.2 s，比值 0.76–0.82，区间在 1 以下。

**B4 首个内容事件与吞吐的观察：**

以下是客户端收到各请求首个内容事件的时间，从批内首个请求发出起算（四个请求的发送时间差不超过 1.2 ms）。这些时间不用于推断服务内部的调度或计算开始时间。
- **TensorFold：** 批内 TTFT 中位数最低（0.27–0.30 s）。四个请求的首个内容事件依次到达：第一个在 0.10–0.14 s，相邻两个相隔约 0.09–0.15 s，最后一个在 0.38–0.48 s。
- **IronMLX：** 每批先在 0.105–0.137 s 收到一个请求的首个内容事件，其余三个请求在 0.441–0.511 s 几乎同时收到，三者相差不超过 0.4 ms。所以表中批内 TTFT 中位数与最大值几乎相同。
- **Splash：** 与 IronMLX 形态相同：一个请求在 0.366–0.423 s，其余三个在 0.579–0.687 s 几乎同时收到，三者相差不超过 0.3 ms。
- **oMLX：** 四个请求依次到达，第一个在 0.30–0.42 s，最后一个在 0.74–1.05 s。
- **两项指标的排名不一致：** 批内 TTFT 中位数最低的是 TensorFold；吞吐最高的应用随批次组合变化（S1 IronMLX、S2 Splash、S3 TensorFold）。Splash 的批内 TTFT 中位数在三组中都是四个应用里最高的，S2 吞吐却最高。本轮数据只记录了这两项指标的观察结果，不能说明它们之间存在因果取舍。

**内存（同口径的 OS footprint）：**
- Splash 在 B1 和 B4 的各阶段都最低：B4 生命周期中位数 19.30 GiB，比 IronMLX（22.57）低 3.27，比 oMLX（22.31）低 3.01，比 TensorFold（23.82）低 4.52。
- IronMLX 的 B1 生命周期峰值（19.69）比 oMLX（21.97）低 2.28、比 TensorFold（23.96）低 4.27；B4 生命周期峰值（22.57）与 oMLX（22.31）接近。
- IronMLX 和 TensorFold 的生命周期峰值出现在加载/预热阶段，高于计分阶段。oMLX 在 B1 中也是加载阶段最高；在 B4 中加载与计分阶段相近，12 个会话中有 6 个在计分阶段达到峰值。Splash 的 B4 会话全部（12/12）、B1 会话 4 个中有 3 个，在计分阶段达到峰值。

**输出与配置差异：**
- 所有计分请求都是固定 256 个 token，速度比较不受输出长度差异影响。但这不等于回答质量相同，本轮没有做质量审阅。
- 各应用的推测执行策略不同，按产品默认值保留：
  - IronMLX：线性预算 7 与 tree 15 节点之间切换；
  - oMLX：草稿深度最多 7；
  - Splash：引擎不公开逐轮宽度；
  - TensorFold：lane 轮次。
- 同为 block 8，并不代表每轮的验证宽度相同。

**漂移：** IronMLX 的 B4 吞吐在三个批次组合上整体随轮次下降，其中 S1、S3 单调下降：
- S1：153.2 → 148.3 → 143.1 → 137.9（首尾 −10.0%）；
- S2：146.3 → 135.9 → 138.0 → 129.3（首尾 −11.6%，第 3 轮略有回升）；
- S3：137.0 → 125.4 → 120.5 → 118.8（首尾 −13.3%）。

其他三个应用没有类似的整体下降。原因未明，本轮不归因于热降频或其他具体机制，也没有开展诊断实验。主表和区间使用全部四轮，没有剔除后几轮，也没有用最好的一轮代替；IronMLX 的 B4 中位数和区间因此带有这一不确定性。

**确定性：** 只有四轮。可以视为稳定的差异：
- B1 TTFT 的分层（IronMLX 和 TensorFold 明显快于 oMLX 和 Splash）；
- Splash 在 code-2 Decode 和 S2 吞吐上的领先；
- oMLX 在 B4 上的落后；
- TensorFold 在 B1 Decode 上的落后；
- Splash 内存最低。

S1 中 IronMLX 高于 Splash 的区间未跨 1（0.937 [0.857, 0.994]），但四轮样本少、区间上限接近 1，IronMLX 又有轮次漂移，只能视为较弱的证据。S1 中 IronMLX 与 TensorFold 的先后、S3 中 TensorFold 和 Splash 相对 IronMLX 的先后，以及多数 1–5% 的 Decode 差异，区间都跨过 1，不能写成确定优势。

## 附录 B：版本、配置与执行路径

**身份：**
- 冻结了 1158 个文件的哈希，包括二进制、引擎、各应用源码、客户端、采样器、fixture 和 MLX；
- 模型逐文件核对；Splash 装配目录和 oMLX 模型别名都指向同一快照；
- 每个会话前复核文件元数据，运行结束时复核完整哈希，都通过。

**启动配置：** 见协议的“统一条件”一节。

**实际执行策略：**
- **IronMLX：** M5 profile active，block 8，tree 15，线性草稿预算 7。
  - B1 中 1484 个窗口全部是树窗口，回滚 1484 次；
  - B4 共 3800 个窗口：树窗口 195 个，ragged 线性组窗口 999 个（行窗口 3605 个，建组 36 次），tree 与 ragged 之间切换 52 次，回滚 3400 次；
  - 预算回退和 governor 回退都是 0；
  - **张量批窗口 0 个，这条路径未覆盖。**
- **oMLX：** 外部 DFlash drafter（checkpoint 没有 mtp 权重），草稿深度最多 7，批量时启用 “MTP batch activated”。
  - verify mode 的配置值为 adaptive（`omlx-runtime/model_settings.json` 中的 `dflash_verify_mode`）。**这个配置值在实际的批量 DFlash 路径中被忽略：** 全部 16 个 oMLX 会话（B1 和 B4 都在内）的服务日志都有 `Batched DFlash ignores dflash_verify_mode for qwen38-27b-4bit (single-stream engine settings)`，例如 `s04-r0-B-b1.server.log` 第 72 行、`s05-r0-B-b4-code-1-code-2-code-3-knowledge-1.server.log` 第 69 行。

## 附录 C：失败记录、漂移与限制

**失败记录：** `preflight-b4-v1` 在 oMLX 的 S1 停止，原因是检查规则沿用了旧的 `finish=stop` 要求，已修正并记录在协议中。正式运行没有任何失败。

**漂移：**
- IronMLX 的 B4 吞吐三组整体随轮次下降，其中 S1、S3 单调下降，首尾降幅约 10%–13%，原因未明，见第 3 节；
- 其余应用的轮间波动大多在几个百分点以内；
- 交错顺序只能平衡漂移，不能消除漂移；
- 时间顺序和每会话的数值见分析文件的 `time_order`。

**限制：**
- 只有四轮，区间粗；分位数和最大值不代表稳定的尾延迟。
- 只比较了固定 256 token 的速度，没有比较回答质量。
- B4 每批都在独立会话中运行，不代表持续服务时批次连续到达的情况。
- Splash 的内存前缀缓存无法通过接口关闭。本轮靠独立会话加逐请求核对 cached_tokens 来保证零命中。
- **内存口径：**
  - 这是采样得到的进程树 OS footprint 峰值，不能保证捕获短时尖峰；目标间隔 50 ms，`formal-v1` 实际最大相邻间隔 170.8 ms（见第 1 节）；
  - Splash 诊断中 `--unmapped` 需要 root，没有取得；
  - Splash 引擎 resident 比 footprint 少约 1.9 GB，原因没有完全解释；
  - 结论是“未发现遗漏进程”。
- IronMLX 的张量批路径没有覆盖。
- **结论边界：**
  - 这不能证明 IronMLX 修复前后性能没有回退；
  - 修复验证中出现过两个原因不明的间歇性库测试失败（`mtp_prefill_vl_uses_paged_ssd_prefix_cache_on_exact_hit`、`rejects_a_second_backend_and_releases_on_drop`），仍保留，没有解决。
